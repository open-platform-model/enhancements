# Risks, Drawbacks, Alternatives: Export a Deployed Instance as GitOps Manifests

Risks describe what could go wrong; Drawbacks describe what definitely costs something; Alternatives describe the high-level paths not taken (per-decision detail lives in `03-decisions.md`).

## Risks and Mitigations

- **The first GitOps apply is not the no-op the design promises.** The exported CR's fields are owned by the `opm-cli` field manager and, post-handoff, partly by the operator. Flux's kustomize-controller applies with its own manager, so the adoption is a server-side-apply ownership transfer on live objects. 0006 D40 already found one case where a transfer that "should" have been invisible relabelled every resource in the instance. Blast radius: the instance's workloads, at the moment the user commits and Flux syncs, which is exactly when they are least expecting movement. **Mitigation:** OQ4 is a graduation gate answered by a runnable experiment rather than by reasoning, and the e2e case asserts the inventory entry set is unchanged. If the experiment finds the transfer is not quiet, the honest outcome is to document the expected change (as D40 did) rather than to claim a no-op the mechanism cannot deliver.

- **Completed fields silently change deletion behaviour.** If OQ1 resolves toward completing `spec.prune` to `true` (the demo's shape), an instance that today orphans its workloads on CR deletion will, after the export is committed, delete them instead. That is the safer default and it is still a behaviour change introduced by a command the user ran to "write some YAML". Blast radius: every workload of every exported instance, at some future `kubectl delete`. **Mitigation:** every completion is named in the command output, and the message for `prune` states the before-and-after behaviour explicitly rather than reporting a field name. OQ1's resolution should weigh a `--prune=false` escape hatch.

- **Generated RBAC is either too wide or too narrow.** Emitting a `cluster-admin` binding propagates the demo's acknowledged shortcut into every user's repository; deriving a least-privilege `Role` from `status.inventory` produces authorization that is correct for the current render and fails on the first module upgrade that adds a resource kind. Blast radius: a cluster-wide privilege grant in the first case, a stuck reconcile in the second. **Mitigation:** OQ2 is a graduation gate. Whichever way it resolves, the RBAC document carries a comment naming its own limitation, and the least-privilege option (if chosen) must be regenerable by re-running the export.

- **Plaintext values reach a git remote.** D3 writes `spec.values` verbatim; a user who exports and pushes without reading the warning publishes whatever the instance's values contain. Blast radius: permanent, since git history is not retractable and remotes are frequently mirrored. **Mitigation:** the warning is unconditional and names the file it was written to. The structural fix is enhancement [0013](../0013/), after which secret-bearing values are references rather than literals in the CR itself and the export inherits the property for free. Until then this risk is accepted, deliberately and with the user's agreement (D3).

- **Export becomes stale the moment the CLI is used again.** After the tree is committed, `opm instance apply` writes a spec that Flux reverts on its next reconcile, a silent tug-of-war between two appliers with no error on either side. Blast radius: user confusion and a reverted change, not data loss. **Mitigation:** OQ6. The cheapest form (detect a Flux field manager on the object and warn during apply) needs no new CR field and covers instances that reached git by any route.

- **The verification gate makes export unusable in the one case that most needs it.** An instance whose published module no longer reproduces its deployed render (a module yanked, a tag moved, a render applied from local bytes) cannot be exported. That user has a running workload and no supported way to get it into git. Blast radius: adoption friction at exactly the migration moment. **Mitigation:** `--force` covers the digest mismatch (as it does for handoff), and the local-provenance refusal carries the same remediation handoff prints: publish the module, re-apply, then export. This is an accepted limit, not an oversight: the operator genuinely cannot reconcile a module it cannot resolve.

## Drawbacks

- **A second representation of the same instance now exists.** The CUE instance file, the live CR, and the exported YAML all describe one deployment. The export does not replace the first two; it adds a third, and keeping any two of them in agreement is manual.
- **The exported YAML flattens CUE.** `spec.values` becomes a YAML tree with no schema, no defaults, and no unification. A user editing the exported file gets no type checking until the operator re-renders, a real regression against editing the original instance file, and the direct cost of choosing the YAML output model over the CUE-native one.
- **Another cluster-touching command with a registry round-trip.** The verification gate downloads and renders a module, so export is not a local, offline, fast operation. Exporting twenty instances renders twenty modules.
- **A partially-hand-maintained repository.** The export writes per-instance directories but not the Flux wiring that pulls them, so the user's first GitOps repo is part generated and part hand-written, with no tool telling them which parts they may edit.

## Alternatives

- **Best-effort scaffold with no verification.** Dump, warn, let the user review. **Why not:** the failure it permits (a committed file describing something other than what runs) is the one the enhancement exists to prevent, and warnings do not prevent it (D2).
- **CUE-native export: reconstruct `instance.cue` and emit a `ModulePackage`.** Preserves typing and matches OPM's authoring model rather than translating out of it. **Why not:** it targets a different operator path than the one these instances are already running on, and it is a larger design (source layout, package boundaries, `sourceRef` wiring) than the transcription problem being solved; deferred as a second output mode.
- **Teach the operator to export itself, a CR field or subresource that emits its own GitOps form.** Keeps the logic next to the object. **Why not:** it puts a file-writing concern inside a controller, and the verification render it would need is a CLI capability; the operator has no reason to grow one.
- **Do nothing and document the manual procedure.** Cheapest option, and it would work. **Why not:** the procedure's expensive step is transcribing a values block by hand, which documentation makes no safer, and the incompleteness that makes `kubectl get -o yaml` wrong (`spec.serviceAccountName`, `spec.prune`) is invisible in a document that shows the happy path.
