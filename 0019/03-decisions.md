# Decisions — Kernel render path parity with pure CUE

## Decisions

### D1: Pure-CUE unification is the parity oracle, and divergence is closed by removing kernel behaviour

**Decision:** The reference semantics of the render path are whatever plain CUE unification of `#transform` with its three inputs produces. Where the kernel differs, the kernel is defective. Divergences are closed by **deleting** the kernel behaviour that causes them, not by adding kernel behaviour that emulates CUE more faithfully. The equality is enforced by a differential parity harness in `library`, not by review.

**Alternatives considered:**

- **Treat the current behaviour as the contract and document it.** Rejected: it makes every schema-computed projection permanently unreachable from the render path, and forces `core` to design around a Go-side artifact. The workarounds in open-platform-model/core#49 and open-platform-model/catalog_opm#44 are the first instalment of that tax.
- **Keep the strip and add explicit passthrough for specific fields** (for example, plumb `#names` into a new `#TransformerContext` slot). Rejected: it makes every future projection an explicit plumbing job, and each one is a kernel addition rather than a removal.
- **State parity as a principle without a harness.** Rejected: the current divergence survived three months and two structural refactors precisely because nothing measured it.

**Rationale:** OPM's value proposition is that the schema computes things and everything downstream reads what it computed. A render path that silently narrows the value it passes on is not a wrapper around CUE; it is a reinterpretation of it, and the reinterpretation is invisible to authors until their transformer fails. Making CUE the oracle also makes the kernel's surface shrink over time by default, because every parity failure has removal as its natural fix.

**Source:** User decision 2026-08-19: "It is very important that OPM kernel keep compatability with pure CUE in this regards. I rather remove shit from the kernel to be compatible then to keep it." Evidence: `library/docs/design/repro-purecue-definitions/` (pure CUE renders all eight probed fields concretely, `cue vet -c` exit 0, with a genuinely closed component), and `experiments/01-purecue-render-flow/` (the whole flow expressed as CUE against the real published catalog, outcome 2026-08-19).

### D2: `#transform` executes once per (component, transformer) pair, and `#component` stays singular

**Decision:** The unit of execution is one component. `#component` carries exactly one `#Component`, and the kernel iterates matched pairs. This is the original design intent of the transformer schema, not an artifact of the current implementation, and it is not revisited by this enhancement.

**Alternatives considered:**

- **Pass the component map and let a transformer select.** Rejected on author-facing complexity and on losing per-pair independence, which is what makes the render deterministic and per-pair errors attributable.
- **Leave the question open.** Rejected: `#moduleInstance` reaches sibling components (see OQ4), so the invariant needs to be stated explicitly before that slot is filled, or it silently becomes a convention nobody wrote down.

**Rationale:** Recording the intent matters more than the mechanism here. The current kernel already behaves this way, so nothing changes in code; what changes is that a future reader can tell the difference between a deliberate contract and an implementation detail.

**Source:** User decision 2026-08-19: "I originally designed the transformers schema so that it took one #component because i wanted to execute each transformer on a single component and not multiple."

### D3: `#moduleInstance` is filled by the kernel; it is not removed from the schema

**Decision:** `#transform.#moduleInstance` is intended surface, added so a transformer author can read instance data. The kernel fills it concretely, matching the contract already stated in `core/src/transformer.cue` ("The runtime supplies all three inputs concretely"). Removing the slot from the schema is rejected.

**Alternatives considered:**

- **Delete the slot.** Rejected by the author: the slot is intentional. Deleting it would also close a capability that the pure-CUE control shows works correctly today.
- **Narrow it to instance metadata only.** Rejected as redundant with `#context.#moduleInstanceMetadata`, and as a divergence from CUE in its own right, since a wrapper would hand over the whole value.
- **Leave it unfilled and document it as reserved.** Rejected on the measured failure mode: a transformer reading it vets clean, publishes, and fails at render with a message naming a disjunction rather than the slot.

**Rationale:** The slot is sound. The pure-CUE control fills all three inputs and renders concretely, including the self-referential case where the instance filled into `#moduleInstance` contains the very component filled into `#component`, with no cycle and no error. Only the filler is missing.

**Source:** User decision 2026-08-19: "The comment in transformer.cue even says `#moduleInstance: _ // Fully concrete #ModuleInstance (D18)`. This is the intended behavior." Tracked as open-platform-model/library#65.

### D4: The work lands as several small slices, ordered by what each one removes

**Decision:** This enhancement is executed as a sequence of narrow per-repo changes rather than one render-path rewrite. The parity harness lands first, so every subsequent slice is checked against the oracle rather than against the existing suite. The flow-test fixture's instance construction is repaired inside the slice that exposes definitions, not after it.

**Alternatives considered:**

- **One change that rewrites the render path.** Rejected against the `library` execution gate, which names "redesigning the compile pipeline in one go" as its example of an oversized request, and on risk: the fixture defect below turns a green suite into a false negative if the ordering is wrong.
- **Land the fills first and the harness afterwards.** Rejected: the harness's first failure is the primary evidence for D1, and writing it after the fix discards that.

**Rationale:** The ordering is not administrative. Exposing definitions before repairing the flow fixture would change that fixture from shipping no value to shipping a broken one, because its instance is built by `LookupPath` plus `FillPath` and never wires `#instance`. That is the one sequencing constraint the measurements actually produced.

**Source:** User decision 2026-08-19: "I suggest we split this into multiple openspec changes." Sequencing constraint measured 2026-08-19 against `TestFlow_WebApp_OnOpmPlatform` (`#names.dns.fqdn` reports `required field missing: namespace` in place, while the `synth.Instance` path resolves it).

### D5: A platform imports its catalog and embeds the transformer map into the registry entry

**Decision:** `#Platform.#registry` stops naming a catalog by a version string and starts carrying the catalog's transformer map by import. A registry entry becomes `{enable, #transformers}`, the `version!` scalar is removed rather than made optional, and the catalog build is named the way every other CUE dependency is named: by the platform module's own `cue.mod`. The whole map is embedded; per-transformer selection is deliberately not expressible here.

**Alternatives considered:**

- **Keep `version!` beside the import.** Rejected: two answers to one question, with no way for a reader or the kernel to tell which is load-bearing. Experiment 02 measured that the import is the one that decides.
- **Embed a selected subset of transformers.** Rejected by the author as granularity the design does not need yet, and as a second selection mechanism competing with enhancement 0015, whose provider classes and `TransformerRegistration` own that concern.
- **Leave `#composedTransformers` a kernel-filled slot.** Rejected: with the transformers present in the registry it is a fold over enabled entries, so `library/opm/materialize/index.go` becomes four lines of CUE.

**Rationale:** This is what makes the platform a participant in dependency resolution rather than a bystander to it. A `version` string is inert data that nothing resolves; an import is resolved by the same mechanism that resolves everything else, which is what lets a single build have an answer at all. Enhancement 0010 D14's property survives the change: catalog selection stays a pure function of committed source, because `cue.mod` is committed source. What changes is the sentence, from "the platform file is the resolution" to "the platform module is the resolution".

**Source:** User decision 2026-08-19: "If we move to embedd the transformers, we embed the whole list of transformers, not just a subset. That is to much granularity that we don't need at the moment. Remember the point of 0015" and "I would like the experiment to redefine the schema and embed the catalog.#transformers directly in the registry entry instead." Shape exercised by `experiments/02-platform-authority-mvs/platform/schema.cue`, which also records that the proposal is inexpressible as an extension of core's `#Subscription` (closed around `enable` + `version!`), so it is a core schema change rather than an authoring convention.

### D6: The Platform CR keeps naming a catalog coordinate; the operator generates the platform package

**Decision:** `PlatformSpec` continues to carry typed Kubernetes fields naming the catalog artifact and version, and the operator encodes those into a `#Platform` CUE package on the backend. Publishing a `#Platform` to a registry is permitted but is not a goal of this work.

**Alternatives considered:**

- **Make the CR a reference to a published platform module** (path plus version, under the reserved `opmodel.dev/platforms/…` namespace). Not taken: the author sees no benefit beyond shareability, and it would make every platform edit a publish.
- **Put CUE text in the CR.** Rejected implicitly by D5: a platform with imports needs a `cue.mod`, which a text field cannot carry.

**Rationale:** D5 moves resolution into a `cue.mod`, which the CR cannot express. Generating the package on the backend keeps the operator's API surface typed and validated while giving the build a real module. It also keeps the generation step, which is where a runtime-discovered transformer set has to be folded in anyway (enhancement 0015 D3's `TransformerRegistration`).

**Source:** User decision 2026-08-19: "The Platform CR may still reference the catalog artifact and version, but the operator still encodes that as a #Platform CUE definition in the backend. Should work fine." and "I will allow #Platform to be published but i don't see the benefit of doing it, except sharing is caring." Current shape: `opm-operator/api/v1alpha1/platform_types.go` `Registry map[string]Subscription`.


### D7: Catalog version skew between a module and its platform is detected by the kernel, and the response is caller-configured

**Decision:** When a `#Module`'s declared catalog requirement is **newer** than the build the `#Platform` imports, the kernel detects it and the caller chooses what happens. Two responses are supported: **warn and render anyway**, or **refuse to render**. The choice is kernel configuration, supplied per compile, so `cli` and `opm-operator` can each expose it on their own surface (a flag, a Platform CR field, a controller option) without either of them reimplementing the comparison.

Three things are fixed rather than configurable:

- **The kernel never decides on its own to emit output.** `library/CONSTITUTION.md` forbids the library logging to stdout or stderr, so "warn" means a structured diagnostic returned to the caller, in the shape `compile` already uses for its `warnings` channel. Rendering it is the caller's job.
- **A module requiring an OLDER build is not skew under this decision.** That is the ordinary forward-compatible case and the platform's choice simply stands. It may deserve its own lower-severity signal; that is left to OQ7's residue rather than folded in here.
- **The render module omitting a path is not skew, it is a kernel defect** (OQ6). It is caught by an internal invariant, not by this policy, because no caller should be able to configure it away.

**Alternatives considered:**

- **Always refuse.** Rejected: it makes a platform upgrade a flag day for every module pinned ahead of it, and the measured behaviour shows the render frequently succeeds anyway.
- **Always warn.** Rejected: on a multi-tenant operator a silently downgraded module is exactly the case an administrator wants to stop at admission, and D5 makes the platform authoritative precisely so that intent is enforceable.
- **Compare inside CUE and let the build fail.** Rejected as the sole mechanism: experiment 01's `_versionsAgree` shows the unification is expressible, but a CUE failure cannot be downgraded to a warning by a caller, so it can implement one of the two responses and not the other.
- **Leave it to `cue mod tidy` at authoring time.** Rejected: the skew is between two independently versioned artifacts that meet only at render, and neither author has the other's file.

**Rationale:** Experiment 02 measured that CUE reports nothing here in either direction. Under `pinned` the module's higher requirement is silently downgraded to the platform's build; under `unpinned` the module's requirement silently escalates the platform onto bytes it did not name. `cue vet -c` exits 0 in both. So the fact "this module was authored against a build this platform does not run" exists only if OPM computes it. Making the *response* configurable rather than the *detection* keeps one implementation of the comparison in the kernel while letting an interactive CLI and an admission-time controller take opposite, equally defensible positions.

**Source:** User decision 2026-08-19: "I want to decide that if the #Module is using a newer version of a catalog than the #Platform imports, it should either warn and try anyway or error. This should be configurable in the kernel so that the operator and CLI can both implement configuration options for this." Measured by `experiments/02-platform-authority-mvs/`, whose matrix shows the skew is silent in both directions.


### D8: ADR-002 is superseded, not amended; nothing built is shared between renders

**Decision:** `library/adr/002-concurrent-render-shared-materialized-platform.md` is superseded by this enhancement. Its model, "per-goroutine Kernels, one shared read-only `*MaterializedPlatform`, no mutex", is replaced by a rule with no shared built value in it: **each render is its own CUE build in its own `cue.Context`, and that context does not outlive the render.** Concurrency is across renders, never within one.

The supersession lands as a `library` slice: ADR-002 gains a superseded-by header, a new ADR states the shares-nothing rule together with the `cue.Context` lifetime rule (OQ12), and `opm-operator/internal/platform/store.go`'s single held slot loses its reason to exist.

**Alternatives considered:**

- **Amend ADR-002 to put a mutex around the shared platform.** Rejected on measurement. `experiments/08-concurrent-render-at-scale/` runs exactly that shape: it costs 2.5x to 5.5x the throughput of a shares-nothing worker across 2 to 129 components, and it still retains 348 MB per render because it holds one `cue.Context` for the life of the process. A correction that is five times slower and keeps the other defect is a stopgap, not an architecture.
- **Amend ADR-002 to give each worker a private copy of the materialized platform.** Rejected without a dedicated experiment, on two grounds that do not need one. Its safety rests on the copy being genuinely independent, which is the same assumption ADR-002 already made and lost. And it is the per-worker-retained-context shape at a different granularity, which experiment 08 measures at 41.9 MB per render on a 2-component module rising to 581.8 MB at 129, reaching 23.4 GB resident through 32 renders.
- **Leave ADR-002 standing and let the collapse quietly not use it.** Rejected. `store.go` is built around it, so an ADR describing a model nothing runs is worse than no ADR: the next person to touch the render path would implement it again.

**Rationale:** ADR-002 drew its own caveat correctly and then set it aside. It recorded that "the verified guarantee is reads-only", and filling a shared value is a write to that value's evaluation state rather than a read, which is precisely the failure `experiments/06-concurrent-render/` reproduced at 2321 reports (1540 after pre-evaluating the shared value, so laziness is not the cause). What makes this a supersession rather than a bug fix is that the trade the ADR was making no longer exists. It traded a safety assumption for speed; experiments 07 and 08 show the shared model is also the *slower* one, at every module size, once holding the platform forces the serialisation its races require. There is nothing left on its side of the ledger.

**Consequences:** an operator sizes a render pool by memory rather than by core count, because a render is single-threaded and the binding constraint is the working set (see `06-operational.md`). D8 also closes the shape most likely to be proposed as a replacement: building the instance once and then executing the matched pairs in parallel. Measured on experiment 08's harness, forcing `rendered` concrete after `BuildInstance` returns costs 3.0 ms of an 1831 ms render, so the pairs are already evaluated and there is no parallel phase to schedule; and rendering one component of a 129-component instance still costs 70% of rendering all of them, which caps splitting the pairs across parallel builds at 1.43x for K times the working set. Rendering different instances concurrently gets 4.0x to 4.3x for 1x the memory each, so the parallelism worth having is the one D8 already permits. The materialize-once machinery in `opm/materialize` shrinks or goes, which D5 already gated. Nothing in the render path holds a value across a reconcile, so the store's cache-invalidation question disappears rather than being answered.

**Source:** User decision 2026-08-19: "I want to superseed ADR-002. Please incude that in the scope of this enhancement." Measured by `experiments/06-concurrent-render/` (the races), `experiments/07-module-scale-cost/` (the cost model), and `experiments/08-concurrent-render-at-scale/` (the serialised yardstick and the retention figures).


## Open Questions

- **OQ1: Does anything still depend on multi-version-per-major catalog composition?** Status: resolved (no), pending ratification. ADR-003 chose federation over single-build evaluation because "a platform may subscribe to multiple versions of the same catalog path and major at once", which CUE's Minimal Version Selection forbids inside one build. Enhancement 0010 D14 later deleted that capability: `#Subscription` carries one scalar `version`, `#Platform.#registry` is keyed by a major-qualified `#ModulePathType`, CUE map semantics enforce one subscription per key, and D14 states the rule as permanent rather than transitional. If no code path still assumes breadth, ADR-003's premise is stale and federation is defence against a condition the design no longer admits. Measured 2026-08-19: the capability is not merely unused, it is inexpressible. `core/src/platform.cue:65` keys `#registry` by the major-carrying `#ModulePathType` and `#Subscription.version` is a required scalar, so CUE map semantics admit exactly one build per key, and the file's own comment states the rule as permanent while dismantling each use of breadth. On the Go side the only code assuming breadth is `indexCatalogs`' same-FQN collapse path, which its own comment (`library/opm/materialize/index.go:68-77`) calls "largely defensive": through the real `#Catalog` shape two builds sharing an FQN key necessarily differ on `modulePath`, and distinct versions produce distinct keys. ADR-003's federation premise is therefore stale. D5 supersedes the question outright by removing the version scalar.

- **OQ2: Can an evaluated `#ModuleInstance` participate in a CUE build as an importable package?** Status: largely answered, pending ratification. Single-build evaluation of the render step requires the instance and the catalogs in one build. The instance exists today as an in-memory `cue.Value`, not as an importable module, which is the friction. `synth.Instance` already stages the synthesized instance package inside the acquired module's own source tree and evaluates it through the normal loader, so the gap may be smaller than it appears. But "the instance is a package on disk during synth" is not the same as "the render step can import it alongside a platform's catalogs". Two findings close most of the gap. `opm/helper/synth/render.go:60-66` records that the synthesized `instance.cue` is overlaid INSIDE the module's own staged main module, so a single build containing the instance already exists today; what is missing is the platform beside it, not the mechanism. And experiment 02 demonstrated the missing half: an unpublished local module enters a build through a `cue.mod/local-module.cue` directory replacement, which `cue/load` honours on the ordinary loader path (`cue/load/config.go:581-620`) and which `mod/modfile/schema.cue`'s `#Strict` forbids in published modules, making it structurally a build-local, kernel-owned mechanism. What remains open is not feasibility but ownership: which module is the main module of the render build (see OQ6).

- **OQ3: In a single build, MVS could override the version the platform names.** Status: resolved (the premise was wrong), pending ratification. Refuted by `experiments/02-platform-authority-mvs/`, outcome 2026-08-19. If the instance's module and the platform's catalogs resolve in one build, MVS selects one version per path and major. A module whose `cue.mod` pins a catalog higher than the platform's subscription would win, and the platform would materialize bytes it did not name, contradicting 0010 D14's core property, "the platform file *is* the resolution", which is what makes catalog selection a pure function of committed source. This is a design fork rather than a verification task. Candidate positions: refuse the mismatch loudly at load; accept MVS as the CUE-native answer and restate D14; or keep the two resolutions in separate builds and accept that the render step cannot be a single build. `experiments/01-purecue-render-flow/` makes this executable: its `_versionsAgree` unifies the platform's subscribed version with the one `cue.mod` selected, and fails the build if they diverge. It also interacts with the skew failure in open-platform-model/library#57, which single-build would resolve deterministically rather than dodge. The question is whether that resolution is the wanted one.

  **Measured answer: minimum version selection does not run at load time.** `cuelang.org/go@v0.17.1` `internal/mod/modpkgload/import.go:93-98` resolves an import by first consulting the main module's own dependency list (`RootSelected`, which returns the declared version) and falls back to the full module graph and its maximum-version selection only for paths the main module does not list. MVS is what `cue mod tidy` computes when it WRITES a dependency list; it is not re-derived when a build reads one. A committed `cue.mod` is therefore a resolution, not a floor. The matrix confirms it end to end: with the render module listing the catalog at the platform's build, a consumer module demanding a higher version is inert and the platform's transformer bytes execute. Authority is lost in exactly one cell, `unpinned` plus a consumer pinning higher, which reframes the risk from "MVS overrides the platform" to "the kernel forgot to write the pin down" (OQ6).

- **OQ4: Should sibling-component access through `#moduleInstance` be constrained?** Status: open. D2 fixes the unit of execution at one component. D3 fills `#moduleInstance`, which contains `components`, so a transformer can reach every sibling. Per-pair independence therefore becomes an authoring convention rather than a structural property, with consequences for whether renders can be reordered, parallelised or cached per pair. A strict reading of D1 says leave it: CUE unification hands over the whole value, and narrowing it would itself be a divergence. The counter-reading is that D2's invariant deserves structural support. Worth deciding explicitly rather than inheriting, and worth measuring whether any real transformer would want sibling access.

- **OQ5: Should `#TransformerContext` become a projection of the other two inputs?** Status: open. Every field except `#runtimeName` is derivable from `#moduleInstance` and `#component` (the table in `02-design.md` lists the derivations). If `core` makes them projections, `library` deletes the Go structs it decodes metadata into and the re-encoding step, and `opm/schema/context.go` collapses to filling one string, removing a hand-maintained mirror of the schema that can drift. Two things make it attractive beyond the deletion: the migration is safe, because for one release the kernel can keep filling values identical to what the projection computes and unification simply agrees; and it moves computation from Go into CUE, which is the direction D1 points. Demonstrated rather than argued in `experiments/01-purecue-render-flow/`, whose `_contextFor` derives every field from the two inputs in 18 lines of CUE. Held open because it changes `core` shapes, carries a `SPEC.md` co-update, and wants its own evidence rather than riding on this entry's.

- **OQ6: What does the kernel-generated render module owe its own `cue.mod`, and what refuses a render when it cannot supply it?** Status: open, and it is now the load-bearing single-build question. Experiment 02 showed the failure mode is omission, not override: a path the render module does not list is answered by the module graph's maximum-version selection instead, and that is the only cell in the matrix where a consumer module changed which transformer bytes executed. A real render glue imports the instance and the platform and has no reason to import the catalog, so omission is the natural default rather than an unlikely slip. The same trap has a subtler form: a default major version is honoured only for a path that is a root dependency, so the catalog's own `default: true` for `cue.dev/x/k8s.io` stopped working the moment the catalog left the roots. The generated render module therefore needs the complete tidied dependency set, not just the OPM paths. Open: does the kernel compute that set itself, run a tidy-equivalent, or refuse to render when it cannot produce one; and is there a check that no path in the OPM namespace resolves from the graph rather than from the roots.

- **OQ7: Should the kernel detect and refuse module-versus-platform skew, given that CUE reports nothing?** Status: resolved by D7; residue below. In every `pinned` row of experiment 02's matrix the consumer module is evaluated against a catalog its own `cue.mod` does not name, and `cue vet -c` exits 0 with no diagnostic. One row silently downgrades a consumer that demanded `2.0.0-alpha.4` to `2.0.0-alpha.3`. That is the intended power relationship under D5, but it means "this module was authored against a build this platform does not run" is a fact only OPM can report. D7 settles the shape: the kernel detects, and the caller picks warn-and-render or refuse. Three sub-questions remain open. **Which way does it default** when a caller says nothing, given that `cli` and `opm-operator` plausibly want opposite defaults. **Where does the comparison read the module's requirement from**, since after D5 the platform's own answer is its `cue.mod` while the module's is the staged tree's `cue.mod`, and the render module's list is a third file that may agree with neither. **Does a module requiring an OLDER build get its own signal**, which D7 deliberately left out. It also still interacts with open-platform-model/library#57, whose skew failure single-build makes deterministic rather than absent.

- **OQ8: What is the unit of reuse once every render is its own build?** Status: answered on feasibility by `experiments/04-render-build-cost/`, on throughput by `experiments/06-concurrent-render/`, on scale by `experiments/07-module-scale-cost/`, and on both together by `experiments/08-concurrent-render-at-scale/` (outcomes 2026-08-19), pending ratification; what remains is which reuse shape is legal, not whether the collapse is affordable. `opm-operator/internal/platform/store.go` plus ADR-002 establish the current model: materialize once per Platform CR generation, hold one read-only `*MaterializedPlatform`, render many `ModuleRelease`s concurrently against it. A per-render single build dissolves that: the catalog is parsed and evaluated again for every instance. Experiment 03 tested the obvious answer, sealing the platform into catalog-independent CUE, and refuted it: `cue def --inline-imports` emits source that does not re-parse, is not self-contained, and carries dangling references. The alternatives left are sealing by vendoring the catalog's bytes into a platform artifact plus a directory replacement (untested, but the mechanism is the one experiment 02 exercised), batching many instances into one build (which reintroduces cross-instance resolution coupling, since one module's pin would decide another module's transformers), or measuring the per-render cost and accepting it. Nothing here is decidable without a measurement of what a render build actually costs.

  **Measured answer: reuse is an optimisation, not a precondition.** A per-render single build costs **2.1x** the held-platform baseline (90.2 ms against 42.3 ms, warm, `n=50`), memory is flat (6 to 10 MB retained after an arm, drift negative), and a cold cache costs 1.76 s once per process rather than per render. Against the 10x threshold the experiment set before it was written, that is a wide hold, so ADR-002's materialize-once model can be decided on operational grounds rather than on feasibility.

  One finding narrows what remains. **A shared `cue.Context` recovers only about 14%**, not the catalog term: every render in that arm resolved and evaluated the same platform bytes through the same context and still paid 32 ms of load and 56 ms of build. So "share the context and the catalog becomes free" is off the table, and if the per-render cost ever does need to come down, the candidates left are the two this question already named, vendoring the catalog's bytes into the platform artifact plus a directory replacement, or batching instances into one build with the cross-instance coupling that implies. Neither is tested. One limit was stated rather than measured at the time: the ratio comes from a two-component module with five pairs and should be re-measured on a large module before it is quoted as general. Experiment 07 did that, and the limit turned out to matter more than the number.

  **The concurrency residue is closed, and it narrows the reuse candidates further.** `experiments/06-concurrent-render/` (outcome 2026-08-19) measured the sweep the sequential number needed: renders do run at the same time, about 4x on eight cores, taking the single build from roughly 11 renders per second to 44, and the 2.1x multiplier survives concurrency essentially unchanged (2.18x at peak throughput). So the affordability verdict stands rather than sitting under an untested ceiling. Two of the reuse strategies this question was weighing are removed by the same experiment, on grounds that have nothing to do with cost. Holding one materialized platform and rendering against it concurrently, which is ADR-002's model and what `store.go` is built around, produces thousands of data races on the shared value graph (OQ13). Holding a `cue.Context` per worker retains about 37.5 MB per render for the context's lifetime (OQ12). What survives is the shape that shares nothing between renders, which is also the fastest thing measured.

  **The size caveat is discharged, and it inverts the question.** `experiments/07-module-scale-cost/` (outcome 2026-08-19) swept two purpose-built large modules, a 129-component fleet and a 32-component module of deep guarded components, each authored both with blueprints and with raw resources and traits, and fitted a cost model to each sweep. Per-render cost is `fixed + slope x components` with R^2 above 0.9996 in all eight fits, and the two terms answer this question directly.

  The single build's **fixed** term is 81.5 to 89.1 ms and does not move across fixtures or authoring styles. That is the catalog: resolved (a flat 31 to 42 ms of load at every size in the sweep) and evaluated once per render. It is precisely the term a reuse strategy would target, and it is all such a strategy could ever buy.

  The single build's **per-component** term is LOWER than the baseline's in every case (7.71 against 12.17 ms, 14.01 against 19.31, 22.79 against 33.35, 34.13 against 46.83), because today's path pays per component forever: finalize the component, build `#context` in Go, `FillPath` once per pair. So the two curves cross, at 4.6 to 14.2 components depending on fixture and style, and past that the single build is the cheaper one. At 129 components it renders in 1.08 s where today's path takes 1.59 s, allocating 913 MB against 1.9 GB.

  What this does to OQ8: the reuse candidates are unchanged in kind and much narrower in scope. They pay off only for modules below roughly a dozen components, and they buy at most about 85 ms. Experiment 07's shared-context confirmation sweep prices the cheapest of them exactly, 9 to 11% at one or two components and 1 to 4% at eight or more, which is experiment 04's 14% finding with its shape explained: sharing shaves a fraction off the fixed term and nothing off the per-component term.

  **The crossover was an artefact of comparing sequentially, and it does not survive the safety constraint.** `experiments/08-concurrent-render-at-scale/` (outcome 2026-08-19) ran 07's fixtures byte for byte through 06's worker pool. Concurrent speedup turns out to be independent of module size, 4.28x, 4.33x, 4.24x and 4.05x at 2, 9, 33 and 129 components, which is close to perfect scaling on the eight physical cores available and reproduces 06's figure at 64 times the module size. Since 06 established that today's path cannot be run concurrently at all, the comparison an operator actually faces is a render worker that shares nothing against today's path serialised behind a mutex:

  | components | single build, best P | today's path serialised | ratio |
  | --- | --- | --- | --- |
  | 2 | 37.07 renders/s | 14.95 | 2.48x |
  | 9 | 19.92 | 4.88 | 4.09x |
  | 33 | 7.65 | 1.46 | 5.26x |
  | 129 | 2.10 | 0.38 | 5.49x |

  At two components, where 07 measured the single build costing 1.74x more per render, it still delivers 2.48x the throughput, because it can use the other seven cores and today's path cannot. So OQ8's reuse question loses its last cost argument: there is no module size at which holding a platform is the faster option once holding it forces serialisation. What remains for this question is entirely operational, chiefly the memory table in 08 (sixteen concurrent renders of a 129-component module need about 14 GB), which argues for sizing a render pool by memory rather than by core count.

  One finding from 07 belongs here rather than to the catalog, because it replaces the mechanism this entry assumed. The definitional payload the collapse stops stripping is **free**. No transformer in `catalogs/opm` reads a definition field off `#component`, and CUE is lazy, so `#resources`, `#traits`, `#blueprints` and `#names` ride into `#transform` unevaluated. Finalizing them is not free: the baseline must export the whole component value to strip them, which is why its per-component term is the larger one and why a blueprint-authored component costs it MORE per component (+13.5 ms) than it costs the single build (+11.3 ms). The strip costs more than the thing it strips.

- **OQ9: With enhancement 0015's `TransformerRegistration`, the effective transformer set is discovered at runtime. What regenerates the platform package, and what keys it?** Status: open. D6 puts platform-package generation on the operator, and 0015 D3 makes the transformer set grow after the Platform CR is written: a provider module ships a registration among its rendered resources, the Platform reconciler accepts it, and the materialized set changes. Under D5 that set is expressed as imports, so an accepted registration means regenerating the package and re-resolving its `cue.mod`. 0015 already flags that `store.go`'s single slot keyed on `.metadata.generation` has to be re-keyed; single-build makes the same question sharper, because the key now identifies a whole module graph rather than a value.

- **OQ10: With several catalogs in one build, whose requirements decide the shared paths, and where is a conflicting registration refused?** Status: open. A base catalog plus each registered provider's catalog all sit in the render build, and they share paths: `core` certainly, and the base catalog itself, since a provider catalog depends on it for the contract definitions its transformers embed. OQ6's answer determines the mechanism (whatever the render module lists wins), but not the policy: what happens when an accepted registration requires a `core` or base-catalog version the platform does not run. The natural place to refuse is 0015 D3's claim-and-accept gate, at registration time rather than at render time, so the failure names the provider rather than an unrelated instance. Worth deciding before the generation step is written, because it decides whether the operator needs a resolution step of its own.

- **OQ11: Does publishing a `#Platform` mean anything, given that a published module cannot carry a build-local override?** Status: open, low priority. D6 permits publishing without pursuing it. If a platform is ever published, `mod/modfile/schema.cue`'s `#Strict` refuses `replaceWith` in it, so a published platform can express its authority only through its own `cue.mod` pins, and those pins become roots only if whoever generates the render build promotes them. In other words publishing a platform publishes its intent but not its enforcement, which is worth stating before someone assumes otherwise. The reserved `opmodel.dev/platforms/…` namespace (`opmodel.dev/site/content/reference/registry-namespaces.md:20`) is where this would land, and its own documentation still calls registry-published platforms an open design question.

- **OQ12: What may a long-lived render worker hold between renders?** Status: open, and answerable cheaply. `experiments/06-concurrent-render/` measured that a `cue.Context` releases nothing until it is dropped: about 37.5 MB per single-build render and about 9.2 MB per render on today's path, flat in worker count and exactly linear in render count (5.9 GB after 160 renders through four reused contexts). Dropping the context per render costs nothing measurable and holds retention under 2.5 MB at every worker count, so the mechanical answer is easy. What is open is where the rule lives and who is bound by it. The kernel's own `Kernel` type is documented as one per goroutine and is the natural place to carry a context, `library/CONSTITUTION.md` gives the kernel no process model to hang a lifetime policy on, and `opm-operator` is the caller that would notice first. This is not a defect the collapse introduces: today's path has the same shape at a quarter of the size, so the question is owed an answer whether or not this entry lands. `experiments/08-concurrent-render-at-scale/` closes the measurement half at realistic module sizes and makes that sentence exact. Per-render retention scales with the module: a reused context holds 41.9 MB per render at 2 components (an independent reproduction of 06's 37.5 MB on a different harness), 71.8 MB at 9, 173.8 MB at 33, and 581.8 MB at 129, reaching 23.4 GB resident through only 32 renders. Today's held-platform path retains 348 MB per render at the same size, because it holds one `cue.Context` for the life of the process by construction. A fresh context per render holds 117 KB per render at 129 components and is flat in render count. So the rule to write is not about the collapse at all: it is that a `cue.Context` may not outlive the render that created it, and the collapse is the only measured shape in which obeying that rule is affordable. D8 gives that rule a home: the ADR that supersedes ADR-002 states it alongside the shares-nothing rule, which leaves this question owing only the enforcement, since `library/CONSTITUTION.md` gives the kernel no process model on which to hang a lifetime policy.

- **OQ13: ADR-002's shared materialized platform races under concurrent render. What replaces it?** Status: **resolved by D8** (user decision 2026-08-19), pending the `library` slice that writes it down. It reaches outside this entry. `library/adr/002-concurrent-render-shared-materialized-platform.md` adopts "per-goroutine Kernels, one shared read-only `*MaterializedPlatform`, no mutex", on the strength of a raw-CUE spike that measured cross-context `FillPath` as race-clean on `v0.17.0-alpha.1`. Against the real catalog on `v0.17.1`, `experiments/06-concurrent-render/` reproduces the opposite: 2321 data-race reports in that exact shape, every one of them two workers meeting in `adt.(*scheduler).signal` through `Vertex.lookup`, reached from `Value.FillPath` on the shared platform value. Forcing the held value graph to evaluate fully before sharing it does not help (1540 reports), because filling a shared value is a write to its evaluation state rather than a read, which is the distinction the ADR's own "the verified guarantee is reads-only" caveat drew and then set aside. No wrong value was ever produced, across every strategy and worker count, so this is undefined behaviour rather than demonstrated corruption. D8 answers the first of the three things this question opened: the ADR is superseded rather than amended, and what replaces it is a rule with no shared built value in it. Two remain, and neither blocks the collapse. Whether `opm-operator`'s render path is serialised in the meantime is a live-fleet decision with a measured price (2.5x to 5.5x throughput), and it is only owed for as long as the operator still holds a platform. Whether the finding is worth an upstream CUE report is unanswered; the reproduction is small and the behaviour may well be intended, since nothing in the `cue` API documents `FillPath` as safe on a shared value. The single-build path is not blocked on any of them, since it shares no built value between renders. `experiments/08-concurrent-render-at-scale/` prices the conservative fix: serialising today's render path behind a mutex costs 2.5x to 5.5x the throughput of a render worker that shares nothing, at 2 to 129 components, and it still retains 348 MB per render. That makes serialisation a stopgap rather than a resting place, and it is an argument for superseding ADR-002 rather than amending it. The detector was also re-run at 33 components with eight workers against both the shares-nothing shape and the serialised one: zero reports, so module size does not change 06's safety verdict for either.

- **OQ14: Finalization reorders map-derived lists, so today's path and the collapse emit different bytes for the same input. Which ordering is the contract?** Status: open, and it is a migration question rather than a design one. `experiments/07-module-scale-cost/` compared every render's bytes across both arms and found 16 of 28 points byte-identical and 12 identical modulo LIST ORDER, with nothing genuinely different. The 12 are exactly the fixture whose container environment is assembled from several guarded sources: `library/opm/compile/finalize.go` re-emits a component through `Syntax(cue.Final())`, which hoists comprehension-produced fields ahead of plainly-declared ones, and the catalog then converts the environment MAP to a Kubernetes LIST, so the order difference reaches the object. The fixture whose environment is written out plainly renders byte-identical in both arms. Two consequences. Landing the collapse changes the `env` ordering of exactly those modules that assemble environments conditionally, which is a server-side-apply diff on the first reconcile after the upgrade and nothing after that; and it means today's ordering is an artifact of the strip rather than anything a module author chose, so "preserve it" is not obviously the right answer. Worth deciding before the graduation plan names a rollout, and worth a note in the migration guide either way.
