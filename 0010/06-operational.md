# Operational Concerns — Module and Catalog Identity

This document is the OPM Production Readiness Review (PRR-lite). Five fixed prompts — answer every one, even briefly.

## Observability

**What new signals, metrics, diagnostics, or error types does this enhancement introduce, and how are they surfaced?**

Five new diagnostics, all errors rather than metrics — plus one condition that deliberately does not become one, listed last. Most replace something that currently fails opaquely; two have no predecessor at all, because the conditions they name could not arise under the old keying.

- **Address mismatch at read (D11).** A typed error naming both the declared `modulePath` and the coordinate the artifact was fetched by. Emitted from `library/opm/helper/loader/registry/module.go` on the acquire path, from `library/opm/materialize` on the catalog pull, and from the platform-subscription check. The CLI and the operator inherit it from one implementation. Today the equivalent condition surfaces downstream as `module not found` or not at all.
- **No provider for a contract (D4, D28).** An error naming the contract demanded and stating that no catalog subscribed by this platform implements it at any API version. Emitted from the match path, and it is a statement about the **platform** rather than the module — the actor who can fix it is the one who chose the subscriptions. Computed by splitting the API version off the demanded FQN and collecting supplied keys sharing that path-and-name; an empty result is what distinguishes it. Under D28 it fails the render rather than being collected.
- **Wrong API version at match (D4).** The same computation with a non-empty result: the contract is implemented, at an API version this module does not speak. Kept distinct because the remedy differs — migrate the module, versus install a provider.
- **Incompatible contract bodies at match (D27).** The always-unify rung's failure, naming the field the module set and the build the provider was compiled against: "this platform's provider predates that field". This diagnostic has no predecessor — under the build-keyed contracts D4 replaced, the condition could not arise, because the keys never met.
- **Two providers for one contract (D32, D37).** A hard error at **materialize**, before any module is rendered, naming both catalog paths and the contract key. Raised in the kernel so the CLI and the operator inherit one implementation; a CLI platform walker reporting the same condition earlier is a convenience on top, not the guard. This one also has no predecessor, and what it replaces is silence rather than a bad message: today both transformers pair, both render, and one component emits two copies of the same workload with no error and no warning. The test keys on a contract's declared `fulfilment` and counts **required** demands only — bucket arity is not the signal, since `catalog_opm`'s own `#ContainerResource` bucket legitimately holds 8 transformers.
- **Missing identity.** Not an OPM error at all: an unfilled identity field surfaces as CUE's own `incomplete value string`, naming the file and line of the declaration. That is deliberate (D6) — absence propagates as absence rather than being translated into an OPM-flavoured message that could be confused with a value.

The `module.opmodel.dev/version` label becomes a real signal for the first time (D9): it now carries the version of the artifact that was actually fetched, so selecting deployed resources by module version starts returning correct results.

## Semver Impact

**Is this a breaking change for any consumer? If so, what's the backwards-compatibility plan?**

Breaking, but **not a `core` major-version event**. Measured 2026-08-05: `opmodel.dev/core@v1` has published `v1.0.0-alpha.1`, `.2` and `.3` and **no stable `v1.0.0`**, so the SemVer compatibility promise has not started and the break lands in `v1.0.0-alpha.4` with the module path unmoved. What follows is the full extent of the break; what it is *not* is a `@v1 → @v2` migration. `#Module.metadata.version` is **retained** (D2) but its source moves to a module identity subpackage and neither `fqn` nor `uuid` reads it, `metadata.modulePath` changes both shape and value, `metadata.name` is retyped, `nameSnakeCase` and `#KebabToSnake` are deleted, `#Module.metadata` gains `registryPath` (D41) and no version-major agreement (D45 — the identity package asserts it, as it does for `#Catalog` under D43), `#ModuleInstance.metadata` gains an `fqn` and re-derives `uuid` from it (D41), and `#SubscriptionFilter` is **deleted outright** — `#Subscription` carries a required scalar `version` in its place (D14). `opmodel.dev/core` is consumed as a published dependency by every module and every catalog, so nothing built against the current alpha keeps working — but every consumer is a repo in this workspace pinning an explicit prerelease (`catalog_opm` and `catalog_kubernetes` on `alpha.1`, `catalog_opm_experimental` on `alpha.3`), so the retarget is a `task update-deps` sweep over an enumerable set.

`#FQNType` **splits** under D4 into `#ContractFQNType` and `#ImplFQNType` (`@SemVer`). Every FQN value changes and, for the three demand-side kinds, so does the shape: a consumer matching on a SemVer tail must be updated. The contract tail is not a bare major — under D34 it is `#APIVersionType`, admitting `vN`, `vNalphaM` and `vNbetaM`, so anything parsing the tail has to accept all three forms. This is the largest single break in the entry after the module path itself.

Two further breaks land on catalogs rather than on modules. **D36** moves matching out of `metadata.labels` into a dedicated `matchLabels` field on `#Resource`, `#Trait`, `#Blueprint` and `#Component`, deletes `#LabelWorkloadType`, and renames the key it named to `opm.opmodel.dev/workload-type` under `catalog_opm` ownership; every primitive that declares a matching label and every transformer's `requiredLabels` moves with it. **D37** adds `fulfilment: *"catalog" | "provider"` to `#Resource` and `#Trait`, which is additive and defaulted — no existing declaration changes meaning.

There is no compatibility shim and none is proposed: the identity of every artifact changes, so a shim would have to maintain two identities for one artifact, which is the condition this entry exists to remove. The plan is a coordinated window rather than a transition period — see Cross-Repo Coordination.

Downstream impact is uneven and worth stating separately. `opm-operator` needs **no feature code change**: `api/v1alpha1/common_types.go:36-45` already types `ModuleReference` as `{Path with major, Version tag}` and reconcile reads only spec fields, never a module's metadata. No user-authored CUE breaks either — `core/src/module_context.cue:13-18`'s `#InstanceIdentity` carries `name`, `namespace`, `uuid`, `clusterDomain` and never exposed a version, so no module template, trait, or resource can reference one.

The last row is the only removal in this table with a **fleet-visible output change**, and it is worth calling out separately because it is the one an operator will notice without reading any CUE. Rendered objects carry `core.opmodel.dev/workload-type` today via the `componentLabels` fold at `transformer.cue:147-157`, and they will stop — a label removal on every live workload. It lands inside the identity migration window rather than adding a second one, and anything selecting on that label (dashboards, `kubectl` selectors, network policies) must be re-pointed first. D36 records the decision as provisional and `experiments/04`'s `v_render` demonstrates an opt-in fold working, so re-adding it costs four lines if the removal proves wrong.

No deprecation aliases are kept. An artifact published under the old shape is not readable under the new one, which is the point of the coordinated window.

## Rollback

**If this lands and proves bad, what's the rollback story?**

Code rollback is clean; data-plane rollback is not, and that asymmetry is the thing to plan around.

Re-pinning `core` back to `v1.0.0-alpha.3` across `library`, `cli`, the catalogs, and the module fleet restores the previous behaviour, and previously-published artifacts remain consumable because they were never modified — the migration republishes rather than rewrites. Both alphas coexist in the registry indefinitely, for the same reason two majors would: a published tag names fixed bytes permanently (0011 D10). That the rollback is a re-pin rather than a major revert makes the code half *cheaper* than it looks; it changes nothing about the data half below.

What does not roll back is the identity label on already-deployed resources. Instances applied under the new identity carry the new `module-instance.opmodel.dev/uuid`; rolling the code back makes the operator compute the old UUID again, and `prune.go:107` will then skip deletes for those resources rather than adopting them. So a rollback after any instance has been reconciled under the new identity needs the same adoption pass the forward direction needs, run in reverse — **relabel in place, never delete and recreate**, per D18: the operator sets no `ownerReferences` and `ModuleInstance`'s finalizer does not garbage-collect on a recreate, so tearing the CR down leaves the old resources holding the old UUID and every subsequent prune hits the mismatch skip. The same positive check applies in reverse as forwards, and for the same reason: remove a resource from the module, re-render, and confirm it is actually deleted. An absence of errors does not demonstrate it — `prune.go:112` increments `result.Skipped` and logs at Info, emitting no Event, status field or metric.

Scope note, because D18 makes it easy to misread: this entry runs **no live-instance pass of its own**. The whole deployed fleet is on the v0 schema line, so the rollback exposure above belongs to the future v0 → v1 migration that carries 0010's shape as its target state. Treat that migration as one-way in practice and rehearse it on a non-production cluster first.

## Migration Inventory

The full enumeration is [`research/migration-inventory.md`](research/migration-inventory.md), measured 2026-07-30 against the workspace registry (`localhost:5000`) and the live cluster, and **extended 2026-07-31 to `ghcr.io/open-platform-model`**, which is the registry the fleet actually resolves against. It exists because D18 rejected an operator-side tolerance window on the ground that the fleet is *enumerable* — so the enumeration is a gate, not a convenience, and it is now satisfied by data on both registries rather than by a stated absence on one.

Headline counts: **12 live `ModuleInstance`s** across 10 distinct modules (two modules carry two instances each), and **1 `Platform` with 3 subscriptions** — the entire D14 rewrite surface in production is three `range` lines. On the **workspace** registry, **39 published module repositories**, **4 catalog repositories**, and **17 non-module artifacts sharing the namespace** (the `library/testdata/modules/web-app` fixture with 11 tags, 10 legacy `…/v1alpha1` paths, `kubernetes/v1`, 4 `releases/*` repositories, and one empty repository), 74 repositories in total. On **GHCR**, 53 packages.

Four findings from the measurement change what the migration has to do, and each is load-bearing:

1. **The live fleet does not resolve against the registry this workspace publishes to.** It resolves against **`ghcr.io/open-platform-model`**, and the reason the operator Deployment shows no registry configuration is that it needs none: `opm-operator/cmd/main.go:94-98` gives the `--registry` flag a **compiled-in default** of `testing.opmodel.dev=ghcr.io/open-platform-model,opmodel.dev=ghcr.io/open-platform-model,registry.cue.works`. The cluster observations were accurate — no `CUE_REGISTRY` env, no registry argument, no mounted config, no `envFrom`, re-verified 2026-07-31 — but nothing in a cluster object could have revealed the value, because it is in the binary. Measured against the workspace registry, **ten of the twelve live instances, across eight of the ten distinct modules**, name coordinates absent from `localhost:5000`: three modules have no repository there at all, and five more exist only below their deployed versions. Only two coordinates resolve locally.

   **The migration spans two registries, and that finding stands** — 74 repositories locally against 53 packages on GHCR, neither a subset nor a superset of the other. What has closed is the collection gap: GHCR enumerates completely through `gh api --paginate`, and **every live coordinate is present there at its deployed version**, including all three modules the workspace registry lacks entirely. So the two-registry finding now constrains the runbook rather than blocking it from being scheduled.

2. **`opmodel.dev/catalogs/opm_experimental` and `opmodel.dev/catalogs/opm-experimental` both exist**, both holding a `v1.3.0-alpha`. Under D4 a catalog path is the permanent prefix of every contract FQN, so two spellings are two key spaces and a module built against one cannot match a platform subscribed to the other. This is the failure D1 and D8 exist to prevent, already live in the registry.

   **Resolved 2026-07-31: `opm_experimental` is canonical and the hyphen repository is deleted.** This is a cleanup rather than a choice between two candidates, and re-measuring says why. The catalog's own source declares the underscore — `catalog_opm_experimental/src/cue.mod/module.cue` is `module: "opmodel.dev/catalogs/opm_experimental@v1"` — and on the **fleet-facing registry the cutover between the two spellings is datable to an eighty-minute window**. Read from GHCR 2026-07-31: the hyphen package holds six versions running `2026-05-31T08:06` → `2026-07-27T15:09` (`v0.0.0-dev.*` ×2, `v1.2.0-dev.*` ×2, and the release tags `v1.2.0-alpha` and `v1.2.0-alpha.1`); the underscore package's earliest version is `2026-07-27T16:30`, and every publish from then through `2026-07-28` — including `v1.2.0-alpha.2`, `.3` and `.4` — went to it. So the underscore is strictly the newer line and nothing has been published to the hyphen since the cutover. (The dev registry shows a different and partial population — hyphen `v1.3.0-alpha` only, underscore `v1.2.0-alpha.1`, `v1.2.0-alpha.2`, `v1.3.0-alpha` — which is why the two registries had to be read separately.) So the hyphen form is not a parallel release line, and the live platform already subscribes to the underscore. **It is legacy rather than accidental, which is worth stating because it explains why it exists:** the hyphen was once *mandated* — an older `core.#ModulePathType` forbade `_` in path segments, recorded in `backup/CLAUDE.md:246` ("hyphen, not underscore — `core.#ModulePathType` forbids `_`; the repo name keeps the underscore") and carried as the module path through enhancement 0002 in June 2026. Core then changed deliberately in the other direction, and `core/src/types.cue:18-26` now permits underscores *specifically* so a snake_case catalog leaf is legal. The hyphen repository is what the pre-change spelling left behind. Underscore is also the only form that *can* be canonical: a CUE module's package name is inferred from its path leaf and only a snake_case leaf is a valid CUE identifier, which is the constraint `core/src/types.cue:18-26` documents in these exact terms. Nothing needs to be republished, re-pinned or renamed, because every consumer is already on the surviving spelling — verified 2026-07-31 by grepping every `cue.mod/module.cue` in the workspace, which yields no pin of the hyphen form in any module, catalog or fixture. **The deletion is in two registries, not one** — the GHCR read on 2026-07-31 found both spellings published to `ghcr.io/open-platform-model` as well as to `localhost:5000`.

   **Status: DONE in both registries (2026-07-31).** On `localhost:5000` the repository was removed on disk (`catalog/.registry-data/docker/registry/v2/repositories/opmodel.dev/catalogs/opm-experimental`), because the container runs `registry:2` without `REGISTRY_STORAGE_DELETE_ENABLED` and its delete API answers `405`; its blobs stay in the shared blob store until a garbage-collection pass, which is harmless, since the repository and its tags are what made the second key space reachable. On GHCR the package was deleted through the API, which required an OAuth token carrying `delete:packages` — note the refusal message names `read:packages` too, but `write:packages` satisfies that half. Verified after: the hyphen package returns `404`, the only surviving experimental package in either registry is `opmodel.dev/catalogs/opm_experimental`, and it is intact — 10 versions on GHCR carrying `v1.2.0-alpha.2`, `.3`, `.4`, and three tags on the dev registry. **One key space, one spelling.**

3. **`opmodel.dev/modules/opm-platform` is in module space and is probably not a module** — which defeats 0011 D5's premise that module, catalog and schema space are distinguishable by path alone. **Downgraded to cleanup on the 2026-07-31 GHCR read:** it is absent from GHCR and exists only on `localhost:5000`, as does the `library/testdata` fixture, so it is dev-registry hygiene rather than a wrong input to a fleet migration. The design question it raises is not closed by that and is not this entry's to close — it is 0011 OQ9, which asks what reserved segments `Platform` and instance artifacts get.
4. **The source tree and the registry are neither a subset nor a superset of each other.** `modules/` holds 12 module directories; three have no repository on the *workspace* registry, and two — `cdi` and `snapshot_controller` — have source with no artifact measured anywhere. **Most of this dissolved on the 2026-07-31 GHCR read:** the three missing ones are published on GHCR at exactly their deployed versions, so they migrate like any other module and only `cdi` and `snapshot_controller` remain sourced-but-unpublished-anywhere. Both are design-only stubs with no `cue.mod` (re-verified 2026-08-05), and a source with no artifact does not need migrating — so what remains is a reconciliation to *record* before step 6 rather than a blocker on it.

Two smaller items the runbook should not rediscover, stated without identifying the instances: exactly one live instance is a `@v0` test artifact rather than a real workload, which makes it the cheapest subject for D18's positive check — **though it has since been removed from the cluster (2026-08-05), so that check needs a purpose-created throwaway instead**; and two modules each carry two instances differing only by instance name within one namespace, so they are the pair that exercises `SHA1(module-uuid : name : namespace)` rather than the module path alone. The per-instance enumeration is held out of band — see [`research/migration-inventory.md`](research/migration-inventory.md)'s redaction note.

### Which registry the migration republishes into

The fleet resolves `opmodel.dev/*` against **`ghcr.io/open-platform-model`**, supplied by a compiled-in `--registry` default in `opm-operator/cmd/main.go:94-98` rather than by anything visible in the cluster. A **dedicated central registry on Zot** is planned to replace that arrangement.

This does not change what the migration does — 0010 changes identity values and 0011 D5 changes the namespace, and neither depends on which host serves the bytes — but it does change *when* it should run. The 0011 D5 namespace move rewrites every published coordinate, so doing it into GHCR and then moving hosts to Zot pays the republish cost twice. **Sequence the namespace move and the registry host move together, or do the host move first.** The choice is a scheduling decision rather than a design one, and it belongs to whoever owns the Zot rollout.

One consequence worth carrying into that rollout: `resolveRegistry` (`main.go:334-342`) documents a precedence of *`--registry` > `OPM_REGISTRY` > CUE default*, but returns the flag value whenever it is non-empty and the flag's default is non-empty — so `OPM_REGISTRY` on the operator is inert today. Retargeting the fleet at Zot means changing the flag default or passing `--registry` explicitly; setting the environment variable will not do it.

## Cross-Repo Coordination

**Which repos must coordinate, and in what order?**

Strictly ordered, because each step consumes a published artifact from the one before:

1. **`core`** — cut `v1.0.0-alpha.4`. Nothing else can move until this tag exists. **Not a major bump**: `core@v1` has published only prereleases, so `opmodel.dev/core@v1` is unmoved and every step below is an ordinary `task update-deps` re-pin rather than a major retarget. The three schema slices in [`plan.yaml`](plan.yaml) land into this one unpublished alpha, and `core-alpha-release` is the cut point — which is why it exists as a slice rather than as whichever schema change merged last.
2. **`library`** — re-pin to `v1.0.0-alpha.4` (a dep bump, not a major retarget); land the D11 read-side checks, D14's **deletion of `materialize/filter.go`** (nothing resolves, so what survives is a single major-agreement check on one string, not a reduced filter), D26's provenance exclusion in D30's denylist form and D27's promise in the match rung, D28's hard failure on an unresolved demand, D32/D37's single-provider guard at materialize, D36's `matchLabels` move on the *read* side (`compile/match.go:111` reads `metadata.labels` today), the D4 diagnostics, and D9's acquire-time comparison of a declared version against the fetched tag — **not** a kernel stamp, which D9 reversed on 2026-08-04. Ships the behaviour every frontend inherits. D26 is the one that cannot be deferred: without it every build skew fails on provenance and contract keys deliver nothing. [`plan.yaml`](plan.yaml) splits this step five ways — the dep bump (`library-core-retarget`) is isolated from the four behaviour changes so each starts from a building tree.
3. **`catalog_opm`** (under D47 the single first-party catalog — `catalog_kubernetes` folds in as the `k8s-*` raw family and `catalog_opm_experimental` as `v1alpha1` members, their v2 lines ending at the `v2.0.0-alpha.1` each already published) — commit `identity/identity.cue` in the D5 shape, consolidate per D47–D49, delete the stamping task, republish. Modules cannot migrate until a conforming catalog exists to build against.
4. **`cli`** — retarget to the new `library`; delete the address-composition helpers; write the resolved coordinate into `spec.module.{path,version}`.
5. **`opm-operator`** — retarget to the new `library`. **No feature change of any kind**, and no adoption code: D18 rejected an operator-side tolerance window outright, on the ground that a single-operator fleet is enumerable and every tolerance mechanism ships code that then has to be removed. Whatever adoption the v0 → v1 migration needs is a run-once pass, not operator behaviour.
6. **`modules`** — add an `identity/` subpackage per module exporting `ModulePath` **and** `Version`, wire `metadata` to it (D2, 0011 D12), move the twelve D42 blueprint imports, republish the fleet through `opm module publish`. The version is **retained**, not dropped (D2), and there are **no renames**: measured 2026-08-05, no hyphenated module name remains on either branch.
7. **Deployment repositories** (outside the workspace; named out of band) — **no step.** 0011 D13 leaves first-party coordinates unmoved, so nothing pinning one breaks and there is nothing to re-pin (0011 D17). Their own v0 → v1 migration is separate work, and the measurement says why they could not have been re-pinned in either direction anyway: their modules are on the `v0_legacy` line, with **zero** overlap with the eleven v1-line modules step 6 republishes.

Two coordination notes that are easy to miss. Step 3 must complete before step 6 can be *validated*, because a module carries the primitive definitions its own `cue.mod` resolved — so a module republished against a pre-migration catalog demands keys built from the old `modulePath` and no post-migration platform supplies them. And step 2's filter deletion is load-bearing for step 3 rather than cosmetic: both workspace catalogs publish only prereleases today, so under the whole-major default D14 replaced, a platform subscribed to a republished catalog materialized nothing.

### Where enhancement 0011 binds, and where it does not

This is stated twice in the pair of entries and has been read both ways, so it is worth separating the two claims:

- **At the level of the entries, neither blocks the other.** 0010 can be designed, sliced and landed without 0011, and the reverse holds too. Steps 1–5 above have no 0011 dependency at all. The intermediate state is valid in either order: 0010 alone leaves modules at `opmodel.dev/modules/jellyfin@v2` — old namespace, new shape — which resolves and renders normally, and 0011 alone rewrites a path prefix rather than a full path, which also works.
- ~~**At the level of the fleet republish, they share one window.**~~ **Superseded 2026-08-04 by enhancement 0011 D13 and D17 — there is no shared window, because there is no second coordinate rewrite.** This bullet held while 0011 D5 moved every module to `opmodel.dev/m/<owner>/<name>`; D13 keeps first-party modules where they are, so 0011's step 3 rewrites no coordinate and moves no owner label. Step 6 below is now the **only** fleet republish, and 0011 contributes to it rather than duplicating it: the republishes go through `opm module publish` instead of the modules repo's checksum task, which 0011 D15 deletes. One event, one pass.

So there is no migration to schedule between the two entries, and the preference [`04-graduation.md`](04-graduation.md) records is now simply true rather than a trade-off — nothing is bought by pairing them because nothing is paid by separating them.

One thing that does **not** need coordinating: catalog releases after the migration are unilateral, and under D4 this extends to a case build-keyed contracts could not serve — a **provider** catalog and the catalog defining a contract release independently of each other, which is what makes a platform-fulfilled primitive possible at all. Nor does a catalog release move what an existing platform runs: under D14 a subscription names one build, so a new publish is not selected by anything until someone edits `version:` in the platform's own source. That inertness is the property [`04-graduation.md`](04-graduation.md) makes an `accepted → implemented` gate.
