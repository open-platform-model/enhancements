# Risks, Drawbacks, Alternatives — Module and Catalog Identity

This document records the honest costs of the proposed design. Risks describe what could go wrong; Drawbacks describe what definitely costs something; Alternatives describe the high-level paths not taken (per-decision detail lives in `03-decisions.md`).

## Risks and Mitigations

- **Every module identity changes once, and an un-migrated live instance silently stops pruning.** `fqn` changes shape, so `module.uuid` changes, so `instance.uuid` changes, so the `module-instance.opmodel.dev/uuid` label on every deployed resource changes. `opm-operator/internal/apply/prune.go:107` tolerates an *empty* live label but skips a delete when the live label disagrees with `Status.InstanceUUID` — and it **skips without erroring**, so reconcile reports success while garbage collection has quietly stopped.

  **Blast radius is bounded, and deliberately so.** OPM has one operator today and the deployed fleet is enumerable — the deployment repositories' instance configs plus the CLI's CR inventory name every live instance. So this is a one-time, single-operator migration rather than an ecosystem event, and it does not need a compatibility path: no operator tolerance for a recorded prior UUID, no transition window, no dual-identity support. Recorded as a decision about *this* migration's circumstances rather than a general property — the same change made after OPM has external consumers would need all three.

  **What does not shrink is the silence.** A skipped prune produces no error, no event, and no status change, so nothing tells the operator that an instance was missed. Being the only user makes the fleet fixable; it does not make the problem visible. **Mitigation:** the migration is manual and enumerated (walk the deployment repositories, relabel or recreate each instance), and it is followed by a **positive check** rather than an absence of complaints — for at least one migrated instance, remove a resource from the module, re-render, and assert the resource is actually deleted from the cluster. That check is what distinguishes "migrated correctly" from "migrated and silently broken", and it is cheap exactly once.

- **RETIRED BY D4 — a subscription that does not cover the fleet's authorship history.** Under the build-keyed contracts D4 replaced, a module matched only the exact build it was authored against, so a materialized set omitting that build failed the demand. Contract keys remove the condition: a subscription covering any build in the major supplies the contract. What replaces it is the risk below, which is smaller in blast radius and larger in subtlety.

- **RETIRED BY D14 — a catalog release could move every render on the platform, with nothing in git changing.** While contract keys carried the build, the key pinned the transformer, so a catalog release was inert until a module was rebuilt. D4 removed that pin and left the platform's subscription resolving at materialize time — `filter.go:43-47` selecting the highest published stable, with `MaterializedPlatform.Resolved` (`materialize.go:109`) in-memory only — so publishing a catalog build could change what every installed module rendered, discovered by whoever reconciled next. D14 deletes the resolution step: a subscription names its builds, so a new publish is selected by nothing and the release is inert again. Worth recording rather than deleting, because this risk is also the general form of a failure the project already met once (enhancement 0006 OQ18, CI `-dev` tags winning every prerelease-tolerant range) and patched by pinning one platform by hand. What remains is the *deliberate* case: an operator who edits `versions` is choosing new rendering logic for every module on the platform, which is the intended interaction and is visible in a diff.

- **RETIRED BY D14 — the materialized set grew monotonically and nothing pruned it.** Under the whole-major default D14 originally carried, every published build in a subscribed major was pulled and indexed, so cost scaled with the catalog's release history rather than with what the fleet used. D14 now makes the set exactly what the platform wrote down, so it never grows on its own and pruning is deleting a line. **Fully retired, and OQ15 with it.** The residue this paragraph once recorded — an author naming two builds on purpose, filling one contract bucket with several builds of one catalog's transformer, every one pairing and every one rendering — is unreachable under D14's final shape: a subscription names *one* build, so two builds of one catalog cannot meet in a bucket and there is nothing to tie-break. Duplicate output across *different* catalogs is a separate condition and is refused at materialize by D32/D37.

- **Prereleases are the live regime, and a selection mechanism that ranks them wrongly excludes the whole fleet.** `catalogs/opm` has published only `v1.0.0-alpha*` and `catalogs/kubernetes` carries `v1.1.0-alpha` (registry read 2026-07-27). Under today's `filterVersions` a bare subscription resolves one build and the obvious range (`>=1.0.0 <2.0.0`) selects **zero**, because Masterminds constraints exclude prereleases unless the constraint itself carries one — and enhancement 0006 OQ18 records the mirror failure, where `-dev` tags sort above `alpha` and win every range that *does* tolerate prereleases. Blast radius: the entire current fleet. **Mitigation:** D14's named build rather than a maturity flag. A named version is selected because it was named; there is no ordering to get wrong in either direction, and nothing to forget to opt into.

- **A shared-resolution render would disable the only compatibility check there is.** A module's primitive definitions must resolve through the *module's own* dependency graph. That holds today — `library/opm/compile/module.go:137` consumes `mp.Transformers` from `materialize` as read-only input built by a separate resolver. If a single-build render put the module and the platform in one CUE build, minimal version selection would pick the maximum and the module's copy of every contract definition would silently become the platform's. Under D4 the symptom was a demand for the platform's build that matched anyway. Under D4 it is worse in kind: the always-unify rung (D26, D27) is now the *only* thing verifying that the module's contract body and the provider's agree, and with one resolution it would be comparing a value against itself — it can never fail, and the additive-only promise stops being checked at render at all. **Mitigation:** state it as an invariant of the render path rather than an incidental property, and cover it with a test that fails if the two resolutions are ever merged. The in-flight render rewrite in `library` must be checked against this before it lands.

- **Removing a required field from a published schema breaks every consumer at once.** `opmodel.dev/core` is consumed as a published dependency by every module and every catalog. Blast radius: nothing built against the current alpha keeps working. **Mitigation:** measured 2026-08-05, `opmodel.dev/core@v1` has published `v1.0.0-alpha.1`, `.2` and `.3` and **no stable `v1.0.0`** — the SemVer compatibility promise has not started, so there is none to break. The change lands in `v1.0.0-alpha.4` with the module path unmoved, and every consumer is a repo in this workspace pinning an explicit prerelease: `catalog_opm` and `catalog_kubernetes` on `alpha.1`, `catalog_opm_experimental` on `alpha.3`. The catalogs and the module fleet still migrate in a coordinated window rather than opportunistically — that half is unchanged — but the window is a `task update-deps` sweep over an enumerable set rather than a major migration.

- **An unfilled identity field can be published.** Measured 2026-07-26: `cue mod publish v1.2.0 --dry-run` succeeded on a tree whose identity fields were open, and `cue vet` *without* `-c` reports `some instances are incomplete` and exits 0. So neither CUE's publish nor a default vet gate blocks an artifact with no identity in it. Blast radius: a consumer of that artifact, which fails at evaluation with `incomplete value string`. **Mitigation:** D11's read-side checks are the guarantee, and every OPM vet path passes `-c`. The degradation is safe — absence fails loudly and names the field — but it fails at the consumer, which is why the check belongs there rather than only in a publish task.

- **The address check makes the registry a harder dependency.** Verification adds a way for a fetch to fail that authors did not previously have to reason about, and the error surfaces inside the operator's reconcile loop as well as at the CLI. Blast radius: any environment where a conforming artifact is misread. **Mitigation:** the error names both the expected and the actual coordinate, so diagnosis is immediate, and the check compares only what `#FetchedArtifact` unifies — not a broader notion of well-formedness.

- **Anything that lets a module's version or major reach the owner label silently orphans every resource an upgrade removes.** The mechanism: a moving input changes `instance.uuid` → the `module-instance.opmodel.dev/uuid` label on every rendered resource, and `opm-operator/internal/apply/prune.go:107` then skips any delete whose live label disagrees with `Status.InstanceUUID`, which `reconcile/moduleinstance.go:308` repopulates from each render. **Blast radius: every deployed instance, on every upgrade, with no error.** `prune.go:112` increments `result.Skipped` and logs at Info, emitting no Event, no status field and no metric, so the failure presents as a successful reconcile that quietly stopped collecting garbage. This is the single most dangerous regression available in the identity design.

  **There are two routes in, and only one of them was closed before D41.** D2 deleted `#Module.metadata.version` because `fqn` interpolated it, and D1 closed that route independently by making `fqn` the module path — which is what let D38 restore the field. The second route stayed open and unremarked: `instance.uuid` derived from `module.uuid`, which carries the **major**, so a `@v2 → @v3` upgrade orphaned everything the new major stopped rendering. D1 reduced the exposure from *every release* to *every major*; it did not remove it. D41 removes it by deriving instance identity from the module's major-free `registryPath`.

  **Mitigation:** both halves of the invariant are stated in `core/SPEC.md` beside the fields rather than only in this entry (§3.2 for artifact identity, §3.5 for instance identity); `schemas/target.cue` carries three MUST-FAIL cases — `_moduleFqnLeak` (a version in `fqn`, refused structurally), `_moduleMajorSkew` (D40's agreement check), and `_instanceFromFqn` (a module path substituted for a registry path, refused by `#PackagePathType` on the type rather than the value); and `04-graduation.md` requires tests asserting both that changing only `version` moves neither `fqn` nor `uuid`, and that a **major** bump moves `module.uuid` while leaving `instance.uuid` fixed. Both directions are asserted, because a test that only pins what must not move will not catch an identity that has stopped distinguishing what it should.

## Drawbacks

- **The module path is stated twice.** `cue.mod/module.cue`'s `module:` line and `identity.cue`'s `modulePath` carry the same string. D1 does not remove that duplication, it makes it *comparable* — one complete string against another, rather than a fragment reassembled from parts. Keeping the two in step is a job for tooling and for the D11 read-side check. Accepted: the alternative that removes the duplication (deriving inside CUE) forces every artifact to carry attribute-and-regex boilerplate and cannot be done on a consumer's behalf.

- **A fresh clone of a catalog does not vet until a version is supplied**, if its author chose the open form (D6). `cue vet -c` reports one named incomplete field. **D4 narrows this back**, undoing the widening build-keyed contracts caused: contract keys interpolate `apiVersion`, which is authored per primitive and always concrete, so an unfilled `Version` leaves only the transformer keys and the provenance stamps non-concrete. D6's original split — identity concrete ⇒ the contract key space evaluates — holds again for three of the four primitive kinds.

- **A primitive's `fqn` becomes author-writable, and `core` can no longer refuse a wrong one.** D21 moves the FQN from a `core` derivation to a value each catalog authors from its identity package. Measured 2026-07-27, that is a real loss of enforcement in both directions: under the derivation, a disagreeing author fails at the catalog's own `cue vet` with `conflicting values "1.2.0" and "1.1.0"` naming both sites; under an authored FQN, a catalog on `1.2.0` shipping `fqn: "…/secrets@1.1.0"` passes `cue vet -c` with **exit 0**. Because D4 makes a key name its own bytes permanently, a wrong key that ships is a key modules match against forever. Accepted deliberately, and the mitigation is that enforcement **moves** rather than vanishing: `#CatalogMemberFQNGate` states what 0011's publish gate re-derives and refuses, which is the same gate D17 puts the primitive-path rule in. What the design buys for it is that `modulePath`, `version` and `fqn` all read from one source — `identity/identity.cue` — so a release moves every key by one edit, and the key becomes visible at the site that defines it. The residual exposure is the window between authoring and publish, which is exactly where a gate can sit.

- ~~**Two hyphenated module names change, and the change is user-visible.**~~ **RETIRED 2026-08-05 — already done, and the risk never applied to this entry.** `web-app` → `web_app` and `zot-registry-ttl` → `zot_registry_ttl` were both completed before this entry was sliced. Re-measured 2026-08-05 across the whole fleet: **zero** hyphenated directory names or declared module paths, on either branch of `modules/` — 13 directories on `main`, 25 module paths on `v0_legacy`. The reasoning stands for anything that hyphenates in future (underscores are legal in Kubernetes label values, and the alternative keeps two spellings of one identity alive), but there is no rename left to perform and the `modules-fleet-republish` slice no longer claims one. What remains hyphenated is a different class the D8 rule does not reach: primitive `metadata.name` values inside `catalog_opm` (`stateless-workload`, `config-maps`), which are `#NameType` and stay kebab-case by design (D33).

- **The version label is only as honest as the read-side check.** D9 as revised keeps the label schema-declared, sourced from the module's own `metadata.version`, and makes the kernel its *verifier* rather than its source — so an artifact published outside `opm publish` can carry a label that lies right up until a consumer acquires it and the comparison against the fetched tag fires. The check is the guarantee; the declaration is not. What this buys is the property a kernel stamp could not deliver: the label is identical on both render paths, including `cli`'s local-directory render, which has no resolved coordinate to stamp from.

- **D36's label removal cannot be absorbed in place by an already-deployed workload, because the key it removes sits in an immutable field.** D36 records the consequence as "a label removal on every live workload" and [`06-operational.md`](06-operational.md) names dashboards, `kubectl` selectors and network policies as what must be re-pointed. Measured 2026-08-05, that understates it by one level: the key does not merely appear *on* rendered objects, it appears *in their selectors*. `core/src/transformer.cue:147-157` folds every `metadata.labels` key into `componentLabels`, and `catalog_opm` consumes that value as a selector directly — `deployment_transformer.cue:134` and `statefulset_transformer.cue:146` set `selector: matchLabels: #context.componentLabels`, and `service_transformer.cue:115` sets `selector: #context.componentLabels`. `apps/v1` makes `.spec.selector` **immutable**, so a `Deployment`, `StatefulSet` or `DaemonSet` that already carries the key cannot accept the render that omits it — the apply is rejected rather than being a no-op diff. A `Service` selector *is* mutable, but changing it out of step with the pod labels drops every endpoint. Blast radius: any workload deployed before the cutover, which is a function of fleet size rather than of anything in this entry. **Mitigation:** this entry ships D36 as decided and does **not** run the cutover — moving a running deployment onto the new shape is separate work outside these entries. What the cutover needs is recorded here so it is not rediscovered at apply time: either an ordered delete-and-recreate with the `Service` selector changed in the same step, or D36's own rejected-for-now alternative, the `v_render` fold measured in [`experiments/04`](experiments/04-component-label-union/) and described there as "a four-line guard at struct level" that "can be added later without disturbing anything this decision fixes" — which keeps the key in the selector and makes the cutover a no-op. The fold is the cheaper of the two and remains available; this is the note that tells whoever schedules it that the choice exists.

- ~~**`#Catalog` and `#Module` stop being symmetric.**~~ **RETIRED BY D38.** Both artifact types now carry a version in an importable `identity/` subpackage, and both get a `version set` command. The asymmetry that remains is one of *meaning* rather than of shape, and it is worth stating because it is invisible: a catalog's version keys its transformers and stamps every primitive's provenance (D3 + D4), so changing it moves keys; a module's version keys nothing at all and is read only by the instance that derives from it. Two identical-looking fields, one load-bearing and one not.

- **There are now three version-shaped values in play, and they mean different things.** A catalog's module major (`@v1`, an address), its release SemVer (`1.2.0`, a build), and each primitive's `apiVersion` (`v1`, a contract). They move independently by design — a catalog on `1.x` may ship `backup@v2` — which is the capability D4 exists to provide and also the thing a newcomer will most reliably misread, since two of the three are spelled `v1`. Accepted: the alternative is tying the contract to one of the other two, which means tying it either to the catalog's module major or to its build, and D4 rejected both on their own evidence. **Mitigation is documentation rather than design** — `core/SPEC.md` must state the three explicitly, and the naming carries some of the load (`apiVersion` versus `catalogVersion`, D25).

- **The additive-only promise is a promise.** D27 is enforceable at publish and partially at match, but neither end can make a catalog author's judgement for them — whether a change is additive is decided by whoever writes it, and the subsumption gate can only check the shape they produced. A publisher who breaks compatibility inside an `apiVersion` poisons every module that then matches it. Accepted as the same class of exposure every ecosystem with SemVer has, and narrower than the catalog-major version of it: under D4 the damage is bounded to one contract rather than to a whole catalog major, and `experiments/02` measures that the match rung catches the common shapes (removed field, narrowed type) even when the gate is bypassed.

- ~~**Landing separately from enhancement 0011 relabels the fleet twice.**~~ **RETIRED 2026-08-04 by enhancement 0011 D13 and D17.** This drawback rested on 0011 D5 moving every module into an owner-scoped namespace, which would have changed `modulePath` — and since `modulePath` *is* `fqn` under D1, every UUID with it. D13 keeps first-party modules at `opmodel.dev/modules/<name>` on the ground that OPM registers names only under the domain it owns, so **no coordinate is rewritten and no owner label moves twice**. There is no second relabelling and no window to schedule: 0010's `modules-fleet-republish` is the only fleet republish in the pair, and 0011 contributes the command it runs through (D15, D17). The reasoning is kept rather than deleted because it is the argument to re-run if a future entry ever reopens a path move — and 0011 D17 records its price, two published artifacts claiming one identity with D10 making both permanent.

## Alternatives

- **Keep `metadata.version` on `#Module` and enforce that it equals the release tag.** The design this entry replaces. **Why not:** it requires a publish-side derivation, a read-side check, a version-authoring command, a migration of every already-published artifact, and a permanent invariant every future tool must respect — all to keep two values equal that need not both exist. It would also have activated the pruning failure described above, which the existing drift has been masking.

- **Remove the version from `#Catalog` too, for symmetry.** **Why not:** under D4 the catalog's version is the component every primitive FQN interpolates, so removing it removes the key space rather than a signal beside it. The symmetry argument dies here for good.

- **Catalog-major FQNs plus a compatibility floor** (an early form of D3 plus catalog-major keys, reversed within D4). **Why not:** it makes a catalog release change what every already-installed module renders, since they all key to `@vN` and pick up whichever build the platform resolved; it needs a floor, a catalog lookup, a required per-primitive version and a definition-comparison check to recover safety SemVer keys have for free; and it breaks the multi-build subscription `library` already implements, turning every survivor of a range into an FQN collision. Full reasoning in D4.

- **Teach the matcher SemVer ranges over SemVer keys** — exact match first, then highest compatible. **Why not:** it turns an O(1) keyed lookup into constraint solving and re-implements resolution CUE already performs for dependencies. It is also redundant: range-aware matching and multi-build subscription are two routes to one capability, and the latter is already built.

- **Generate identity into the artifact at publish, leaving source without it.** **Why not:** the published bytes stop equalling the source bytes, so a local render and a published render compute different values from the same tree — which is the divergence measured in the current catalog flow, transposed onto modules. It also hides the value in a file the developer never wrote.
