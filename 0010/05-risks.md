# Risks, Drawbacks, Alternatives — Module and Catalog Identity

This document records the honest costs of the proposed design. Risks describe what could go wrong; Drawbacks describe what definitely costs something; Alternatives describe the high-level paths not taken (per-decision detail lives in `03-decisions.md`).

## Risks and Mitigations

- **Every module identity changes once, and an un-migrated live instance silently stops pruning.** `fqn` changes shape, so `module.uuid` changes, so `instance.uuid` changes, so the `module-instance.opmodel.dev/uuid` label on every deployed resource changes. `opm-operator/internal/apply/prune.go:107` tolerates an *empty* live label but skips a delete when the live label disagrees with `Status.InstanceUUID` — and it **skips without erroring**, so reconcile reports success while garbage collection has quietly stopped.

  **Blast radius is bounded, and deliberately so.** OPM has one operator today and the deployed fleet is enumerable — the `ModuleRelease` configs in `releases/` plus the CLI's CR inventory name every live instance. So this is a one-time, single-operator migration rather than an ecosystem event, and it does not need a compatibility path: no operator tolerance for a recorded prior UUID, no transition window, no dual-identity support. Recorded as a decision about *this* migration's circumstances rather than a general property — the same change made after OPM has external consumers would need all three.

  **What does not shrink is the silence.** A skipped prune produces no error, no event, and no status change, so nothing tells the operator that an instance was missed. Being the only user makes the fleet fixable; it does not make the problem visible. **Mitigation:** the migration is manual and enumerated (walk `releases/`, relabel or recreate each instance), and it is followed by a **positive check** rather than an absence of complaints — for at least one migrated instance, remove a resource from the module, re-render, and assert the resource is actually deleted from the cluster. That check is what distinguishes "migrated correctly" from "migrated and silently broken", and it is cheap exactly once.

- **RETIRED BY D24 — a subscription that does not cover the fleet's authorship history.** Under D13 a module matched only the exact build it was authored against, so a materialized set omitting that build failed the demand. Contract keys remove the condition: a subscription covering any build in the major supplies the contract. What replaces it is the risk below, which is smaller in blast radius and larger in subtlety.

- **A catalog release can move every render on the platform, with nothing in git changing.** Under D13 the key pinned the transformer build, so a catalog release was inert until a module was rebuilt. Under D24 the key pins nothing and the platform's subscription resolves at materialize time — `filter.go:43-47` selects the highest published stable, and `MaterializedPlatform.Resolved` (`materialize.go:109`) is in-memory only. So publishing a catalog build can change what every installed module renders, and the operator reconciling continuously is who finds out. Blast radius: every module on the platform, simultaneously, from an action taken in another repository. **Mitigation:** OQ11 — an exact subscription pin or a recorded resolution. This is the half of D13's guarantee that D24 relocated rather than removed, and it is the one place where the new model is *worse* until OQ11 is answered. Correctness is unaffected (D27 makes any build in the major a legal supplier); reproducibility is not.

- **The materialized set grows monotonically and nothing prunes it — now contingent on OQ15.** Under D14 every published build in a subscribed major is pulled and indexed, so cost scales with the catalog's release history rather than with what the fleet uses. D24 removes breadth's *reason*, so the answer to OQ15 plausibly deletes this risk outright by materializing one build per subscription. If breadth survives it acquires a second, sharper failure that D14 never had: a contract bucket holding several builds of one catalog's transformer, every one of which satisfies the predicate, so every one pairs and every one renders — duplicate output rather than a missed key. **Mitigation:** OQ15 decides between one-build selection, a highest-build tie-break, and erroring on the condition. Until it is answered, do not assume the current default is safe under contract keys.

- **Prereleases are the live regime, and today's selection excludes them.** `catalogs/opm` has published only `v1.0.0-alpha*` and `catalogs/kubernetes` carries `v1.1.0-alpha` (registry read 2026-07-27). Under today's `filterVersions`, a bare subscription resolves one build and the obvious range (`>=1.0.0 <2.0.0`) selects **zero**, because Masterminds constraints exclude prereleases unless the constraint itself carries one. Blast radius: the entire current fleet, on the first platform authored against the new schema. **Mitigation:** D15's explicit opt-in, which must land in the same `core` release as D13 rather than after it — the design is unusable against the real catalogs without it.

- **A shared-resolution render would disable the only compatibility check there is.** A module's primitive definitions must resolve through the *module's own* dependency graph. That holds today — `library/opm/compile/module.go:137` consumes `mp.Transformers` from `materialize` as read-only input built by a separate resolver. If a single-build render put the module and the platform in one CUE build, minimal version selection would pick the maximum and the module's copy of every contract definition would silently become the platform's. Under D13 the symptom was a demand for the platform's build that matched anyway. Under D24 it is worse in kind: the always-unify rung (D26, D27) is now the *only* thing verifying that the module's contract body and the provider's agree, and with one resolution it would be comparing a value against itself — it can never fail, and the additive-only promise stops being checked at render at all. **Mitigation:** state it as an invariant of the render path rather than an incidental property, and cover it with a test that fails if the two resolutions are ever merged. The in-flight render rewrite in `library` must be checked against this before it lands.

- **Removing a required field from a published schema breaks every consumer at once.** `opmodel.dev/core` is consumed as a published dependency by every module and every catalog. Blast radius: nothing that depends on the current major keeps working. **Mitigation:** this is a `core` major-version event, published as such, with the catalogs and the module fleet migrated in a coordinated window rather than opportunistically.

- **An unfilled identity field can be published.** Measured 2026-07-26: `cue mod publish v1.2.0 --dry-run` succeeded on a tree whose identity fields were open, and `cue vet` *without* `-c` reports `some instances are incomplete` and exits 0. So neither CUE's publish nor a default vet gate blocks an artifact with no identity in it. Blast radius: a consumer of that artifact, which fails at evaluation with `incomplete value string`. **Mitigation:** D11's read-side checks are the guarantee, and every OPM vet path passes `-c`. The degradation is safe — absence fails loudly and names the field — but it fails at the consumer, which is why the check belongs there rather than only in a publish task.

- **The address check makes the registry a harder dependency.** Verification adds a way for a fetch to fail that authors did not previously have to reason about, and the error surfaces inside the operator's reconcile loop as well as at the CLI. Blast radius: any environment where a conforming artifact is misread. **Mitigation:** the error names both the expected and the actual coordinate, so diagnosis is immediate, and the check compares only what `#FetchedArtifact` unifies — not a broader notion of well-formedness.

## Drawbacks

- **The module path is stated twice.** `cue.mod/module.cue`'s `module:` line and `identity.cue`'s `modulePath` carry the same string. D1 does not remove that duplication, it makes it *comparable* — one complete string against another, rather than a fragment reassembled from parts. Keeping the two in step is a job for tooling and for the D11 read-side check. Accepted: the alternative that removes the duplication (deriving inside CUE) forces every artifact to carry attribute-and-regex boilerplate and cannot be done on a consumer's behalf.

- **A fresh clone of a catalog does not vet until a version is supplied**, if its author chose the open form (D6). `cue vet -c` reports one named incomplete field. **D24 narrows this back**, undoing the widening D13 caused: contract keys interpolate `apiVersion`, which is authored per primitive and always concrete, so an unfilled `Version` leaves only the transformer keys and the provenance stamps non-concrete. D6's original split — identity concrete ⇒ the contract key space evaluates — holds again for three of the four primitive kinds.

- **A primitive's `fqn` becomes author-writable, and `core` can no longer refuse a wrong one.** D21 moves the FQN from a `core` derivation to a value each catalog authors from its identity package. Measured 2026-07-27, that is a real loss of enforcement in both directions: under the derivation, a disagreeing author fails at the catalog's own `cue vet` with `conflicting values "1.2.0" and "1.1.0"` naming both sites; under an authored FQN, a catalog on `1.2.0` shipping `fqn: "…/secrets@1.1.0"` passes `cue vet -c` with **exit 0**. Because D13 makes a key name its own bytes permanently, a wrong key that ships is a key modules match against forever. Accepted deliberately, and the mitigation is that enforcement **moves** rather than vanishing: `#PrimitiveFQNGate` states what 0011's publish gate re-derives and refuses, which is the same gate D17 puts the primitive-path rule in. What the design buys for it is that `modulePath`, `version` and `fqn` all read from one source — `identity/identity.cue` — so a release moves every key by one edit, and the key becomes visible at the site that defines it. The residual exposure is the window between authoring and publish, which is exactly where a gate can sit.

- **Two hyphenated module names change, and the change is user-visible.** `web-app` → `web_app`, `zot-registry-ttl` → `zot_registry_ttl`. `name` feeds the `module.opmodel.dev/name` label, so anything selecting on it must be updated. Accepted: underscores are legal in Kubernetes label values, and the alternative keeps two spellings of one identity alive.

- **The `module.opmodel.dev/version` label changes hands.** It stops being declared by the schema and starts being stamped by the kernel. Anyone reading it gets a *more* truthful value — the artifact actually fetched, rather than a field that had drifted — but the field is no longer visible in module source, so "where does this label come from" has a less obvious answer.

- **`#Catalog` and `#Module` stop being symmetric.** One carries a version, the other does not. That is a real cost in explicability, paid for a real reason: a catalog's version keys its transformers and stamps every primitive's provenance (D3 + D24), and a module has no primitives and therefore nothing to key.

- **There are now three version-shaped values in play, and they mean different things.** A catalog's module major (`@v1`, an address), its release SemVer (`1.2.0`, a build), and each primitive's `apiVersion` (`v1`, a contract). They move independently by design — a catalog on `1.x` may ship `backup@v2` — which is the capability D24 exists to provide and also the thing a newcomer will most reliably misread, since two of the three are spelled `v1`. Accepted: the alternative is tying the contract to one of the other two, which is D4 (tie it to the module major) or D13 (tie it to the build), and both were rejected on their own evidence. **Mitigation is documentation rather than design** — `core/SPEC.md` must state the three explicitly, and the naming carries some of the load (`apiVersion` versus `catalogVersion`, D25).

- **The additive-only promise is a promise.** D27 is enforceable at publish and partially at match, but neither end can make a catalog author's judgement for them — whether a change is additive is decided by whoever writes it, and the subsumption gate can only check the shape they produced. A publisher who breaks compatibility inside an `apiVersion` poisons every module that then matches it. Accepted as the same class of exposure every ecosystem with SemVer has, and narrower than D4's version of it: under D24 the damage is bounded to one contract rather than to a whole catalog major, and `experiments/02` measures that the match rung catches the common shapes (removed field, narrowed type) even when the gate is bypassed.

- **Landing separately from enhancement 0011 relabels the fleet twice.** 0011 moves module paths into an owner-scoped namespace, which changes `modulePath` — and since `modulePath` *is* `fqn` under D1, every UUID moves again, so every live instance is relabelled a second time. This was previously recorded as a risk and is demoted to a cost, because there is no correctness constraint underneath it: the intermediate state is valid in both orders. 0010 alone leaves modules at `opmodel.dev/modules/jellyfin@v2` — old namespace, new shape — which resolves and renders normally; 0011 landing first would rewrite a path prefix rather than a full path, which also works. Only the migration effort doubles. Accepted: with one operator and an enumerable fleet the doubled effort is bounded and known, so landing the two in one window is a preference rather than a gate. It stays worth doing — the effort is proportional to how much is published when it lands, so the combined window is strictly cheaper — but nothing breaks if they separate.

## Alternatives

- **Keep `metadata.version` on `#Module` and enforce that it equals the release tag.** The design this entry replaces. **Why not:** it requires a publish-side derivation, a read-side check, a version-authoring command, a migration of every already-published artifact, and a permanent invariant every future tool must respect — all to keep two values equal that need not both exist. It would also have activated the pruning failure described above, which the existing drift has been masking.

- **Remove the version from `#Catalog` too, for symmetry.** **Why not:** under D13 the catalog's version is the component every primitive FQN interpolates, so removing it removes the key space rather than a signal beside it. The symmetry argument dies here for good.

- **Major-keyed FQNs plus a compatibility floor** (D3 + D4, reversed by D13). **Why not:** it makes a catalog release change what every already-installed module renders, since they all key to `@vN` and pick up whichever build the platform resolved; it needs a floor, a catalog lookup, a required per-primitive version and a definition-comparison check to recover safety SemVer keys have for free; and it breaks the multi-build subscription `library` already implements, turning every survivor of a range into an FQN collision. Full reasoning in D13.

- **Teach the matcher SemVer ranges over SemVer keys** — exact match first, then highest compatible. **Why not:** it turns an O(1) keyed lookup into constraint solving and re-implements resolution CUE already performs for dependencies. It is also redundant: range-aware matching and multi-build subscription are two routes to one capability, and the latter is already built.

- **Generate identity into the artifact at publish, leaving source without it.** **Why not:** the published bytes stop equalling the source bytes, so a local render and a published render compute different values from the same tree — which is the divergence measured in the current catalog flow, transposed onto modules. It also hides the value in a file the developer never wrote.
