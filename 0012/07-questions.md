# Open Questions: Kubernetes as a First-Class Kernel Platform

## Open Questions

Each carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, or `answered`. Several carry a recommendation. A recommendation is not a decision and does not close the question.

### Kernel boundary

- **OQ1: How far past the render line does the kernel go: Rung 2 (decides), Rung 3 (acts), or a split?** Status: open. Blocking: acceptance (every slice's shape depends on it). [`02-design.md`](02-design.md) argues Rung 2 alone reproduces D31's failure mode, because a plan a frontend can decline to follow is how the CLI came to lack a CRD exclusion the operator has. It also argues that Rung 3 cannot apply uniformly, because the operator's apply is `fluxcd/pkg/ssa` and the CLI must not inherit it. The recommendation is asymmetric: the kernel owns execution for delete (no framework opinion) and verdicts only for apply. Resolving this fixes the shape of every slice below it. What would resolve it: agreement on whether "behaves the same" must be structurally enforced or may rest on each frontend choosing to call the planner.

- **OQ2: Does the kernel take a cluster client, and what is the minimal interface?** Status: open. Blocking: acceptance (every slice's shape depends on it). Rung 3 requires the kernel to GET and DELETE. The proposal is a two-method interface over `*unstructured.Unstructured` supplied by the caller, keeping the library on `apimachinery` with no `client-go` edge; the operator adapts its controller-runtime client and the CLI its dynamic client in roughly fifteen lines each. Precedent exists (`opm/helper/loader/registry` already performs OCI network I/O under caller-supplied configuration), but this would be the first time the kernel touches a cluster. What would resolve it: deciding whether cluster I/O belongs in `opm/helper/` (opt-in tier, consistent with the registry loader) or is refused outright, which forces OQ1 to Rung 2.

- **OQ3: Is the neutral `core.Resource` / `Identity` contract deleted, or retained and implemented?** Status: open. Blocking: acceptance (determines config.yaml.semver). D2 settles that no portability work is undertaken for it; it does not settle its fate. Deletion is a library-major break requiring a `MIGRATIONS.md` entry and coordinated frontend updates; retention leaves an unused abstraction that the next contributor must be told to ignore. This question sets `config.yaml.semver`, so it blocks promotion to `accepted`.

### Deletion and ownership

- **OQ4: `ownerReferences`: candidate (a), (b), or (c) from 0010's OQ10?** Status: open. Blocking: acceptance (half the entry's stated scope; deferring it means the entry did not answer what it was opened for). With a recommendation. [`01-problem.md`](01-problem.md) §6 establishes two things. Kubernetes garbage-collects a dependent when all its owners are gone regardless of `controller` or `blockOwnerDeletion`, so there is no read-only ownerReference. And `spec.prune` defaults to false, whose contract is that workloads survive. An ownerReference therefore contradicts the default policy for exactly the namespaced subset. Conditioning it on `prune: true` removes the contradiction and also the benefit, since the hold already prunes in that case. The recommendation is (a): inventory, labels, and a kernel-owned hold, with no ownerReferences at all, for a stronger reason than the cluster-scope limitation OQ10 leads with. What would resolve it: confirming the residual value of ownerReferences as a backstop when a hold is force-removed, and whether that outweighs a policy contradiction.

- **OQ5: Does `spec.prune` keep defaulting to false?** Status: open. Blocking: deferrable. It is the difference between "the hold exists" and "the hold does anything", and no amount of kernel work substitutes for it. Flipping it is a one-line CRD default that silently begins deleting workloads on delete for every existing instance, so it needs an explicit decision and a migration note. Leaving it means orphan-by-default remains the shipped behaviour and the tooling's job is to say so loudly. Owned by `opm-operator` but decided here because the deletion protocol's meaning depends on it.

- **OQ6: Do CLI-owned instances carry a deletion hold?** Status: open. Blocking: deferrable. Today `handleCLIOwned` deliberately adds no finalizer so the operator never prunes CLI-owned resources, which means `kubectl delete moduleinstance` removes the CR (the only inventory record) and orphans every workload with nothing left to find them by. The options are a hold the CLI itself releases, a hold the operator honours on behalf of a CLI-owned instance (which reintroduces the ownership confusion the owner-skip gate exists to prevent), or an explicit accepted leak with a warning surface. This is the one gap in the area that code-sharing alone does not close.

- **OQ7: Which stale-set base relation wins: component-aware or component-blind?** Status: open. Blocking: deferrable. Absorbed from 0006 OQ15, which classified it "product-consistency, not safety" and deferred it. Standardising on the operator's component-blind `K8sIdentityEqual` makes the CLI's separate `ApplyComponentRenameSafetyCheck` post-filter unnecessary by construction rather than merely redundant, which is an argument for that direction. What would resolve it: confirming no CLI behaviour depends on the post-filter's distinct reporting.

- **OQ8: Does the apply-time collision guard land in this entry?** Status: open. Blocking: deferrable. Absorbed from 0006 OQ16, which called it "a real, presently-shipping exposure" and deferred it. Both apply paths force SSA field ownership unconditionally, and the operator's delete-time guard cannot backstop an apply-time mislabel: a successful colliding apply relabels the foreign object as `opm-controller`-managed, so it looks legitimately owned from then on. Open sub-questions inherited from OQ16: whether the guard runs on every reconcile that grows the entry set or only on an instance's first, and whether refusal has an override.

### Relationships to other entries

- **OQ9: Does the library own the CRD Go types, and how does that interact with 0008?** Status: open. Blocking: acceptance (needs an agreed position recorded in 0008 too; a unilateral answer is not a resolution). 0008 makes `core/` CUE the source of truth for `ModuleInstance` / `ModulePackage` / `Platform` and generates the Go types into `opm-operator/api/v1alpha1`. If the shared Kubernetes vocabulary homes in `library` under D1, the generation target is arguably `library` with the operator re-exporting, which would also dissolve 0006 D13's constraint that the CLI cannot import the operator's types.

  Note that 0008's README currently states the CLI "consumes those same Go types", which is not the case: `cli/go.mod` has no `opm-operator` dependency and `cli/internal/inventory/cr.go` hardcodes the CRD coordinates precisely to avoid one. Resolving this needs a joint decision with 0008 rather than a unilateral one here.

- **OQ10: How does this entry's kernel surface relate to 0009's execution half?** Status: open. Blocking: acceptance (needs an agreed position recorded in 0009 too; a unilateral answer is not a resolution). 0009 adds `opm/flow/` (a planner plus orchestrator for `#Op` / `#Action` / `#Lifecycle` / `#Workflow`) with an opt-in executor backend layer and a caller-composed backend set. That is structurally the same move this entry makes for deletion: a pure planner in the kernel, execution behind a caller-supplied seam. If both land independently they will invent two different executor conventions. The two should share one, and deciding which entry owns it is cheaper before either ships. 0009's initial Op vocabulary already includes `k8s get/apply`, which is the overlap made concrete.

- **OQ11: Where does label stamping live?** Status: open. Blocking: deferrable. Today `core/src/transformer.cue` composes the label set and the runtime fills `#runtimeName`, so labels are stamped in CUE and only read in Go, while `opm-operator/pkg/core/labels.go` and its CLI twin hold the Go-side vocabulary that reads them. Enhancement 0010 separately moves the `module.opmodel.dev/version` label "from the schema to the kernel". If the kernel is to own ownership decisions, the question of whether it also owns stamping (and how that splits against `core/`'s CUE) needs an answer that 0010 and this entry agree on.
