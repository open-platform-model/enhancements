# Open Questions: Kubernetes as a First-Class Library Tier

## Open Questions

Each carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, or `answered`. Several carry a recommendation. A recommendation is not a decision and does not close the question.

### Kernel boundary

- **OQ1: How far past the render line does the kernel go: Rung 2 (decides), Rung 3 (steps), or a split?** Status: resolved-by-D4 (2026-10-02). Answered in two steps. Library ADR-008 settled the shape half on 2026-09-14: the library ships no loop that drives a plan to completion (rule 1) and the kernel names an action and never performs one (rule 3), so Rung 3 is a transition the caller drives. Rung 2 alone reproduced 0006:D31's failure mode, because a plan a frontend can decline to follow is how the CLI came to lack a CRD exclusion the operator has; under ADR-008 a frontend cannot decline, because asking for the next action is the only way to make progress. 0012:D4 settles the asymmetry that remained: the library owns the whole deletion sequence (plan, transition, hold verdict), and for apply it owns the per-object verdict and the order but not the engine, so the operator keeps `fluxcd/pkg/ssa` and the CLI keeps its own server-side apply. Where that code lives is 0012:D3: the `opm/k8s` tier beside the kernel, so "the kernel" in this question's wording now means that tier.

- **OQ2: Does the kernel take a cluster client, and what is the minimal interface?** Status: answered (2026-09-14), amended 2026-10-02. No. Library ADR-008 rule 1 says the kernel plans and the caller runs. Rule 3 says the kernel names an action and never performs one. Rule 1 also says the library ships no loop that drives a plan to completion. Rule 3 also allowed opt-in executor backends under `opm/helper/`; on 2026-10-02 the owner limited that allowance, by an in-place amendment to ADR-008 citing library ADR-011, to executor backends that perform no planned action against a cluster, so no code in the library performs a planned action against a cluster (0012:D3). 0012:OQ10 records what that means for 0009's hosts. So there is no `ObjectClient` interface and no cluster I/O in `library`: the caller performs every GET and DELETE with the client it already holds and feeds the outcome back through the transition's state. Live object state stays an input to the plan rather than something the kernel fetches. This also removes the question's own fallback, since refusing cluster I/O no longer forces Rung 2.

- **OQ3: Is the neutral `core.Resource` / `Identity` contract deleted, or retained and implemented?** Status: answered (2026-09-01). Deleted. The library OpenSpec change `library-plan-diagnostics-prune` removed `core.Resource` and `core.Identity` on measured evidence: zero implementations anywhere, both frontends defining their own resource types and importing `opm/core` only for `Compiled`. `Compiled` stays the kernel's terminal output and platform identity is stated as the frontend's concern, consistent with D2 (no portability abstraction maintained on the kernel's behalf). Delete-vs-retain no longer blocks promotion. The removal is a library-major event recorded pre-GA as changelog plus archive per the library's migrations policy, so no migration fragment was written.

### Deletion and ownership

- **OQ4: `ownerReferences`: candidate (a), (b), or (c) from 0010's OQ10?** Status: open. Blocking: acceptance (half the entry's stated scope; deferring it means the entry did not answer what it was opened for). With a recommendation. [`01-problem.md`](01-problem.md) §6 establishes two things. Kubernetes garbage-collects a dependent when all its owners are gone regardless of `controller` or `blockOwnerDeletion`, so there is no read-only ownerReference. And `spec.prune` defaults to false, whose contract is that workloads survive. An ownerReference therefore contradicts the default policy for exactly the namespaced subset. Conditioning it on `prune: true` removes the contradiction and also the benefit, since the hold already prunes in that case. The recommendation is (a): inventory, labels, and a kernel-owned hold, with no ownerReferences at all, for a stronger reason than the cluster-scope limitation OQ10 leads with. What would resolve it: confirming the residual value of ownerReferences as a backstop when a hold is force-removed, and whether that outweighs a policy contradiction.

- **OQ5: Does `spec.prune` keep defaulting to false?** Status: open. Blocking: deferrable. It is the difference between "the hold exists" and "the hold does anything", and no amount of kernel work substitutes for it. Flipping it is a one-line CRD default that silently begins deleting workloads on delete for every existing instance, so it needs an explicit decision and a migration note. Leaving it means orphan-by-default remains the shipped behaviour and the tooling's job is to say so loudly. Owned by `opm-operator` but decided here because the deletion protocol's meaning depends on it.

- **OQ6: Do CLI-owned instances carry a deletion hold?** Status: open. Blocking: deferrable. Today `handleCLIOwned` deliberately adds no finalizer so the operator never prunes CLI-owned resources, which means `kubectl delete moduleinstance` removes the CR (the only inventory record) and orphans every workload with nothing left to find them by. The options are a hold the CLI itself releases, a hold the operator honours on behalf of a CLI-owned instance (which reintroduces the ownership confusion the owner-skip gate exists to prevent), or an explicit accepted leak with a warning surface. This is the one gap in the area that code-sharing alone does not close.

- **OQ7: Which stale-set base relation wins: component-aware or component-blind?** Status: resolved-by-D7 (2026-10-03). Component-blind: an entry is the same object as a rendered one when group, kind, namespace and name agree, so the CLI's separate rename filter goes and no behaviour changes. Absorbed from 0006 OQ15, which classified it "product-consistency, not safety" and deferred it.

- **OQ8: Does the apply-time collision guard land in this entry?** Status: resolved-by-D8 (2026-10-03). Yes: the guard lands here as the library's per-object apply verdict (0012:D4). 0012:D8 settles the two sub-questions inherited from 0006:OQ16. The guard runs on every apply for each object not already in the instance's inventory, not only on an instance's first (since 2026-10-05 it also refuses an object in the inventory whose adopt annotation names another instance, 0012:D8:R8), and its one override is a per-object adopt annotation on the existing live object naming the adopting instance. A ModulePackage gains a persisted instance identity in an additive status field so the comparison covers it. Absorbed from 0006:OQ16, which called it "a real, presently-shipping exposure" and deferred it. Both apply paths force SSA field ownership unconditionally, and the operator's delete-time guard cannot backstop an apply-time mislabel: a successful colliding apply relabels the foreign object as `opm-controller`-managed, so it looks legitimately owned from then on.

### Relationships to other entries

- **OQ9: Does the library own the CRD Go types, and how does that interact with 0008?** Status: open. Blocking: acceptance (needs an agreed position recorded in 0008 too; a unilateral answer is not a resolution). 0008 makes `core/` CUE the source of truth for `ModuleInstance` / `ModulePackage` / `Platform` and generates the Go types into `opm-operator/api/v1alpha1`. If the shared Kubernetes vocabulary homes in `library` under D1, the generation target is arguably `library` with the operator re-exporting, which would also dissolve 0006 D13's constraint that the CLI cannot import the operator's types.

  Note that 0008's README currently states the CLI "consumes those same Go types", which is not the case: `cli/go.mod` has no `opm-operator` dependency and `cli/internal/inventory/cr.go` hardcodes the CRD coordinates precisely to avoid one. Resolving this needs a joint decision with 0008 rather than a unilateral one here.

- **OQ10: How does this entry's kernel surface relate to 0009's execution half?** Status: deferred-to-0009 (2026-10-03). Partially resolved 2026-09-14, amended 2026-10-02, ownership half answered by 0012:D4 on 2026-10-03, and the remaining half deferred to 0009 by owner decision on 2026-10-03. The risk this question named, that both entries invent two different executor conventions, is closed: library ADR-008 binds both to one contract, a plan the kernel emits and a transition the caller drives, and 0009 records it on its own D3. On 2026-10-02 the owner recorded that 0012:D3 amends 0009:D4. 0009's wasm, HTTP, `cue.eval` and local container hosts perform no planned action against a cluster and may stay opt-in under `opm/helper/`. 0009's k8s get/apply Ops and the container host's Job-rendering variant perform a planned action against a cluster, so the frontend must perform them and no library backend may. This entry does not edit 0009; `task show ID=0009` lists the amendment. On 2026-10-03 the owner answered the ownership half (0012:D4): the deletion plan and its serialisable, caller-held state are this entry's, used by both frontends' delete paths, and carry no hook semantics. 0009 records that position in its own register. What remained is whether 0009's `#Op` vocabulary for k8s get/apply is expressed as this entry's action set or beside it. The owner deferred that half to 0009 on 2026-10-03, and 0009:OQ7 carries it, so the position is recorded in both entries. It waits until hooks are wanted. Since 0012:D3 already puts those Ops in the frontend, no answer changes what this entry delivers.

- **OQ11: Where does label stamping live?** Status: resolved-by-D6 (2026-10-02). In CUE, at render, where it lives today: core's transformer contract composes the label set and the frontend fills `#runtimeName`, while Go only reads labels (0012:D6). The shared render digest in the `opm/k8s` tier excludes the runtime-name (managed-by) label value, so the CLI and the operator digest the same render to the same bytes. The conflict this question anticipated with 0010 does not exist. Moving the `module.opmodel.dev/version` label "from the schema to the kernel" was 0010's original design. 0010:D9 as revised on 2026-08-04 keeps that label declared by the schema, and the kernel verifies it. 0010 is delivered and archived, so the agreement is recorded here as 0012:D6's dependency on 0010:D9.
