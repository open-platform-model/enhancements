# Open Questions: Self-Service Kinds from Published Modules

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design.

`OQ` numbers are permanent, never reused, never renumbered, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves. Each **unresolved** entry also carries a `Blocking:` field: `acceptance` (with the reason inline; `task promote` refuses while open), `deferrable` (may stay open at `accepted`), or `implementation` (handed to delivery; the change that settles it claims it via `resolves` in `delivery.yaml`). Contract-level questions cannot be deferred to implementation.

While a question is open, its bullet is a working surface: edit the wording, sharpen the framing, add or drop alternatives freely. Once resolved, the bullet collapses to its question and its status at the `draft → accepted` compaction pass.

## Open Questions

- **OQ1: What is the kind name of the platform-owned definition object?** Status: open. Blocking: acceptance: the kind is the CRD's API surface and every consumer types it. Five candidates, none with a `Module` prefix, since the object is platform-owned like `Platform` and `TransformerRegistration` rather than module-family like `ModuleInstance`. `Offering` (Cloud Foundry and Open Service Broker lineage, safest, least distinctive). `Capability` (the CNCF platforms white paper's vocabulary; mild collision with the capability-based routing 0015 names as successor material). `Facade` (most precise about the mechanism: `#config` is the interface, `#components` is hidden; unusual as a kind). `Promise` (best semantic fit; Kratix's core CR, so it reads as derivative). `Form` (the consumer's mental model; too generic in code). Rejected on collision: anything with Catalog, Blueprint, Template, Release, Claim, Service, Package or Class in it, each colliding with an OPM word, a retired OPM word, a Kubernetes kind, or a rejected 0015 vocabulary. Until resolved the draft uses "offering" in lower case as a placeholder noun, never as a kind; the CUE identifiers in `schemas/` carry the placeholder and rename with the decision.

- **OQ2: Does the binding layer ship as a product on its own, or only as an implementation slice of the kind layer?** Status: open. Blocking: acceptance: it decides scope, `semver`, and whether the `ModuleInstance` definition reference is a documented consumer surface or an internal one. Shipping it alone delivers platform-owned versioning and the tenant guardrail with no dynamic CRDs; the cost is a documented second way to write a `ModuleInstance` that the kind layer later makes rarely used. Shipping it only as a slice keeps the consumer surface to served kinds and leaves platforms that do not want dynamic CRDs with nothing. The answer also bears on OQ1: `Offering` and `Capability` cover both layers, `Facade` and a kind-only name fit the second alone.

- **OQ3: What is the update-policy vocabulary on a definition, what is its default, and what does each value do to live instances?** Status: open. Blocking: acceptance: the policy is contract on the definition and the rebinding blast radius depends on it. Candidates: `automatic` (a rebind re-renders every instance under the instance's own rollout controls) and `manual` (a rebind takes effect per instance when the instance is next changed, or on an explicit per-instance action). A channel model (the definition tracks the newest release inside its major) is a third value or a successor. StorageClass's silent re-route is the failure mode to avoid, which argues for `manual` as the default; the fleet-upgrade user story argues for `automatic` being easy to choose. 0015 D13's regeneration posture is the nearest precedent and accepts the blast radius explicitly.

- **OQ4: May a definition serve two module majors at once, and if so how do instances move between them?** Status: open. Blocking: acceptance: it decides whether a served CRD carries one version or several, which is API surface. D7 gives one CRD version per major. Serving two majors means two CRD versions with different schemas and no conversion webhook, so `None` conversion would relabel objects without changing their fields, which is wrong. The candidate answer is one served major per definition, with a major upgrade being a new definition (or a rebind that is refused while instances of the old major exist). A two-version story with conversion is a successor.

- **OQ5: What is the status contract of a served-kind instance?** Status: open. Blocking: acceptance: `status` is API surface on every served kind. Minimum: conditions mirrored from the projected `ModuleInstance` (ready, render failed with the diagnostic, rollout state) and a reference to the projected object. Beyond that, a module might want to declare fields the platform surfaces (a connection endpoint, a generated credential's Secret name), which would need a `#status` schema on `#Module` beside `#config`, a core addition the entry does not otherwise need. The candidate answer is the fixed minimum now, `#status` as a successor when a consumer for it exists, the same posture 0015 D9 takes for a derived `#provides`.

- **OQ6: Is `#config` structural-ness also gated at publish time?** Status: open. Blocking: deferrable. D2 refuses at definition acceptance, which is the floor. A publish-side gate in the 0011 family would tell a module author at publish that their module cannot be offered as a kind, before anyone tries to bind it. It cannot be the only check (modules published before the gate exist, and modules never meant to be offered must keep publishing), so the question is whether it is worth adding and whether it is a warning or a refusal.

- **OQ7: Is the projected `ModuleInstance` a real object in the cluster, or in-memory only?** Status: open. Blocking: acceptance: it decides ownership, deletion cascade, the 0006 CLI-operator handoff, and 0014's export of a served-kind instance. A real `ModuleInstance` owned by the served-kind instance via an owner reference reuses every existing reconcile, status and inventory path unchanged, makes the kind controller literally "a loop that writes ModuleInstances", and gives 0014 something to export; the cost is one more object per instance and a status that lives in two places. In-memory projection keeps one object per instance and requires the kind controller to reimplement what the `ModuleInstance` reconciler already does. The candidate answer is the real object.

- **OQ8: What is the tenant guardrail, and how does tenancy map through the projection?** Status: open. Blocking: acceptance: it is the security contract the tenancy user story rests on. Two parts. First, the binding layer's refusal of a direct module reference under a tenant identity: a ValidatingAdmissionPolicy keyed on the requesting identity, or RBAC that grants tenants served kinds and never `ModuleInstance`. Second, which ServiceAccount the projected `ModuleInstance` renders and applies under: the candidate is the instance namespace's tenant ServiceAccount, exactly as a hand-authored instance in that namespace would, so a served kind grants no privilege the tenant does not already hold.

- **OQ9: Do `#config` defaults become CRD defaults?** Status: open. Blocking: deferrable. A CUE default in `#config` can be emitted as an OpenAPI `default`, so the API server fills it and `kubectl explain` shows it; or defaulting can stay in the render, where 0017's layered defaults design places it. Emitting defaults into the CRD means a default change on rebind rewrites stored objects' effective values. Interacts with 0017 and should be answered against it.

- **OQ10: May a definition bind values the consumer never sees, and is the served schema `#config` minus the bound fields?** Status: open. Blocking: acceptance: it decides the served schema's shape. The platform will want to fix storage class, image registry, backup policy and similar without exposing them. The candidate answer is yes: `spec.values` on the definition carries bound values, the projection unifies them with consumer values and refuses a conflict (D6), and the served schema omits every field the definition binds, so a consumer cannot even attempt to set one. The alternative, exposing all of `#config` and refusing overrides at admission, is simpler to generate and worse to use.

- **OQ11: What happens to a definition's deletion, and to its instances, when instances exist?** Status: open. Blocking: deferrable. The candidate is 0015 D3's posture: deletion refused by a finalizer naming the dependent count, so an offering cannot vanish under its consumers. The alternative, orphaning instances as plain `ModuleInstance` objects (mechanical if OQ7 makes them real objects), is a legitimate migration path off an offering and may be an explicit action rather than a deletion side effect.

- **OQ12: Who installs the served CRD: the operator at runtime, or rendered output the platform applies?** Status: open. Blocking: deferrable. Dynamic installation by the operator is what KRO and Kratix do and keeps the definition self-contained. Rendering the CRD as output of the definition's own transformer (the same self-hosting shape as D5) would put the CRD under GitOps ownership and the RBAC gate, at the cost of a two-step apply (CRD, then definition activation). The answer is mechanism-adjacent but it decides who owns the CRD object, which is contract.
