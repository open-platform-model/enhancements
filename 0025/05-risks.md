# Risks, Drawbacks, Alternatives: Self-Describing Modules

Risks describe what could go wrong. Drawbacks describe what definitely costs something. Alternatives describe the high-level paths not taken; per-decision detail lives in `03-decisions.md`.

## Risks and Mitigations

- **Extension-slot sprawl.** A generic attachment point on `#Module` invites every future need to become a module trait, and Kubernetes annotations show where an untyped version of that ends. **Mitigation:** a module trait is catalog-published under its own API version and the additive promise, `#TraitOptionalGate` refuses a pinned posture, and D14 puts every aspect under the contract inventory, so a trait nobody handles is a diagnostic, not a silent no-op. The gate on sprawl is the catalog's, where it already is for component traits.
- **One extension point, many consumers.** `#aspects` is a generic slot, and the entries that fill it arrive with their own questions: a declaration of what a module offers (entry 0027), lifecycle and workflow placement (entry 0009), a rendered policy trait in some catalog. Read together they can look like several designs under one title, which the `single-question` admission gate refuses. **Mitigation:** the question here is one, what a module may say about itself as a whole and how that statement is matched and rendered, and D11 to D15 all rest on it. No vocabulary ships here (D15), so there is no second design inside the entry. Every consumer is its own entry resting on this one through a `depends_on` edge, which is the shape the gate's own redirect asks for.
- **A second matching pass per render.** Aspects add a walk over their attachment maps and a matching pass beside the components'. **Mitigation:** the per-component cost 0019 measured is small and linear; an aspect count is far below a component count in any real module. Re-measure before promotion if a module with many aspects appears.
- **An extension point with no shipped instance.** Nothing in a catalog uses the slot when this entry lands (D15), so a design error in `#Aspect` surfaces only when the first consumer publishes a trait. **Mitigation:** the delta's fixtures stand up three module traits and run a transformer end to end, and two consumers (entries 0027 and 0009) already carry `**Depends:**` edges into D11 and D12, so the shape is being designed against real demands rather than an imagined one.

## Drawbacks

- **Two attachment vocabularies.** A catalog author now keeps component traits and module traits apart, and a module author learns which concern belongs where. The rule is short (a workload's concern is a trait, the module's is a module trait) and the schemas refuse the wrong one, but it is one more distinction to teach.
- **A second thing to learn.** A catalog author now asks whether a word is about a workload or about a module, and a reader of a module has two maps to read instead of one.
- **The capability is invisible on the day it lands.** Until a catalog publishes a module trait, nothing a user can run behaves differently. The value arrives with the first consumer.

## Alternatives

- **A field on `#Module` per module-wide concern.** The path OPM was already on: one entry wants lifecycle, another wants seed values, this one wants a way to say what a module is. **Why not:** each field arrives with its own consumer, its own versioning story and no matching, so the schema grows a field per feature and nothing can report a field nobody implements.
- **A second whole-object schema.** A `#ServiceModule` beside `#Module`, carrying the module-wide facts `#Module` has no room for. **Why not:** two object schemas sharing nothing, a third for the next kind of module, and every consumer of a module branching on which one it is holding.
- **Reuse the component machinery verbatim.** A component that attaches traits and declares no resources can carry a module-wide concern today. **Why not:** it satisfies the component transformer contract, one workload and one component context, while lying about scope, so every transformer author has to know it might be looking at one. The machinery is reused by transposition instead: an aspect matches the way a component matches, under its own definition.
- **Keep every module-wide fact outside the module.** Two shapes of the same answer, and between them the state of the art this entry is measured against. A NetworkPolicy and a ResourceQuota written by the platform team beside the module, or attached by an external policy engine keyed on labels. And, when the fact is meant to change how the module is interpreted rather than to become an object, a controller written beside it carrying an API by hand. **Why not:** the fact then does not travel with the module artifact, is not versioned with it, and cannot read `#config`, so the two drift the first time the module changes shape. The hand-written API drifts the same way, and costs a second codebase to operate. The contrast with both is what "a module describes itself" means.
- **A module-level pass over rendered output.** Render the components, then append to or mutate the result, the overlay shape. **Why not:** a second build after the first, which is what the single build and its parity oracle exist to prevent (0019:D9). The aspect pass joins the one build instead of post-processing it.
