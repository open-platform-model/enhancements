# Enhancement Diagrams

Design discussion is full of things worth drawing: how a new entry relates to the others, how a protocol resolves its inputs, what a layered design looks like once a part is removed. This skill makes a diagram the default move at the right moments.

## The split

Mermaid is the medium for both kinds. The kind decides what the diagram may show.

- **A relationship diagram** has entries as nodes. `GRAPH.md` already draws it, generated by `task index` from `after` (an entry follows another) and `superseded_by`. Never draw one into an entry. A sketch during a discussion is scaffolding for the conversation.
- **A mechanism diagram** has actors, artifacts, data, states or components as nodes. **Every `design.md` carries exactly one**, under `## How it works`, in Mermaid: one diagram of at most 7 boxes, each a plain phrase, with at most three sentences below it. The template is `openspec/schemas/enhancement/templates/design.md`.

The `README.md` of an entry is generated and carries no diagram.

## When this skill applies

Load it when:

- you write or change `## How it works` in a `design.md`;
- a design discussion would settle faster with a picture: a theme of the design, a before and after, a handoff between components;
- you weigh whether to split an entry in two, merge two, or set `after` or `superseded_by`;
- you add a diagram to an `evidence/` note;
- you are unsure which kind of diagram a question needs.

Skip it when a generated file already answers the question. If `GRAPH.md` shows what is asked, point at it. Run `task index` first if it may be stale.

## Reaching for a diagram

| Question shape | Reach for | Example |
| --- | --- | --- |
| What is this entry about, in one picture? | Mermaid in `design.md ## How it works` | One per entry. The mechanism it designs. |
| Should this entry follow, or be superseded by, another? | A relationship sketch in the chat | Draw the graph both ways before you edit `config.yaml`. |
| Should we split this entry, or merge two? | A relationship sketch, before and after | Look at the graph both ways first. |
| How does data flow through this pipeline or protocol? | `flowchart` | Inputs, plan, verdict. |
| Who calls whom, in what order? | `sequenceDiagram` | A handoff between two frontends and a controller. |
| What states does this object move through? | `stateDiagram-v2` | A claim that is pending, accepted, then active. |
| What does it look like before and after? | Two `subgraph` blocks | In an `evidence/` note, linked from the theme. |

## Relationship sketches

Sketch it inline in the chat. No tool call is needed at typical size. Reuse the palette of `GRAPH.md` so the sketch looks like the file that `task index` writes:

```text
classDef draft       fill:#fef3c7,stroke:#b45309,color:#000
classDef accepted    fill:#dbeafe,stroke:#1d4ed8,color:#000
classDef rejected    fill:#fee2e2,stroke:#b91c1c,color:#7f1d1d,stroke-dasharray:4 2
classDef withdrawn   fill:#fef2f2,stroke:#b91c1c,color:#7f1d1d,stroke-dasharray:1 3
classDef superseded  fill:#e5e7eb,stroke:#6b7280,color:#6b7280
classDef delivered   fill:#dcfce7,stroke:#15803d,color:#14532d
classDef stub        fill:#f3f4f6,stroke:#9ca3af,color:#374151
classDef category    fill:#ede9fe,stroke:#6d28d9,color:#000
```

`GRAPH.md` is split by `config.yaml` `category`. An Overview has categories as nodes and counts the `after` edges between them. Then there is one diagram per category, where an entry of another category is a grey `stub`. A closed entry (delivered, rejected, superseded, withdrawn) appears only where a live entry's edge reaches it. Follow the same two conventions in a sketch.

When the decision is made, encode it in `config.yaml` and run `task index`. Never edit `GRAPH.md` to match a sketch.

## Mechanism diagrams

Rules for any mechanism diagram:

- **One concept per diagram.** If you draw two things, split them. A second mechanism goes in an `evidence/` note.
- **Never bare.** Give it prose: the diagram shows the shape, the prose says what to take from it. In `design.md`, three sentences at most.
- **Small.** In `design.md`, at most 7 boxes. A diagram that needs a legend should be two diagrams.
- **Concepts, not construction.** Nodes are actors, artifacts, data and steps: `Platform spec`, `Registration CR`, `Render`. Never a file path, a package name, a function or a line number. Those are the target repo's to choose, and naming one is prescribing mechanism.

### Authoring Mermaid safely

A syntax error does not degrade. It replaces the whole diagram with an error box. The traps:

- **Quote every label with punctuation**: `A["Render (one build)"]`, not `A[Render (one build)]`. Parentheses, colons, commas, slashes and quotes all need the quotes.
- **No `#` in a label.** Mermaid reads it as the start of an entity code. Write `Module`, not `#Module`. The same goes for `@` at the start of a word.
- **No node id starting with `o` or `x`**, and none named `graph`, `end`, `set`, `class` or `style`. `A-->oB` parses as a circle arrowhead, and the keywords are reserved.
- **No `|` or `;` in a label**, and no colon or parenthesis in an edge label.
- **ASCII only.** No Unicode arrows, box-drawing characters or emoji.
- **Check before it lands.** Render it, or read the block on the PR's Files changed view, which renders Mermaid. Never commit a block nobody has seen rendered.

## Live, during discussion

Produce the diagram inline in the chat. Use a rendered page only when the owner wants something kept across a long session, and ask before you switch.

## Anti-patterns

- **A relationship diagram drawn into an entry.** It goes stale the first time `after` changes, and nothing catches it.
- **More than one diagram in `## How it works`, or none.** A second mechanism belongs in an `evidence/` note.
- **A Mermaid block nobody rendered.**
- **A file path, package name or function as a node.**
- **A bare diagram with no prose.**
- **One diagram for two concepts.**
- **Editing `GRAPH.md` by hand.** It carries a "do not edit" header for a reason.
- **A diagram as decoration.** If the question is "how does X relate to Y" or "how does this flow", a diagram is often the answer.
