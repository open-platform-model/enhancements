# Open Questions: OPM Versioning Policy

This is the entry's working question register. `OQ` numbers are permanent. Each unresolved entry carries a `Status:` line and a `Blocking:` field (`acceptance` with the reason inline, `deferrable`, or `implementation`). Once resolved, the bullet collapses to its question and its status; the answer lives in the decision it points at.

## Open Questions

### The module surface

- **OQ1: Does the rendered output's stateful identity form a second compatibility surface for modules?** Status: open. Blocking: acceptance, because it decides whether the concrete example's PVC rename is a patch or a major, and a module author cannot follow a rule that has not said. D2 binds the version to `#config`, which is the input contract. The output contract an instance also depends on is narrower than "the rendered output": the names and kinds of the resources that carry state or identity (volume claims, workload kind, service names, ports), which each component already computes as its own `#names`. Candidates: (a) `#config` only, and the policy documents stateful renames as a convention-layer "treat as breaking"; (b) two surfaces, `#config` gated mechanically and stateful identity by written rule now and a render diff later; (c) two surfaces, both gated from the start, which needs a definition of "stateful identity" a gate can compute. What would settle it: whether the workspace fleet's history contains identity changes that shipped as patches, measured against the modules' release history.
- **OQ2: Do modules carry a maturity rung beside SemVer, or is SemVer with `0.x` and prerelease lines the whole ladder?** Status: open. Blocking: acceptance, because it decides whether `#Module.metadata` gains a field, which would flip `core_schema` and change what an author declares. The catalog ladder exists because a catalog build carries many independently evolving contracts under one number (0010 D4); a module is one unit with a major in its path. The `05-risks.md` alternative argues against a rung; the case for one is a stability signal beyond "pre-1.0" that a platform could filter on. What would settle it: whether any consumer today wants to distinguish "stable module at 0.x" from "experimental module at 1.x", or whether the prerelease line already says it.
- **OQ3: Is a change to a `#config` default additive or breaking?** Status: open. Blocking: acceptance, because the design table has one unfilled row and it is the row authors get wrong. A default change never fails unification, so subsumption alone calls it additive; it moves the rendered output of every instance that left the field unset, which is why 0010 D27 made contract defaults immutable within a level. Candidates: additive (SemVer-literal), breaking (0010 D27-consistent), or breaking only when the default reaches a stateful surface (couples to OQ1). What would settle it: a decision on consistency with D27, since a module author and a catalog author reading two different answers for the same act is the outcome the policy exists to prevent.
- **OQ4: What is the pre-stable form for modules, and what does it permit?** Status: open. Blocking: acceptance, because the workspace fleet's v2 line is unreleased and its first releases will be cut under whichever rule stands. U3 says the promise is off pre-stable. For modules the candidates are `0.x` (SemVer's own escape hatch, breaking allowed in minors), an `-alpha.N` line on `1.0.0` (the form core, catalogs and the Go artifacts all use today under release-please), or both permitted with the policy stating their precedence. What would settle it: whether the fleet's release tooling is kept on release-please prerelease mode, in which case the alpha line is the form already in hand.

### The gate

- **OQ5: What does a module compatibility gate compare, and against which predecessor?** Status: open. Blocking: deferrable, because the gate is scaffolded as design intent and the policy binds without it. The comparison is subsumption of the previous release's `#config` by the new one, computable because `#config` is OpenAPIv3-shaped. Predecessor selection can inherit 0011 D23's backward scan (same major, prereleases included, newest first). Open within that: whether the gate also compares the OQ1 surface if one is adopted, and what it does for a module whose predecessor was published outside the CLI and carries no readable `#config` at the expected path. Context for an implementer: the catalog gate's walk and refusal shape are the precedent; the module walk is the same loop over one member.
- **OQ6: What does the gate refuse, and can the same comparison carry a gate for the core schema?** Status: open. Blocking: deferrable. The refusal rule follows U2: refuse when the authored bump is below the maximum change class the comparison found, naming the field and the level demanded; a pre-stable version (OQ4) is never refused for a break, only for an already-published tag (0011 D15). For core, the surface is the set of published definitions and subsumption per definition is computable in principle, but core's consumers are catalogs and the kernel rather than value files, and a definition that gains a required field is breaking for authors while a definition that is removed is breaking for importers; whether one comparison covers both is unmeasured. What would settle it: a throwaway comparison of two consecutive core alpha releases to see whether definition subsumption classifies the actual changes the way the changelog did.

### Cross-class rules

- **OQ7: How does a contract-level event move the catalog build number?** Status: open. Blocking: acceptance, because the class that already has a gate would otherwise be the one class the policy leaves implicit. 0010 D34 makes the build SemVer and the contract level independent axes; the policy must still say what a build's bump is when its contents change on the ladder. Candidates per event: a new `apiVersion` level shipped beside its predecessor is additive (minor); a tombstone under 0020 D6 is breaking for anyone demanding the key (major) or additive because the key was seasoned and declared (minor); an alpha-rung break is invisible to the build number because alpha promises nothing (0010 D34); a transformer change is whatever the transformer's own surface says, since transformers are keyed by the build (0010 D44). What would settle it: a decision that the build number tracks the *catalog's* promise (its member set) and never restates a *contract's* promise (its level), or the reverse.
- **OQ8: What is the CLI's compatibility surface?** Status: open. Blocking: acceptance for the definition, because U6 requires each class to state whether its surface is comparable and the CLI is what consumers install; deferrable for any enforcement. Candidates for the surface: command names and their required arguments, flag names and defaults, exit codes, and any output declared machine-readable; help text and human-readable output excluded. Removing or renaming any of the first four is breaking; adding a command or a flag is additive. What would settle it: agreement that machine-readable output formats are part of the surface once declared, since that is the part scripts break on.
- **OQ9: What is the operator's CRD versioning policy?** Status: open. Blocking: acceptance for the statement, deferrable for anything it requires building. The operator serves one group version, `v1alpha1`, and Kubernetes supplies the ladder and its own compatibility rules (storage version, conversion, served versions). Under U3 the alpha rung promises nothing, which is honest for the current state; the policy needs to say what a `v1beta1` would require (a served-alongside window and conversion, which Kubernetes mandates, and which is the one place OPM inherits a consumer window it did not choose) and how the CRD version relates to the operator binary's SemVer. What would settle it: a decision that the CRD ladder and the binary SemVer are independent axes on the 0010 D34 pattern, with the binary's surface being controller behaviour.
- **OQ10: What is the kernel library's compatibility surface, given that its only consumers are `cli` and `opm-operator`?** Status: open. Blocking: deferrable. The exported Go API is the literal surface and Go's own major-in-path rule applies at `v2`; the practical question is whether OPM promises anything to a third party embedding the kernel, or whether the library is versioned for its two first-party consumers and says so. What would settle it: whether any consumer outside the workspace embeds the library.
- **OQ11: Are platforms versioned artifacts?** Status: open. Blocking: deferrable. The `platforms` registry prefix is reserved and nothing is published under it; a platform names catalog builds by scalar version and is a consumer. If a platform is ever published (a shareable platform definition), it becomes a class with a surface (its subscriptions and its component overrides). Nothing decides this until something publishes one.
- **OQ12: What does a module whose published history already contains an in-major `#config` break do at its next release?** Status: open. Blocking: deferrable. The policy reclassifies past promises without changing past bytes. Candidates: nothing, the policy binds from the next release forward and the gate compares against the immediate predecessor only; or the next release must be a major to restore the invariant that every version inside a major subsumes its predecessor. The second is cleaner and costs every affected module a major at once. What would settle it: measuring the fleet for in-major breaks that already shipped.
- **OQ13: How does a core major bump cascade to catalogs and modules?** Status: open. Blocking: deferrable. A core major is an import rewrite for every catalog and module (U5). A catalog that moves to the new core major changes its own contracts' shapes only if core's change reaches them; whether the move alone is breaking for the catalog's consumers (who must also move) is unstated, and the same holds one hop down for modules. Candidates: the move is breaking for the mover's consumers because they cannot unify across core majors, so it is a major all the way down; or the move is additive because the old major stays resolvable forever and nothing forces the consumer to follow. What would settle it: whether a consumer on the old core major can consume a catalog build on the new one at all, which is measurable with two workspace catalogs.

### The tooling train and its documentation

- **OQ14: Do the kernel library, the CLI and the operator release in lockstep on one version?** Status: open. Blocking: acceptance, because it decides whether class 7 is one row or three, whether the kernel has an external API surface at all, and what class 9 is versioned against. The author's position is that it is probably better: the three have only each other as consumers, the CLI already pins the operator manifest and enforces a skew ceiling, and one number removes both as compatibility problems. Candidates: (a) one train, one version, released from one manifest whether the repos merge or not; (b) three trains with a stated compatibility matrix and a gate that checks the CLI's operator pin and the kernel pin in both consumers on every release; (c) two trains, kernel separate because it is a library. What would settle it: whether any consumer outside the workspace embeds the kernel or pins the operator independently of the CLI, and whether the release tooling can cut one version across three repos without merging them.
- **OQ15: How is the documentation site versioned?** Status: open. Blocking: acceptance for the rule, deferrable for the build. Today the site is a flat tree with a site-wide version string, and its generators read the core schema and the CLI at whatever versions are checked out. The author's position: versioning docs per component (kernel, catalog, tooling) is the accurate model and is too expensive to maintain; versioning against the tooling train (OQ14) with the schema and catalog versions that train pins stated on each generated page is the tractable one. Candidates: (a) one docs version per train release, older versions archived and reachable; (b) unversioned docs that always describe the latest train, with each generated reference page stamped with the versions it was generated from; (c) per-component versioning, rejected as above unless something makes it cheap. What would settle it: OQ14, and whether the generated reference pages can carry their source versions today.
- **OQ16: What replaces the kernel's migration ledger?** Status: open. Blocking: deferrable. The ledger today is a hand-written file of breaking and additive entries keyed to a commit trailer, and it claims a release gate that was proposed and never built. Under OQ14 (a) the kernel's Go API stops being a consumer-facing contract and the ledger becomes an internal changelog section, which is the "something better" the author asked for: the problem dissolves rather than gets a gate. Under (b) or (c) the candidates are an API-diff tool run at release that refuses a non-major on a removed or changed exported symbol, or the ledger kept and its claimed gate actually built. What would settle it: OQ14.

### Transformers

- **OQ17: Can one component carry two levels of the same resource or trait at once?** Status: open. Blocking: deferrable. D6 assumes that per-level transformer registrations never both match one component. A component names a resource through its spec key (`spec.container`), which is the bare resource name without a level, so two levels of one resource would collide on the key and a component should be able to name exactly one. If that holds, D6 is safe by construction; if a component can carry both, two registrations match it and both render, and D6 needs a rule for which wins. What would settle it: a fixture component declaring both `container@v1beta1` and `container@v1` under the current core schema, and what `cue vet` says.

The sweep of 2026-08-24 also raised the catalog build class's reason to exist beside the contract class; D4 answers it (a platform pins a build, and transformer keys embed it) and leaves the build's bump rule for contract-level events to OQ7.
