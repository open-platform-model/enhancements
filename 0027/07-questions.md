# Open Questions: Self-Service Kinds from Published Modules

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design.

`OQ` numbers are permanent, never reused, never renumbered, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves. Each **unresolved** entry also carries a `Blocking:` field: `acceptance` (with the reason inline; `task promote` refuses while open), `deferrable` (may stay open at `accepted`), or `implementation` (handed to delivery; the change that settles it claims it via `resolves` in `delivery.yaml`). Contract-level questions cannot be deferred to implementation.

While a question is open, its bullet is a working surface: edit the wording, sharpen the framing, add or drop alternatives freely. Once resolved, the bullet collapses to its question and its status at the `draft → accepted` compaction pass.

## Open Questions

**OQ13 to OQ15 are entry 0025's**, and the numbers here are the ones this half carried in 0025 before the scope split, so an existing citation of `0025 OQ7` resolves by changing only the entry id. That leaves a gap at OQ13 to OQ15 and OQ16 in its original place.

## Open Questions

- **OQ1: What is the kind name of the platform-owned definition object?** Status: open. Blocking: acceptance: the kind is the CRD's API surface and every consumer types it. Five candidates, none with a `Module` prefix, since the object is platform-owned like `Platform` and `TransformerRegistration` rather than module-family like `ModuleInstance`. `Offering` (Cloud Foundry and Open Service Broker lineage, safest, least distinctive). `Capability` (the CNCF platforms white paper's vocabulary; mild collision with the capability-based routing 0015 names as successor material). `Facade` (most precise about the mechanism: `#config` is the interface, `#components` is hidden; unusual as a kind). `Promise` (best semantic fit; Kratix's core CR, so it reads as derivative). `Form` (the consumer's mental model; too generic in code). Rejected on collision: anything with Catalog, Blueprint, Template, Release, Claim, Service, Package or Class in it, each colliding with an OPM word, a retired OPM word, a Kubernetes kind, or a rejected 0015 vocabulary. Until resolved the draft uses "offering" in lower case as a placeholder noun, never as a kind; the CUE identifiers in `schemas/` carry the placeholder and rename with the decision.

- **OQ2: Does the binding layer ship as a product on its own, or only as an implementation slice of the kind layer?** Status: open. Blocking: acceptance: it decides scope, `semver`, and whether the `ModuleInstance` definition reference is a documented consumer surface or an internal one. Shipping it alone delivers platform-owned versioning and the tenant guardrail with no dynamic CRDs; the cost is a documented second way to write a `ModuleInstance` that the kind layer later makes rarely used. Shipping it only as a slice keeps the consumer surface to served kinds and leaves platforms that do not want dynamic CRDs with nothing. The answer also bears on OQ1: `Offering` and `Capability` cover both layers, `Facade` and a kind-only name fit the second alone.

- **OQ3: What is the update-policy vocabulary on a definition, what is its default, and what does each value do to live instances?** Status: open. Blocking: acceptance: the policy is contract on the definition and the rebinding blast radius depends on it. Candidates: `automatic` (a rebind re-renders every instance under the instance's own rollout controls) and `manual` (a rebind takes effect per instance when the instance is next changed, or on an explicit per-instance action). A channel model (the definition tracks the newest release inside its major) is a third value or a successor. StorageClass's silent re-route is the failure mode to avoid, which argues for `manual` as the default; the fleet-upgrade user story argues for `automatic` being easy to choose. 0015 D13's regeneration posture is the nearest precedent and accepts the blast radius explicitly.

- **OQ4: May a definition serve two module majors at once, and if so how do instances move between them?** Status: open. Blocking: acceptance: it decides whether a served CRD carries one version or several, which is API surface. D7 gives one CRD version per major. Serving two majors means two CRD versions with different schemas and no conversion webhook, so `None` conversion would relabel objects without changing their fields, which is wrong. The candidate answer is one served major per definition, with a major upgrade being a new definition (or a rebind that is refused while instances of the old major exist). A two-version story with conversion is a successor.

- **OQ5: What is the status contract of a served-kind instance?** Status: open. Blocking: acceptance: `status` is API surface on every served kind. Minimum: conditions mirrored from the projected `ModuleInstance` (ready, render failed with the diagnostic, rollout state) and a reference to the projected object. Beyond that, a module might want to declare fields the platform surfaces (a connection endpoint, a generated credential's Secret name). Under D5 and D11 that declaration has a home: the `offering` module trait's spec on an aspect (0025:D11), beside the declared group and kind, so no field is added to `#Module` for it. The candidate answer is the fixed minimum now, and a declared status schema on the `offering` trait as a successor when a consumer for it exists, the same posture 0015 D9 takes for a derived `#provides`.

- **OQ6: Is `#config` structural-ness also gated at publish time?** Status: open. Blocking: deferrable. D2 refuses at definition acceptance, which is the floor. A publish-side gate in the 0011 family would tell a module author at publish that their module cannot be offered as a kind, before anyone tries to bind it. It cannot be the only check (modules published before the gate exist, and modules never meant to be offered must keep publishing), so the question is whether it is worth adding and whether it is a warning or a refusal. The `offering` module trait (D5) gives such a gate a declared intent to key on: a module that declares an offering and whose `#config` does not encode is a refusal worth making at publish, while an undeclared module stays a warning at most.

- **OQ7: Is the projected `ModuleInstance` a real object in the cluster, or in-memory only?** Status: open. Blocking: acceptance: it decides ownership, deletion cascade, the 0006 CLI-operator handoff, and 0014's export of a served-kind instance. A real `ModuleInstance` owned by the served-kind instance via an owner reference reuses every existing reconcile, status and inventory path unchanged, makes the kind controller literally "a loop that writes ModuleInstances", and gives 0014 something to export; the cost is one more object per instance and a status that lives in two places. In-memory projection keeps one object per instance and requires the kind controller to reimplement what the `ModuleInstance` reconciler already does. The candidate answer is the real object.

- **OQ8: What is the tenant guardrail, and how does tenancy map through the projection?** Status: open. Blocking: acceptance: it is the security contract the tenancy user story rests on. Two parts. First, the binding layer's refusal of a direct module reference under a tenant identity: a ValidatingAdmissionPolicy keyed on the requesting identity, or RBAC that grants tenants served kinds and never `ModuleInstance`. Second, which ServiceAccount the projected `ModuleInstance` renders and applies under: the candidate is the instance namespace's tenant ServiceAccount, exactly as a hand-authored instance in that namespace would, so a served kind grants no privilege the tenant does not already hold.

- **OQ9: Do `#config` defaults become CRD defaults?** Status: open. Blocking: deferrable. A CUE default in `#config` can be emitted as an OpenAPI `default`, so the API server fills it and `kubectl explain` shows it; or defaulting can stay in the render, where 0017's layered defaults design places it. Emitting defaults into the CRD means a default change on rebind rewrites stored objects' effective values. Interacts with 0017 and should be answered against it.

- **OQ10: May a definition bind values the consumer never sees, and is the served schema `#config` minus the bound fields?** Status: open. Blocking: acceptance: it decides the served schema's shape. The platform will want to fix storage class, image registry, backup policy and similar without exposing them. The candidate answer is yes: `spec.values` on the definition carries bound values, the projection unifies them with consumer values and refuses a conflict (D6), and the served schema omits every field the definition binds, so a consumer cannot even attempt to set one. The alternative, exposing all of `#config` and refusing overrides at admission, is simpler to generate and worse to use.

- **OQ11: What happens to a definition's deletion, and to its instances, when instances exist?** Status: open. Blocking: deferrable. The candidate is 0015 D3's posture: deletion refused by a finalizer naming the dependent count, so an offering cannot vanish under its consumers. The alternative, orphaning instances as plain `ModuleInstance` objects (mechanical if OQ7 makes them real objects), is a legitimate migration path off an offering and may be an explicit action rather than a deletion side effect.

- **OQ12: Who installs the served CRD: the operator at runtime, or rendered output the platform applies?** Status: open. Blocking: deferrable. Dynamic installation by the operator is what KRO and Kratix do and keeps the definition self-contained. Rendering the CRD as output of the definition's own transformer (the same self-hosting shape as D5) would put the CRD under GitOps ownership and the RBAC gate, at the cost of a two-step apply (CRD, then definition activation). The answer is mechanism-adjacent but it decides who owns the CRD object, which is contract.

- **OQ16: May the `offering` trait carry suggested bound values the platform definition inherits?** Status: open. Blocking: deferrable. A module author often knows which `#config` fields a platform will want to fix (a storage class, an image registry). Letting the declaration suggest them, for the CLI to draft into `spec.values`, is convenient; letting the definition inherit them silently would move a platform decision into the module. The candidate answer is suggest-only: the CLI copies them into the draft and the definition carries them explicitly or not at all. Interacts with OQ10.

### Served schema and portal questions

OQ17 to OQ23 come from the portal and marketplace design (entry 0031), and OQ24 to OQ29 are its order questions, folded here because an order is an instance of this entry's served kind. Candidates marked *measured* come from this entry's [`experiments/`](experiments/) and are recommendations, not decisions.

- **OQ17: May the definition carry an optional presentation block whose content entry 0031 defines?** Status: open. Blocking: deferrable: an optional, inert field can be added after acceptance. A platform team needs to brand and curate an offering (title, icon, field labels, presets) without a module release, and the definition is the only object it owns. Candidate: the definition gains an optional presentation block; 0031 defines its content; changing it re-renders nothing and changes no served schema; and it is outside the declaration D5 compares, so a module's offering declaration never disagrees with it. Alternative: revise D1 in place now to name the block.

- **OQ18: Do the served CRD, the CLI pre-flight and every form agree on what is valid, binding-only definitions included?** Status: open. Blocking: acceptance: it decides whether "the served schema" is one artifact or several (extends OQ10). No decision assigns the subtraction of bound fields, and a binding-only definition (D1:R4) has no CRD for a reader to compare against. Candidate: one structural encoding of `#config` minus the bound fields, reported by digest in the definition status, which every reader compares. *Measured:* offline structural validation agreed with a live API server on 403 of 403 CRD verdicts, so the CLI can reach the same CRD verdict as the operator without a cluster ([`experiments/02-validator-agreement/`](experiments/02-validator-agreement/)).

- **OQ19: How is a `#Secret` field encoded in the served structural schema?** Status: open. Blocking: acceptance: without an answer, D2:R3 refuses every module that declares a secret, because `#Secret` is a struct union. *Measured candidate (B):* recognise the field by core's hidden secret tag, never by shape, and serve a fixed flattened object (`value`, `ref`, `key`, `source`, with `settings` and `spec` preserving unknown fields) constrained by `oneOf` over the arms with `not` on foreign fields. It agreed with CUE on 55 of 55 fixtures and has no CEL cost ceiling; its kubectl messages are poor. *Optional improvement (A):* the same object with CEL rules, clearer messages, 53 of 53, but CRD admission fails from 4 unbounded lists or maps of secrets unless the lists are bounded, so it fits only where the CEL cost budget allows. Rejected: an explicit discriminator (C, by analysis: changes the values contract) and an opaque object (D, measured: 31 of 55 false accepts). Either way `value` carries no pattern, enum, format or length bound, so the API server never echoes plaintext ([`experiments/03-secret-encoding/`](experiments/03-secret-encoding/)).

- **OQ20: How are struct unions in `#config` served, and which are refused?** Status: open. Blocking: acceptance: it decides which modules D2 refuses. *Measured candidate:* serve discriminated unions (a distinct constant per arm) and presence-discriminated ones (each arm owns a field) with the OQ19 mechanism; require the discriminator in the served schema even where CUE could infer it (the one false refusal measured, 54 of 55 otherwise); reduce struct defaults `*{...} | T` to their default arm first, since they are not unions; and refuse five shapes by name: arms typing one non-constant field differently, mixed scalar-or-struct unions, two or more candidate discriminators without a discriminator hint, no discriminator where some arm owns no field of its own, and open arms without a discriminator. With defaults reduced, 20 of 20 real modules encode with no refusal; the fleet has no true struct union today ([`experiments/04-struct-unions/`](experiments/04-struct-unions/)).

- **OQ21: Is a defaulted `#config` field required in the served schema, and what happens to computed fields?** Status: open. Blocking: acceptance: `required` is API surface. *Measured candidate (required):* a field is required only when marked required or when it is a regular field with no default that is neither concrete nor computed, and defaults are not emitted as CRD defaults (consistent with OQ9's candidate of keeping defaulting in the render). That rule accepted every real module's own `debugValues` (20 of 20), where an encoder marking computed fields required refused 19 of 20, so whatever else an encoder does, it must not mark a computed field required. *Measured and rejected (computed):* serving a computed field (a concrete regular field, an interpolation, a comprehension output) as a one-value enum, which the measured candidate encoder still does, refuses valid values: setting a different input together with the matching computed value is refused although CUE accepts it. *Unmeasured candidates (computed):* (a) computed fields leave the consumer schema, so setting one is an unknown field; (b) they stay as unconstrained strings, admitted but unchecked until the render. A measured constraint on every candidate: strict decoding refuses a CRD that carries an `x-opm-*` key, so an encoder that marks computed fields that way produces a CRD the API server refuses or prunes ([`experiments/05-required-and-computed/`](experiments/05-required-and-computed/)).

- **OQ22: How is D2:R2's admission promise kept when the structural schema is a lossy subset of `#config`?** Status: open. Blocking: acceptance: kubectl and GitOps creates pass admission with values CUE refuses at render. Experiment 05 shows the loss is real (a computed field's wrong value is admitted) even with the candidate encoder. Candidates: (a) a validating webhook that runs CUE through the projection, keeping D2:R2 as written at the cost of a webhook on the admission path; (b) narrow D2:R2 to "refused at admission where the structural schema expresses the constraint, otherwise refused at render as a status condition naming the path". Either way, D2:R3 names the shapes the encoder refuses (OQ20's five at least).

- **OQ23: May a module declare outputs that served-kind status reports (endpoints, credential Secret names)?** Status: open. Blocking: deferrable: status fields can be added after acceptance. Extends OQ5. Candidate: the `offering` trait's spec gains an optional outputs schema (endpoint URLs, Secret name and key references, never secret data), mirrored into status by the kind controller. It touches 0025's trait, so it waits on 0025:OQ13.

- **OQ24: What may a UI create on a tenant's behalf?** Status: open. Blocking: acceptance: it is the write half of the tenancy contract (OQ8). Candidate: an instance of a served kind only, created as the user after a server-side dry-run, never a `ModuleInstance` that names a module, which is the bypass OQ8's guardrail refuses.

- **OQ25: Is a binding-only definition orderable from a UI?** Status: open. Blocking: acceptance: it waits on OQ2 and OQ8. A binding-only definition has no served kind, so an order would be a definition-referencing `ModuleInstance`. Candidate: orderable only if OQ8 picks the admission-policy guardrail; under the RBAC guardrail a tenant cannot create any `ModuleInstance`, so not orderable by tenants.

- **OQ26: Under which identity does an in-cluster UI write an order?** Status: open. Blocking: acceptance: a create under the UI's own ServiceAccount bypasses the user's RBAC and the OQ8 guardrail. Candidates: (a) token passthrough, the UI forwarding the user's token where the API server trusts its identity issuer, with no impersonate grant; (b) export only, where the UI hands the object to the user or a GitOps flow and writes nothing; (c) impersonation, which in practice grants acting as anyone and so is confined to a separate write component. Candidate: (a) where the API server trusts the issuer, else (b); (c) only by explicit platform choice.

- **OQ27: How are order and validation errors reported per field?** Status: open. Blocking: deferrable: error wording is a UI's own, the contract is only which path an error names. Candidate: errors are keyed by the `#config` path, mapped from CUE's diagnostic path and from the API server's dry-run causes into one path space; a disjunction's per-arm errors collapse into one; values at declared secret paths are always redacted.

- **OQ28: May a platform disable the literal-value secret arm for an offering?** Status: open. Blocking: deferrable: an optional definition field can be added after acceptance. A literal secret in a served-kind instance is plaintext at rest in etcd. Candidate: yes, as an optional definition field that the served schema enforces by dropping the literal arm, so kubectl creates are refused too, not only forms. This interacts with D2:R1 (the served schema is `#config` and nothing else) and OQ10 (the served schema as `#config` minus definition choices).

- **OQ29: What may prefill an order?** Status: open. Blocking: deferrable: prefill is offered, never asserted. Candidate, in order: a preset the platform defines on the definition, else the module's `initValues` with every bound path removed and the remainder checked through the projection (an invalid prefill is dropped with a notice, never sent), else nothing. `debugValues` is never a prefill: it is the author's test data, and a prefill is one click from a create. OQ16's suggested bound values are never shown as editable defaults.
