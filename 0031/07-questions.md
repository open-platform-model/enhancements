# Open Questions: Module Presentation Contract

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design. The validator requires this file for every entry; the `## Open Questions` block below (with or without entries) is required starting at `status: accepted`.

`OQ` numbers are permanent, never reused, never renumbered, like `DN` and `DN:Rn`, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/`/`contracts/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves.

Each **unresolved** entry also carries a `Blocking:` field saying whether the question gates acceptance:

| Value | Meaning |
| --- | --- |
| `acceptance` | `task promote` refuses while this question is open. Give the reason inline (`Blocking: acceptance: determines config.yaml.semver`). |
| `deferrable` | May stay open at `accepted`. |
| `implementation` | Handed to delivery; the change that settles it claims it via `resolves: [OQ9]` in `delivery.yaml`. |

This is where per-question blocking rules live. They used to be prose in a separate gate document, one cross-reference away from the question they governed. On the question itself, they are visible to whoever answers it, and `task questions:open` and `task promote` can both read them.

`deferred-to-implementation` is the deferral register: an implementation-level question the design deliberately hands to whoever delivers it. Attach the context a future implementer needs (what is unclear, what evidence exists, what would settle it), but never name the inheritor. The change that picks it up claims it in this entry's `delivery.yaml` log entry (`resolves: [OQ9]`), and `task delivery:deferred` reports deferred questions no logged change has claimed. Contract-level questions cannot be deferred this way: they must be resolved before `accepted`.

While a question is open, its bullet is a working surface: edit the wording, sharpen the framing, add or drop alternatives freely. Numbers stay fixed (`schemas/target.cue` marks gated fields with `// OQN:` and decisions cite `resolves OQN`), but the prose is yours to change.

Once resolved, the bullet collapses to its question and its status. The answer now lives in the decision it points at (in `03-decisions.md`); restating it here is how this register grows into a second decision log. Collapsing happens at the `draft → accepted` compaction pass, not by hand mid-design.

## Open Questions

The questions about the served kind itself, and about ordering an offering, are entry 0027's and are not repeated here: an optional presentation block on the definition (0027:OQ17), agreement between the served CRD, the CLI pre-flight and every form (0027:OQ18), the `#Secret` encoding (0027:OQ19), struct unions (0027:OQ20), defaulted and computed fields (0027:OQ21), the lossy structural schema (0027:OQ22), module-declared outputs (0027:OQ23), and the order questions (0027:OQ24 to 0027:OQ29). Several questions below wait on their answers and say which.

### Tenants and readers

- **OQ1: Who may read offerings, and through which object?** Status: open. Blocking: acceptance: it is the read half of the tenancy contract, and it decides whether module coordinates reach tenants. A tenant marketplace lists definitions that are not hidden. Making definitions readable by every authenticated user would hand back, through `kubectl get`, the module path, version and bound values that 0027:D1:R2 keeps off consumer-facing objects. Candidates: (a) an unbound reader role on definitions that a platform grants; (b) a separate listing projection per non-hidden definition, carrying only the merged presentation, the form layout and the kind to create, never the module coordinate or bound values. Recommended candidate: (b), at the cost of one more object kind kept in step by the definition's reconciler.

- **OQ3: What does a definition's status carry for readers without registry access?** Status: open. Blocking: acceptance: it decides whether tenants and non-portal readers (Headlamp, Backstage, an MCP server) need registry credentials and CUE evaluation. Only the presentation block and the served CRD are API-server data; the card and icon live in the registry, and a form layout needs `#config`. Candidate: the definition's reconciler writes the bound module's card, an index-sized thumbnail, the form layout with a presentation digest, and the filtered prefill into status, or into an object status references when size demands. What the prefill holds is 0027:OQ29. To settle: measure the largest real form layout first.

- **OQ7: How does an in-cluster reader fetch screenshots and READMEs from a private registry?** Status: open. Blocking: deferrable. Candidate: a read-only pull secret configured for that reader, never the operator's credentials; without it, a detail page shows the status-carried data of OQ3 only.

- **OQ16: Does the operator copy the card into a module instance's status?** Status: open. Blocking: deferrable. It would let a read-only portal show titles and icons for installed instances with no registry access, at the cost of status size on every instance.

### Card and assets

- **OQ2: Is the card's category a closed enum in core or a free label, and what is the list?** Status: open. Blocking: acceptance: the type of a required card field is contract. A closed enum groups deterministically but needs a core release per new category, and removing one bumps the card's `schemaVersion`. Experiment 02 used free labels and needed `gpu` and `observability` beyond the surveyed lists. Candidate list for an enum: `ai-ml`, `application`, `database`, `developer-tools`, `integration-delivery`, `media`, `monitoring-logging`, `networking`, `platform`, `security`, `storage`, `streaming-messaging` (Artifact Hub's eight plus four this fleet needs). `schemas/target.cue` marks the field.

- **OQ4: Is a presentation-only change a patch release, and what must the commit be?** Status: open. Blocking: deferrable. The card, assets, hints and doc comments travel inside the immutable module version, so changing any of them needs a new version: an already-published version is always refused (0011:D15). Candidate: a presentation-only change is fix-class under entry 0021's rule that a module's compatibility surface is its `#config` schema, and needs at least a patch. Under release-please it must be committed as `fix(...)`, because `docs:` and `chore:` commits never release in the module repos. No registry-side overlay; the platform's presentation (D6) is the release-free layer.

- **OQ5: What is the locale shape?** Status: open. Blocking: deferrable. `locales` is reserved and refused (D2:R4). Measured: the reservation's error, `explicit error (_|_ literal) in source`, names no field, so the gate's own wording must. Candidate: a `locales` map keyed by BCP 47 tag in the card, and a translation catalog in the zip keyed by config path. A `string | {locale: string}` union from day one would break strict readers. None of the six closest surveyed systems localises catalog content.

- **OQ6: Which badges may a UI show?** Status: open. Blocking: deferrable. Candidate: only facts derived by someone other than the author: pre-release (from the version), deprecated (the author's statement against interest), featured (the definition), signed by an identity (when entry 0023 lands), update available (admin views only). No author-declared "stable" or "verified". Input to 0021's maturity question: a marketplace needs no maturity field beyond SemVer.

- **OQ14: Does the gate assert that `summary` equals `#Module.metadata.description` when both are set?** Status: open. Blocking: deferrable. Duplication is safe only when checked, which is 0022's own rule. Asserting it costs the gate a read of the module's metadata, which needs the zip and CUE evaluation, while the rest of the card gate reads the module file alone.

- **OQ17: What may a card's images be, and how are they rendered?** Status: open. Blocking: acceptance: a module-supplied image every OPM UI renders is a security contract, and 0031:D2 names images by a path under `assets/` without saying what may sit there. This is outside the four approved layers, so it stays open. Candidate (from the portal design research 2026-10-04; awaits confirmation at acceptance): an icon is SVG or PNG and at most 64 KiB, a screenshot is PNG, JPEG or WebP, at most 512 KiB and at most four per card; publish refuses a path that names no file, a wrong format or a file over its cap, naming the path, and refuses an SVG that can run script or load anything (a script, an event attribute, a reference other than a same-document fragment, a URL-loading style, an embedded document, an external entity), naming the element; and every OPM UI renders a module-supplied image so that nothing in it executes. The SVG and inert-rendering rules also bind the index thumbnail that 0031:D7 derives from a member's icon, unless OQ15's rasterisation to PNG removes SVG from it. Measured: an `assets/icon.svg` shipped inside the published zip unchanged (`experiments/02-listing-card/`, E4a); cue v0.17.1 packs `.png` and `.svg` files unfiltered up to 500 MiB; CUE's client refuses a module manifest that does not have exactly two layers; GHCR returns 404 on the referrers endpoint. Cost: the zip is downloaded whole on every render fetch, so the candidate caps add about 2.1 MiB to a module version at worst, against real module zips of a few to tens of KiB (an estimate, not measured across the fleet). Alternatives: lower caps; icons only in the zip with screenshots left to README links; sanitising SVG at render only (one layer, which a reader that skips the step defeats). A digest-keyed fetch cache makes the cost once per version instead of once per render.

- **OQ18: Do the card's field caps count runes or bytes?** Status: open. Blocking: acceptance: the caps are the card's contract, and they decide whether every card within them passes publish. Candidate (awaits confirmation at acceptance): field caps in runes, with the separate 8 KiB size line of 0031:D2 as the only byte bound. Measured: an ASCII card at every cap is 7,099 bytes and passes, while a card at every cap in CJK text is 13,641 bytes and is refused (`schemas/examples.cue`, cue v0.17.1), so the candidate can refuse a legal card written in a non-Latin script. Alternative: restate the field caps in bytes so that every card within the caps passes the size line, at the cost of fewer characters for a non-Latin author.

### Forms and hints

- **OQ9: How does a form render a conditional field?** Status: open. Blocking: acceptance: it decides what a form can express. Waits on 0027:OQ20. The 19-module survey found cross-field rules only in comments ("required when type == pvc"). Candidate: a discriminated union renders as an arm choice with the chosen arm's fields swapped in, using `discriminator` (D4) only to break a tie; a union the served schema refuses falls back to a YAML editor for that subtree, and the CLI reports it as not form-renderable. No `visibleWhen` hint (D4).

- **OQ10: Where do hints and help text travel to a reader that has no CUE, and are they ever inside the served CRD?** Status: open. Blocking: acceptance: it decides where every non-CUE reader finds the form layout. Measured (`experiments/01-ui-hint-attributes/`, E2d): the API server's strict decoding refuses a CRD carrying `x-opm-ui`, and lenient decoding drops it silently, so a CRD cannot carry hints. Measured (`experiments/04-served-schema-boundary/`): a walker that emitted `x-opm-*` keys had its whole CRD refused. Candidate: hints and help text travel beside the schema, as a form-layout document served by whoever serves the offering (OQ3), never inside the served CRD.

- **OQ11: Is agreement between the served schema and every form a contract, and how is it checked?** Status: open. Blocking: acceptance. Waits on 0027:OQ18. Candidate: two digests. A consumer-schema digest is carried by the CRD, the CLI pre-flight and form validity alike. A presentation digest changes on presentation edits alone, which also makes D6's inertness (D6:R2) checkable from outside.

- **OQ15: Does the index builder rasterise SVG icons to PNG thumbnails?** Status: open. Blocking: implementation. It removes SVG from list views entirely at the cost of a rasteriser in the CLI. `schemas/target.cue` marks the thumbnail type.

### Secrets and bound values

- **OQ12: What may any reader of an offering, an order, an instance or a definition return at a secret path?** Status: open. Blocking: acceptance: it is a security contract every OPM UI and API must hold. Candidate: never the value. Any read, YAML view or diff returns a marker at a declared secret path, the redaction walks the schema and never trusts the client, and there is no reveal action (the read-only portal has none, and adding one would be a decision of its own). 0013's redaction rules cover kernel diagnostics; a UI's own logs, errors and views are its own responsibility. Measured (`experiments/04-served-schema-boundary/`): none of the 451 fixture dry-runs, accepted or refused, echoed a literal secret value, and the API server echoes a value only on pattern or enum failures, so a served `#Secret` value must carry neither.

- **OQ13: How are bound fields shown, and may a definition bind a secret field with anything but a reference?** Status: open. Blocking: acceptance: it decides what a definition may hold in plaintext. May move to 0027, whose 0027:OQ10 owns bound values. Candidate: a bound field is absent from the form and listed read-only on a detail page as set by the platform, a secret field without its value. A definition binding a `#Secret` field with the literal arm or any source arm is refused at acceptance, naming the field: a literal renders through the platform's literal source exactly as the named-source form would, so refusing only the literal still admits the same plaintext through a source arm. Alternative: refuse the platform's literal source by name and treat every bound source arm's `spec` as secret.

### Listing

- **OQ8: Is an index an artifact kind of its own in 0022's block, and what publish path does it take?** Status: open. Blocking: acceptance: D7:R1 needs a publish path that checks an index instead of running the module gates, which an index package cannot pass. 0022's block refuses any `kind` but `module`, `catalog` or `template`, so an index cannot carry a block today. Measured (`experiments/03-index-module/`): the index published as a plain CUE module with no block and resolved by import. Candidate: an `index` value in 0022's artifact kinds and a publish path that validates against `#ListingIndex`. `schemas/target.cue` marks the definition.
