# Risks, Drawbacks, Alternatives: Module-Dictated Catalog Versions and the Generated Platform

Risks describe what could go wrong. Drawbacks describe what definitely costs something. Alternatives describe the high-level paths not taken; per-decision detail lives in `03-decisions.md`.

## Risks and Mitigations

- **A fleet fragments across many catalog releases, and the platform cannot push a fix.** Without a platform pin, forty modules may sit on ten different releases of one catalog, each running that release's transformer bytes. A transformer fix, a CVE patch included, reaches an instance only when its module re-releases against the fixed catalog: raising the floor above the broken release stops every laggard by name (D2), it never delivers the fix. This is the Helm chart-library failure that `01-problem.md` cites against module-hosted transformers, and this entry accepts it deliberately: a loud stop is preferred to a silent re-render, and the fix lever moves from the platform team to each module owner. **Mitigation:** the floor is the platform team's stop lever, the refusal names every instance it stops, and the held versions are recorded per render (D1, OQ1), so the spread and the laggards are visible before a fix is needed. An owner-side lever short of a module re-release, such as an instance-level held version inside the range, is not designed here.
- **The readiness answer weakens.** 0015 D1's inventory and the module-less readiness build evaluate at reference versions (OQ3). A module pinned above the floor may demand a contract the inventory at the floor never listed, so "unfulfilled" and "unknown key" are exact only at those versions. **Mitigation:** the diagnostic states the reference version it evaluated at; the render build itself still holds the module's version and reports the true answer for that instance.
- **The platform team widens past the author's claim and the operator rejects the rendered CRs.** D6 allows a platform range wider than the provider's window. **Mitigation:** the widening is a warning condition on the registration naming both bounds, attributable to the platform commit and reversible by deleting the entry; the author's claim survives as the baseline.
- **Per-resolution platform generation thrashes on a churning fleet.** Every distinct resolved set is a resolved platform; a platform change or an accepted registration invalidates them. **Mitigation:** generation is keyed by the resolved set and shared across renders with the same resolution (D3); the cost is unmeasured and filed as OQ5 rather than assumed away.
- **A render with no platform and a render against one disagree on the same module.** The platform-less path admits every catalog the render pins, bounded by nothing and with no registrations; a platform refuses a pin outside its ranges and adds the provider catalogs its registrations supply. A module that renders on a laptop can therefore be refused, or render differently, on a cluster. **Mitigation:** the CLI's provenance line names the source it rendered against, and an instance render or module apply uses the cluster's Platform whenever it can read one, while a module build or vet never reads the cluster. The two paths deliberately do not share an admission step: the platform-less path has no platform team whose ranges it could apply (D3).
- **Until this entry ships, a catalog major upgrade is all at once.** Side-by-side majors (D9) exist only once resolutions are generated per module. Today a platform can carry a second major of a catalog only disabled (experiments/01-one-major-per-build/, case D), so moving to it moves every module in the same step. **Mitigation:** none inside this entry; whether that interim is acceptable is OQ17.
- **The shipped contract fold fails to evaluate on two majors that share contract keys.** The shipped `#Platform` (renamed `#ResolvedPlatform` by D3) folds every enabled entry's contracts by key, and two majors of one catalog declare the same keys, so enabling both conflicts on `catalogVersion` and `definedBy` and the whole platform value fails to evaluate (experiment 01, case A, measured 2026-09-30). That breaks core SPEC.md § 3.4's rule that no report makes the platform fail to evaluate, and it holds independently of this entry: anyone enabling two majors hits it today. **Mitigation:** under D9 no resolution holds two majors, so a generated `#ResolvedPlatform` never reaches the conflict. A collision-tolerant fold, reporting colliding keys instead of conflicting, is a separate small core fix; whether it lands ahead of this entry is OQ17.
- **The operator's build-compatibility check answers arbitrarily on a two-major platform.** At registration acceptance it indexes the platform's resolution by catalog path without the major, and keeps whichever entry map iteration visits last, so with opm@v4 and opm@v5 both present it compares a provider against either major at random (opm-operator `internal/controller/transformerregistration_buildcompat.go:98-107`, read 2026-09-30). **Mitigation:** a bug fix independent of this entry: index by the path with its major, and refuse a major mismatch only when no admitted entry shares the provider's major, which is what D7 R2 and D9 R7 require.
- **Providers release in step with every catalog major.** A provider built against opm@v4 cannot serve an opm@v5 component: its required trait carries a 4.x `catalogVersion` and plain unification refuses it (experiments/02-provider-serves-its-major/). So modules on a new major cannot use a provider contract until a provider built against that major is registered. This is already true today, where it shows up as an unrendered component rather than a named gap. **Mitigation:** D9 R4 makes the gap explicit per resolution, and a provider may serve two majors from one build if OQ9 admits it.
- **Ordering checks live outside CUE and drift from the schema.** Floor and ceiling are `#VersionType` strings; CUE cannot compare them, so `floor <= pin <= ceiling` is a kernel check the schema cannot express. **Mitigation:** the platform-level facts CUE can check are checked in CUE (shape, major matching the path, no prerelease bound without opt-in); the ordering rules are stated as contract in D2 and tested by the kernel's own fixtures.

## Drawbacks

- **The platform team loses the ceiling by default, and the additive promise does not cover the output side.** An absent ceiling admits every release of the major at or above the floor, so a module can pull transformer bytes newer than the platform validated. The additive discipline (0010 D27) protects an old module against a newer catalog's input contract; it says nothing about a newer catalog's output against the cluster it lands on: a newer Kubernetes API version, a CRD field the installed operator lacks. Provider catalogs carry an author window for exactly that (D5); static catalogs carry nothing, and whether a catalog release should declare its own output requirements is out of scope for this entry. Until then the ceiling is the only guard: a team that wants validation before admission must author one and edit it per release.
- **The provider claim gains its first authored field.** 0015 D11's "every field derived or stamped" no longer holds for the window. The trust argument moves from derivation to the RBAC gate the CR already rides.
- **Two more things to explain.** A platform operator now reads the authored platform, a registration's claim and a registration's status to know what binds a provider catalog. The status carries `source` to keep that readable, but it is three surfaces where 0015 had one.
- **`#Platform` changes meaning.** A reader of 0019, or of any library code written against it, expects the embedded catalog registry under that name and finds the authored pure-data value instead; the registry is `#ResolvedPlatform`. The cost is paid once, at alpha, and the `schemas/spec.md` section states the move; at GA the same rename would have been a major.
- **Several majors multiply the readiness question.** With two majors of one catalog admitted, the module-less build is split (D2 R7, D9 R3), so readiness and the contract inventory become per slice, and a platform can be healthy for one major and broken for another. What Ready means then is OQ11.
- **A module moves across a major whole.** D9 R6 refuses a module importing two majors of one catalog, so a large module migrates in one release or is split first. Per-component migration is OQ10.
- **0019 D6's cold path is gone.** Platform generation runs per resolution rather than per CR change. The set stays small in practice, but "generated once" is no longer a property anyone can state.

## Alternatives

- **Platform-exact with a better skew diagnostic.** Keep 0019 D13 and improve the report. **Why not:** the report cannot act; the render list is derived before it is written, and Gaps 1 and 2 stand.
- **Platform floor, module raises, maximum-version selection resolves.** The platform's pin becomes a floor and CUE's resolver picks the higher of platform and module. **Why not:** a pin below the floor is promoted silently, and 0019 D13 measured that involving the resolver is where authority fails by omission.
- **Module-exact with no platform range.** The module's pin is the version, the platform only lists majors. **Why not, for a platform:** no fleet-wide lever at all; a transformer fix waits on every module author, the Helm chart-library failure. It is, however, exactly what the CLI does for a render given no platform, and defensibly so: with no platform there is no fleet and no platform team, so there is no lever to lose. Rejecting it as the rule for platforms says nothing about that path, which stays platform-less (D3) rather than becoming a synthesized `#Platform` admitting exactly the render's pins.
- **Ranges on the authored `#CatalogEntry`, platform module kept.** **Why not:** the entry embeds an import whose version cannot float; a range on it describes nothing.
- **The catalog major in every contract key.** `opmodel.dev/catalogs/opm@v5/traits/backup@v1alpha1`. **Why not:** measured to work end to end, but every catalog major re-keys every contract, a published major needs a legacy flag to keep its keys, the publish gates change, and the owner rejected changing contract IDs. D9's alternatives keep the measurement.
- **Shared keys with the catalog major as a matching scope.** **Why not:** measured to work end to end, but it reshapes every consumer of the inventory and two operator CRD fields at once and puts provenance into matching (D9).
- **Ranges in the platform module's `cue.mod` custom block.** **Why not:** keeps the platform an authored CUE module with two authored forms, which generation removes; the block survives tidy and would work, and D2's alternatives keep it on record.
