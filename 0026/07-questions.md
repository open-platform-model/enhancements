# Open Questions: Module-Dictated Catalog Versions and the Generated Platform

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design. The validator requires this file for every entry; the `## Open Questions` block below (with or without entries) is required starting at `status: accepted`.

`OQ` numbers are permanent, never reused, never renumbered, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/`/`contracts/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves.

Each **unresolved** entry also carries a `Blocking:` field saying whether the question gates acceptance:

| Value | Meaning |
| --- | --- |
| `acceptance` | `task promote` refuses while this question is open. Give the reason inline (`Blocking: acceptance: determines config.yaml.semver`). |
| `deferrable` | May stay open at `accepted`. |
| `implementation` | Handed to delivery; the change that settles it claims it via `resolves: [OQ9]` in `delivery.yaml`. |

This is where per-question blocking rules live. They used to be prose in a separate gate document, one cross-reference away from the question they governed. On the question itself, they are visible to whoever answers it, and `task questions:open` and `task promote` can both read them.

`deferred-to-implementation` is the deferral register: an implementation-level question the design deliberately hands to whoever delivers it. Attach the context a future implementer needs (what is unclear, what evidence exists, what would settle it), but never name the inheritor. The change that picks it up claims it in this entry's `delivery.yaml` log entry (`resolves: [OQ9]`), and `task delivery:deferred` reports deferred questions no logged change has claimed. Contract-level questions cannot be deferred this way: they must be resolved before `accepted`.

While a question is open, its bullet is a working surface: edit the wording, sharpen the framing, add or drop alternatives freely. Numbers stay fixed (`schemas/target.cue` marks gated fields with `// OQN:` and decisions cite `resolves OQN`), but the prose is yours to change.

Once resolved, the bullet collapses to its question and its status. The answer now lives in the decision it points at (in `03-decisions.md`); restating it here is how this register grows into a second decision log. Collapsing happens at the `draft → accepted` compaction pass, not by hand mid-design.

## Open Questions

- **OQ1: Where does a render record the catalog versions it held, and does the exported instance carry them?** Status: open. Blocking: acceptance: it is the observability contract that makes every refusal and every "why did this render change" attributable. D1 says the record exists and is part of the render's identity. Unclear: whether it lives on the instance's status as readable `path` to version pairs, in the render digest only, or both; and whether enhancement 0014's GitOps export reproduces it. Evidence: the CLI's platform-less renders already print each catalog path and version they generated in their provenance line, a frontend-only record that reaches no instance. What would settle it: naming the field a platform operator reads to answer "which catalog release rendered this instance".

- **OQ2: Does the platform spec hold a pin or a floor for `core`?** Status: open. Blocking: acceptance: it decides D7's acceptance-time comparison target and whether a module's core pin is module-dictated like a catalog's. D1 promotes `core` from the module's tidied closure, so the build's core version follows the module. The kernel is compiled against one core major and can build nothing else, which is a structural ceiling. Candidates: no platform field, the module's core pin binds and the major mismatch is the only refusal; a required core floor beside the catalog floors; an exact core pin, keeping 0019 D13's rule for `core` alone. Evidence: the CLI's platform-less renders already take a position, holding `core` at the higher of the render's pin and the release the kernel was verified against, so the kernel's release acts as a core floor there. What would settle it: whether any provider or catalog requirement on `core` needs an acceptance-time target that is not a module's pin.

- **OQ3: Which reference version does each path use for the module-less readiness build and 0015 D1's inventory?** Status: open. Blocking: acceptance: it changes what 0015's readiness answer means once no single version exists. D2 and D4 make the static floor the reference for static catalogs. For a provider catalog the candidates are the registration's `version` or the effective ceiling. A module above the floor may demand a contract the inventory at the floor does not list, so the readiness answer is exact only at the reference versions. What would settle it: a decision that the readiness answer is "at the floors and the registration versions" and says so in its diagnostic.

- **OQ4: Which refusals happen at platform acceptance and which at render, given that version ordering lives in the kernel and not in CUE?** Status: open. Blocking: deferrable. `floor <= ceiling`, an entry's major matching its path, and D6's excluded-`version` refusal are platform-level facts checkable before any render, as is a prerelease bound without opt-in, which CUE checks. Pin-in-range and D7's shared-path check need a module. Unclear: whether a platform that fails its own checks is refused wholesale or per entry, and how the offline CLI reports a platform-level failure with no cluster to write a condition to.

- **OQ5: What is the blast radius and caching identity of per-resolution platform generation on a real fleet?** Status: open. Blocking: implementation. D3 keys generation by the resolved catalog set, the authored platform's generation and the accepted registrations. Unmeasured: how many distinct resolutions a fleet produces, how a platform change or a registration change invalidates them, and what the cold and warm generation costs are against 0019 D6's once-per-CR baseline. What would settle it: a measurement over the workspace module fleet's committed pins.

- **OQ6: Is the `registry` override on an admission entry needed, and how does it compose with the trust policy of enhancement 0023?** Status: open. Blocking: deferrable. The workspace routes every OPM path through one registry mapping, and identity is the path (0010 D1), so an entry naming an OCI repository is an override of where a path resolves, never a second identity. Unclear: whether any platform needs a per-path override that the process-level mapping cannot express, and whether 0023's trusted-signer statement should be the place that binds a path to a repository instead.
- **OQ7: Does the registration window need a `prereleases` flag?** Status: open. Blocking: deferrable. D2 gives an admission entry a prerelease opt-in; D5's registration window (`floor`, `ceiling` defaulting to `version`) has none. A provider module pinning a prerelease of its own catalog already puts that prerelease in the registration's `version`, so the default window is a prerelease whether or not anyone opted in. Unclear: whether a consumer pinning a prerelease of a provider catalog inside the author's window should be admitted by ordering alone, refused unless the platform's admission entry opts in, or governed by a flag on the window. What would settle it: whether any provider module is expected to ship against a prerelease catalog in production.

- **OQ8: Does a render given no platform survive this design as a generated `#Platform` that admits exactly what the render pins, or stay a platform-less path?** Status: resolved-by-D3. Settled as option B, a platform-less path stated as such: a render takes a module and, optionally, an authored `#Platform`; with none, the kernel generates the resolved platform from the render's pins alone, every pinned catalog is held, and D2's admission does not run. D3 R1 and R3 are narrowed to renders given a platform and D3 R5 states the platform-less path; the answer lives in D3 in 03-decisions.md. The question decided whether D3 R1 ("a render takes an authored platform and a module") and R3 hold for every render or only for renders given a platform, and whether the refusal vocabulary of D2 applies on the laptop. Today the CLI renders with no `--platform` and no cluster Platform used against a platform it generates from the render's own committed pins (a module's `cue.mod` for module build, vet and apply; the instance package's for instance build, vet, diff and apply): one enabled entry per `opmodel.dev/catalogs/*` dependency at its pin, closed over the catalogs' own requirements, `core` floored at the kernel's verified release, content-hash cached, no admission, no registrations. There is no local default platform. Verified against cli 1.0.0-alpha.24. Under either option a render with no platform admits every catalog it pins and carries no registrations, so it can pass where a cluster's platform would refuse (see 05-risks).
  - **Option A: a generated `#Platform` admitting exactly the pins.** The frontend or kernel synthesizes a `#Platform` with one `#CatalogAdmission` per pinned catalog, floor and ceiling both at the pin and prereleases on when the pin is one, and renders through the same admission and generation as any platform. One kernel path and one refusal vocabulary for every render. The cost: an admission that can never refuse is ceremony, the value is called authored while nobody authored it, and it bends D3 R1's wording rather than its substance.
  - **Option B: a platform-less path, stated as such.** A render takes a module and, optionally, an authored platform; with none, the resolved platform is generated from the render's pins alone, every pinned catalog is held, and D2's admission does not run. D3 R1 and R3 are narrowed to renders given a platform. The cost: two input shapes at the kernel boundary.
  - **Recommendation: B.** With no platform there is no platform team whose authority an admission expresses, so a synthesized admission records nothing true. B states what the CLI already does and keeps `#Platform` meaning "what a platform team wrote". What would settle it: an owner's call on whether the kernel's input contract names the no-platform case explicitly (B) or hides it behind a synthesized value (A).

- **OQ9: How does resolution know which major of its declaring catalog a provider serves, and does a provider build that imports two majors enter both resolutions?** Status: open. Blocking: acceptance: D9 R4 selects providers by that major and cannot be delivered without a source for it. D9 says a resolution includes a provider only when it was built against the major the resolution holds; experiment 02 shows why (a provider built on opm@v4 is refused by a v5 component at plain unification). Candidates for the source: the provider catalog's own dependency list on the declaring catalog, which 0015 D11 already reads to derive the registration's `version` and D7 already compares; or a value stated on the registration. A second case is open under either: a provider build that depends on both opm@v4 and opm@v5 and ships one transformer per major. That shape was measured routable, each transformer matching only its own major's components, but only under the designs D9 rejects: module-qualified keys in core and through a real render (`experiments/03-module-qualified-keys/`, L1; `experiments/08-render-module-qualified-keys/`), the major as a key segment (`experiments/04-major-segment-keys/`, P2), and shared keys scoped by major (`experiments/05-major-as-matching-scope/`, s6). Under D9's shared keys it has not been measured. Unclear: whether it enters both resolutions, and whether the other major's contract values it carries as dependency bytes count as the build holding two majors under D9 R2 and under D7's shared-path check, which refuses a different major unconditionally. **Recommendation:** derive the major from the provider's dependency list, the same derived-and-verified posture 0015 D11 takes for `version`; no strong recommendation on the two-major build, which turns on how D9 R2 and D7 read a requirement on a major the resolution does not hold.

- **OQ10: Is migration across a catalog major per module, or may one module move component by component?** Status: open. Blocking: acceptance: D9 R6 refuses a module importing two majors of one catalog, and a per-component answer would replace that requirement. Per module is D9's rule: a module on opm@v4 and a module on opm@v5 coexist, and a module moves whole, so a large module either migrates in one release or is split first. Per component would let one module carry opm@v4 components and opm@v5 components during a migration. Per-component routing was measured working through a real render, but only under the two designs D9 rejects, which change contract keys (`experiments/08-render-module-qualified-keys/`, the split module) or scope matching per major (`experiments/09-render-major-as-matching-scope/`, the mixed module), the second of which D8 excludes. Under module-qualified keys the same render showed that a component mixing majors silently drops an optional attachment from the other major rather than refusing (experiment 08, the mixed module). **Recommendation:** per module, as D9 states. It keeps one major per resolution with no matching change; the per-component evidence came only from the two designs D9 rejects.

- **OQ11: How is the module-less readiness and inventory build split when several majors are admitted, what does Platform Ready mean when one slice is broken, and what does `opm platform check` report?** Status: open. Blocking: acceptance: D2 R7 and D9 R3 require the split but do not name it, and 0015's readiness answer changes meaning with it (see OQ3). Options for the split: one build per admitted major of a multi-major catalog, every other catalog at its floor, which is linear in the number of majors; or one build per consistent combination of admitted majors across catalogs, which is exact but multiplies when two catalogs each have two majors. The per-major option has a hole the combination does not: a catalog at its floor may itself depend on one major of another catalog, and then fails D7's shared-path check in the other major's slice. For readiness: Ready only when every slice evaluates and routes, or Ready per slice with the broken major named. **Recommendation:** none yet on the split; on readiness, name the failing slice rather than hide it, since D9's point is that one major can be broken or draining while another serves.

- **OQ12: Where is over-subscription reported at platform level once the one-provider count is taken per resolution?** Status: open. Blocking: acceptance: 0015 D18 makes over-subscription the report that refuses platform-package generation, and D9 R5 moves the count to each resolution. Candidates: in the authored platform's inventory with each provider paired to the major it serves; per slice of the module-less build (OQ11); or only per resolution at render, with registration acceptance (D9 R7) as the early refusal. Experiment 02 shows that counting across every provider regardless of major reports a false over-subscription for k8up@v2 on opm@v4 beside k8up@v3 on opm@v5. **Recommendation:** refuse early at registration acceptance per declaring major (D9 R7) and report per slice of the module-less build, so the platform-level report and the per-resolution count agree.

- **OQ13: Does operator registration acceptance learn a provider's declaring major from the registered build's dependencies, or from a value declared on the registration?** Status: open. Blocking: acceptance: a declared value changes the registration CRD's shape and adds an authored field beside D5's window. D9 R7 makes acceptance compare providers per declaring major, for contract conflicts and for the shared-path comparison. Deriving it matches 0015 D11, where `catalog`, `version` and `provides` are derived from the provider module and verified at acceptance; declaring it is readable without the provider catalog in hand but is a claim to verify anyway. Independently of the answer, the operator's shared-path check today indexes the platform's resolution by base path with the last entry winning, so it answers arbitrarily on any platform carrying two majors of one catalog (see `05-risks.md`). **Recommendation:** derive, following OQ9's answer.

- **OQ14: Must a provider's own major upgrade run side by side, or does it stay an atomic swap?** Status: open. Blocking: deferrable. Example: k8up@v3 and k8up@v4 both built against opm@v5, so both serve the same declaring major. D9 R5 still refuses them as two providers of one contract on one resolution, so replacing k8up@v3 with k8up@v4 is one registration swap, as under 0010 D37. The pair was measured over-subscribed under every alternative key design (`experiments/03-module-qualified-keys/` L6, `experiments/04-major-segment-keys/` P4, `experiments/05-major-as-matching-scope/` s4); under shared keys it is the single-provider rule itself. Running both would need something to choose between them per module, which is provider routing, 0015 D2's successor material and outside this entry (D8). **Recommendation:** keep the atomic swap. A module demands the contract, not the provider, so it has no pin that could select a provider major.

- **OQ15: May a new catalog major ship a bridge transformer that consumes the previous major's contracts?** Status: open. Blocking: deferrable. The use would be to keep rendering modules still on opm@v4 after the opm@v4 catalog is retired. Under D9 a module pinned to opm@v4 gets a resolution holding opm@v4 only, so a bridge shipped in opm@v5 never reaches it; admitting it would mean a resolution holding a major the module did not pin, against D1. A bridge beside the major it bridges matches the same components twice, measured through real renders as two objects of one name: with shared keys on the shipped library and core, and with the major as a key segment, the render gate passing both times (`experiments/07-render-shipped-core/`); and with the major as a matching scope, where the patched glue flags the double match but the kernel still returns both objects (`experiments/09-render-major-as-matching-scope/`). **Recommendation:** no bridges in this entry; retire a major only after draining it (OQ16).

- **OQ16: How does a platform operator see that a major is drained before disabling it?** Status: open. Blocking: deferrable. Disabling the opm@v4 entry refuses every instance still pinned to it (D2), so an operator needs a count of instances holding opm@v4 first. D1 R3 records the catalog versions each render held; where that record lives is OQ1. Unclear: whether a per-instance record is enough, or whether the platform should report, per admitted entry, how many instances hold it, and whether the CLI can answer the same question offline. **Recommendation:** answer OQ1 first; if the held versions reach instance status, the drain count is a query over it and needs no new field.

- **OQ17: Does the collision-tolerant contract fold land ahead of this entry as a separate core fix, and is an all-at-once catalog major upgrade acceptable until this entry ships?** Status: open. Blocking: deferrable. Today a platform enabling two majors of one catalog that share contract keys fails to evaluate (experiment 01, case A), which violates core SPEC.md § 3.4's rule that no report makes the platform fail to evaluate. That is a core defect whether or not this entry ships. A fold that folds only keys with exactly one definer and reports the rest as collisions, with `routable` false while any exist, was measured to evaluate with two and three majors sharing keys inside a copy of core's `#Platform`, leaving a one-major platform unchanged (`experiments/06-collision-tolerant-fold/`). Until this entry ships, side-by-side majors are impossible and a major upgrade moves every module at once. **Recommendation:** land the fold as its own core fix, and the operator's last-entry-wins index fix as its own operator fix, both independent of this entry; accept the all-at-once upgrade in the interim.

- **OQ18: What happens when a render given no platform comes from a module importing two majors of one catalog?** Status: open. Blocking: acceptance: D3 R5 holds every catalog the render pins, which for two majors of one catalog is the build experiment 01 case A shows cannot evaluate. The platform-less path (D3) runs no admission, but D9 R2 still bounds its resolved platform to one major per catalog. The answer follows OQ10: under per-module migration the render is refused by name exactly as D9 R6 refuses it on a platform, instead of failing inside the fold; under per-component migration it would need the same matching change. Today the CLI's platform-less generation writes one enabled entry per pinned catalog, so such a module would reach the fold with both majors. **Recommendation:** the same refusal as D9 R6, by name.
