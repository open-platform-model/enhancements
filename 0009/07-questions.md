# Open Questions: Operational Primitives: Op, Action, Lifecycle, Workflow

## Open Questions

Each entry carries a `Status:` line; close with `resolved-by-D##`, `deferred-to-NNNN`, or `answered`.

- **OQ1: What form do cataloged op artifacts take, WASM, OCI image, or both?** Status: open. Blocking: acceptance, because it gates the executor backend set and the `@op(...)` attribute's `protocol`/`ref` schema. Recommendation on the table: support both, selected per-op by `protocol`. WASM would default for pure-logic ops (http, cue.eval, wait-evaluation); OCI/container would serve inherently side-effecting ops (exec, build, k8s apply), with the operator's container backend rendering a Job rather than running locally. Resolving it requires choosing the wasm host and the OCI execution contract. Note: OPM's wasm backend would run op artifacts at **runtime**, in the frontend that registered it, which is a side effect. That is distinct from CUE's own **evaluation-time** WASM `@extern` functions, which are pure and currently flagged experimental. Do not conflate the two (see `research/cue-attribute-longevity.md`).

- **OQ2: Do steps pass typed data to each other, or is `dependsOn` ordering the only inter-step relation?** Status: open. Blocking: deferrable. Typed `out → in` wiring (hof.io's data-DAG elegance) is feasible but heavier to build and specify than ordering-only. D3 bounds the answer: the run state is the caller's and MUST survive serialisation, so whatever a step hands its successor is data that round-trips through a custom resource, never a live value or an open handle. `schemas/target.cue` currently reserves a hidden `#out` and an explicit `dependsOn` without committing to data references.

- **OQ3: What is the run-state / idempotency model for `#Workflow` (and how does it differ from `#Lifecycle`)?** Status: open. Blocking: deferrable. `#Lifecycle` is tractable inside the operator reconcile loop: re-plan each reconcile, lean on convergent executors (k8s apply) plus completion records for run-once steps. On-demand `#Workflow` invocation is harder: it may be non-idempotent, may need run history, re-entrancy guarantees, and a place to store invocation state. This needs its own design pass.

- **OQ4: Where do `#Lifecycle` and `#Workflow` attach on `#Module`: module root, per-component, or both?** Status: resolved-by-D10. Module root, as module traits on a 0025 aspect; no per-component attachment.

- **OQ5: Is the meta-controller toolkit in scope, and when?** Status: open (likely deferred). The same primitives + execution half could let authors stand up Kubernetes meta-controllers quickly (PoC operators): an operator becomes "a reconcile loop + an executor registry." Treated as a north-star the architecture should not preclude, not a v1 deliverable; may split to a follow-up enhancement.

- **OQ6: How far does cancellation reach inside a single advance, and how is a cancelled step recorded?** Status: partial. Blocking: deferrable. D9 makes cancellation inside a stage this entry's (checks at a kernel verb's entry and between its stages may land standalone), and D3 answers the larger half of it: the caller owns the loop, so cancelling between steps is the caller not calling advance again, and no mechanism is owed for it. What is left is cancellation inside one advance. Measured limit: CUE's loader replaces the caller's context with a placeholder before any registry fetch, so passing a context down the kernel's load path changes nothing by itself. The only seam is the registry interface the load configuration accepts, whose methods all take a context; an adapter that supplies the caller's context there makes every fetch cancellable. A running CUE evaluation has no cancellation hook at all. Resolving the remainder needs the executor design (D4) to state whether a step abandoned mid-action is a failure or a distinct outcome, and what the state value carries for it so the next advance can tell.

- **OQ7: Does this entry's in-module step ordering survive the owner's intent that nothing orders within a module?** Status: open. Blocking: acceptance (the conflict reaches D2, D3 and D7, the core of the execution half, and OQ2). The owner parked this entry until hooks are wanted, and recorded in the Kubernetes-tier entry [0012](../0012/03-decisions.md) that no ordering within a module is planned: the library applies every resource in kind-class order and Kubernetes' eventual consistency settles the rest, and ordering across modules belongs to a future Bundle definition, in the order the bundle lists its modules. This entry orders steps inside a module: a step's ordering edges name sibling steps (D2 R5), steps within a lifecycle phase run in the order authored (D7), the planner decides which steps are eligible and in what order (D3), and OQ2 weighs `dependsOn` edges between steps. A refresh owes an answer: whether lifecycle steps are a sanctioned exception (an order of operations, not of resources), move up to the Bundle level, or go. Deletion is not reopened by it: the deletion plan and its caller-held state belong to entry 0012 and carry no hook semantics, as 0012:OQ10 records. A refresh also owes the half of 0012:OQ10 the owner deferred here on 2026-10-03: whether this entry's `#Op` vocabulary for k8s get/apply is expressed as the Kubernetes tier's action set or beside it. Entry 0012 already has the frontend perform those Ops, so the question is one of vocabulary, not of who acts.
