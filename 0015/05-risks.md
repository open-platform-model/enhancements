# Risks, Drawbacks, Alternatives — Catalog Contracts, Provider Classes, and Transformer Registration

## Risks and Mitigations

- **Reproducibility regression: a local render stops matching the cluster's.** D3 puts accepted claims in cluster state, and 0010 D14 deleted subscription resolution precisely so a render is reproducible from a commit. Blast radius is wide and quiet: `opm module render` and the operator disagree with no error on either side, and 0014's GitOps export produces a platform that does not reproduce the render it exported. **Mitigation:** OQ3 is a blocking gate for `draft → accepted`, so the entry cannot be accepted with this unanswered. Whatever the answer, `Platform.status.registry` carries the effective set explicitly rather than leaving it implicit in the reconciler, so the divergence is at worst *visible*.

- **Cluster-wide re-render on every registration change.** The store key moves from the Platform CR's `.metadata.generation` to a digest over the accepted-claim set, so installing, upgrading or removing any provider invalidates the materialized platform and moves every ModuleInstance's render digest. On a cluster with hundreds of instances, one `kubectl apply` of a provider becomes a fleet-wide reconcile. **Mitigation:** OQ6 owns the measurement. The floor is that this is no worse than editing the Platform CR today, which has the same effect — what changes is how often it happens, because provider upgrades are more frequent than platform edits.

- **A class vocabulary that drifts from what is installed.** The platform publishes `archive → velero`; the Velero registration is deleted; components carrying `class: "archive"` now match nothing, and the failure appears at render on whichever instance reconciles first. **Mitigation:** the contract inventory makes this a platform-level condition — a class with no active implementation is `unroutable`, reported on `Platform` status and by `opm platform check` before any render. The deletion finalizer additionally refuses to remove a registration while instances depend on it.

- **The default class makes a routing decision invisibly.** A module that names no class silently gets whatever the platform defaults to, and a platform team changing the default re-routes every such module at once with no diff in any module. This is StorageClass's known failure mode, inherited wholesale. **Mitigation:** the resolved class is recorded in the render output's provenance, so "which engine backed this up" is answerable after the fact; and changing a default is a Platform edit, which is reviewable source under GitOps. Not fully mitigated — an accepted cost of the pattern.

- **RBAC gate assumed rather than verified.** D3 rests on a tenant ServiceAccount not carrying create on a cluster-scoped resource. If any deployment path applies module resources with the controller's own identity instead of an impersonated one, the gate is absent and any module author can register a transformer — a privilege escalation, not a bug. **Mitigation:** `04-graduation.md` requires an envtest covering both arms rather than a manifest review, and `opm-operator/docs/TENANCY.md`'s `--default-service-account` lockdown is the existing control being relied on.

- **Contract maps and adapter demands disagree.** D1 lists a contract in `#traits` while a transformer's `requiredTraits` carries what may be a different value for the same key. **Mitigation:** this one is nearly free — CUE unifies the two occurrences, so a disagreement is a build failure in the catalog rather than a runtime skew. It is a risk only for a catalog published outside `opm catalog publish`, which is the same exposure 0010 D35 already documents.

- **D2's premise fails: classes turn out to need matcher changes after all.** The whole argument for classes over a guard is that 0010 D36's `matchLabels` carries them with `compile/match.go` untouched. If the default-fill (OQ2) cannot be done outside the matcher, the cost calculus changes and the guard becomes competitive again. **Mitigation:** OQ2 is a gate for acceptance, and `04-graduation.md` makes "match.go:344-379 unchanged, verified by diff" an implementation criterion rather than an aspiration.

## Drawbacks

- **A new CRD, with a new lifecycle to operate.** `TransformerRegistration` adds claim states, a health dependency on a ModulePackage, and a finalizer that can block deletion. Every one of those is an operator-facing concept that did not exist, and a stuck finalizer is a support call.
- **The catalog artifact grows.** Every contract is now serialized twice — once as a member, once inside each adapter that demands it. Mechanical and harmless, but catalog pulls get larger and materialize does more work per build.
- **Two registration paths to reason about.** "Where did this transformer come from?" now has two answers. `Platform.status.registry` unifies them for reading, but a platform team debugging a match still has two places to look.
- **Amending an accepted decision in another entry.** D2 changes 0010 D37, which means 0010 stops being readable in isolation. Cheap now because 0010 is `accepted` and `not-started`; it is still a cross-entry edge that has to be maintained on both sides.
- **Classes are a vocabulary someone must design.** StorageClass's ergonomics depend on the class names being meaningful. OPM supplies the mechanism and no naming guidance, and a cluster with `class: "class1"` gets none of the benefit.

## Alternatives

- **Do nothing beyond 0010.** Keep `fulfilment: "provider"` with the exactly-one rule and no contract maps. **Why not:** D37's zero case is undetectable, so the design's central shape has a failure mode it cannot report, and the two-engine topology stays unexpressible.
- **Solve registration at authoring time only** — a provider catalog ships a `#Platform` fragment, a CLI command splices it into the platform file, GitOps applies it. **Why not:** preserves the lockfile completely and is genuinely attractive, but cannot express "not until the provider's CRDs exist", which is the ordering half of Gap 2. Kept as an ergonomic layer over D3 rather than instead of it.
- **A guard instead of classes** — refuse two comparable providers, loudly. **Why not:** it makes the motivating topology a diagnosable error rather than a supported state, and the author's requirement is to run two backup engines, not to be told clearly that they cannot.
- **Capability-based routing instead of classes** — the module states RPO and retention, the platform routes to whatever satisfies it. **Why not:** strictly better and strictly larger; classes degenerate to it, so building classes first costs nothing that capability routing would have to undo.
- **Push routing into the module** — let a component name the catalog that should serve it. **Why not:** a module that can name k8up has stopped consuming a contract and started depending on an implementation, which forfeits the reason contracts exist.
