# Risks, Drawbacks, Alternatives — Catalog Contracts and Transformer Registration

## Risks and Mitigations

- **Reproducibility regression: a local render stops matching the cluster's.** D3 puts accepted claims in cluster state, and 0010 D14 deleted subscription resolution precisely so a render is reproducible from a commit. Blast radius is wide and quiet: `opm module build` and the operator disagree with no error on either side, and 0014's GitOps export produces a platform that does not reproduce the render it exported. **Mitigation:** resolved by D6 — `opm platform pull` fetches the operator-generated platform package (the exact bytes cluster renders consume, identity per OQ8), so a local build against the pulled package reproduces the cluster's render; `Platform.status.registry` carries the effective set explicitly, so the divergence is visible and closable on demand, never silent.

- **Cluster-wide re-render on every registration change.** Under 0019 there is no materialized platform to invalidate (D8 deleted the held slot) — instead every accepted, upgraded or revoked claim regenerates the platform package every render build consumes (0019 D6), which moves every ModuleInstance's render digest just the same. On a cluster with hundreds of instances, one `kubectl apply` of a provider becomes a fleet-wide reconcile. **Mitigation:** OQ8 owns the measurement (it inherited this from OQ6). The floor is that this is no worse than editing the Platform CR today, which has the same effect — what changes is how often it happens, because provider upgrades are more frequent than platform edits.

- **RBAC gate assumed rather than verified.** D3 rests on a tenant ServiceAccount not carrying create on a cluster-scoped resource. If any deployment path applies module resources with the controller's own identity instead of an impersonated one, the gate is absent and any module author can register a transformer — a privilege escalation, not a bug. **Mitigation:** the acceptance criteria require an envtest covering both arms rather than a manifest review, and `opm-operator/docs/TENANCY.md`'s `--default-service-account` lockdown is the existing control being relied on.

- **Contract maps and adapter demands disagree.** D1 lists a contract in `#traits` while a transformer's `requiredTraits` carries what may be a different value for the same key. **Mitigation:** this one is nearly free — CUE unifies the two occurrences, so a disagreement is a build failure in the catalog rather than a runtime skew. It is a risk only for a catalog published outside `opm catalog publish`, which is the same exposure 0010 D35 already documents.

- **Provider skew between operator CRDs and catalog transformers.** D10's two-artifact rule gives up the atomic lockstep a single co-located artifact would have had: "module 1.2.0 deploys the k8up operator's CRDs while registering catalog 1.3.0's transformers" is expressible. **Mitigation:** D11 makes the skew explicit and attributable rather than ambient — the registration pins the exact catalog version the module's `cue.mod` resolved, so the pairing is visible in the module's diff and in the CR; lockstep versioning in the provider's CI (`06-operational.md`) closes the rest. The residual risk is a provider that deliberately pins mismatched versions, which is loud in review.

- **Registration activation deadlocks on its own package.** Under D9 the CR is among the ModulePackage's own rendered resources, and activation gates on that package being Ready — a readiness aggregation that counts the registration's acceptance would wait on itself forever. **Mitigation:** resolved by D14 — the registration CR is excluded by kind from its package's readiness at the wait-set aggregation (the kstatus layer that would otherwise hold it InProgress on its own conditions), and the envtest obligation extends to this case (a provider module must reach active with no manual intervention).

- **An active registration can outlive its provider's health.** Activation latches (D3): a provider that goes NotReady after activation — or whose CRDs are removed by hand while it is down — keeps its claim active, so renders keep targeting its contracts. **Mitigation:** deliberate. Deactivating on health regression would regenerate the platform package without the provider catalog and fail every dependent render for the duration of a transient condition, which is strictly worse. Established CRDs outlive provider restarts and rendered output waits level-triggered; hand-deleted CRDs fail loudly at apply naming the object; true removal goes through deletion, where the finalizer names the dependents.

- **D5's guard turns out to need a matcher change after all.** The guard's premise is that comparable-predicate detection is a platform-assembly assertion, never a rung change in the match glue. If OQ9's detection cannot be expressed outside the glue's matching semantics, the design needs re-deciding rather than shipping. **Mitigation:** the site is fixed at platform-package generation (D5, resolving OQ10), OQ9's deferral hands the slice a measured candidate validated against the shipped bucket, and the delivery criteria make "the match glue unchanged, verified by diff" an implementation criterion rather than an aspiration.

## Drawbacks

- **A new CRD, with a new lifecycle to operate.** `TransformerRegistration` adds claim states, a health dependency on a ModulePackage, and a finalizer that can block deletion. Every one of those is an operator-facing concept that did not exist, and a stuck finalizer is a support call.
- **The catalog artifact grows.** Every contract is now serialized twice — once as a member, once inside each adapter that demands it. Mechanical and harmless, but catalog pulls get larger and the platform value carries more bytes per build.
- **Two registration paths to reason about.** "Where did this transformer come from?" now has two answers. `Platform.status.registry` unifies them for reading, but a platform team debugging a match still has two places to look.
- **One engine per contract per cluster.** The deliberate cost of D2's revision: a platform with two legitimate reasons to back up differently runs the second engine outside OPM until the successor routing entry exists. Named here so the trade is visible, not discovered.
- **Provider artifacts depend on catalog_opm, on both sides.** The provider module imports it for D9's registration primitive (and in practice already does, for the primitives that deploy the provider); the provider catalog imports it for the contract values its required maps carry — a requirement is a value, not a bare FQN key, so implementing a base-catalog contract means depending on the base catalog. Independence holds between providers, never toward the defining catalog. Named so the dependency is chosen, not accidental: D8's comparison covers it as a shared path, and 0019 D13's promotion resolves it to the platform's version in-build.
- **Two published artifacts per provider.** D10's lockstep flow means a provider repo runs a sequenced dual publish (catalog before module) instead of one release. The 0011 pipeline makes the second artifact mechanical, but it is CI surface every provider maintains.

## Alternatives

- **Do nothing beyond 0010.** Keep `fulfilment: "provider"` with the exactly-one rule and no contract maps. **Why not:** D37's zero case is undetectable, so the design's central shape has a failure mode it cannot report.
- **Solve registration at authoring time only** — a provider catalog ships a `#Platform` fragment, a CLI command splices it into the platform file, GitOps applies it. **Why not:** preserves the lockfile completely and is genuinely attractive, but cannot express "not until the provider's CRDs exist", which is the ordering half of Gap 2. Kept as an ergonomic layer over D3 rather than instead of it.
- **Provider classes** — the platform publishes a routing vocabulary per contract and two providers coexist, routed by label. **Why not:** adopted 2026-08-05 and rejected 2026-08-20 (D2, as revised): an operator-facing vocabulary to design and operate, StorageClass's invisible-default failure mode, and a default-fill design of its own, all ahead of any real two-engine requirement. Preserved in D2's alternatives as the successor entry's leading candidate.
- **Capability-based routing** — the module states RPO and retention, the platform routes to whatever satisfies it. **Why not:** strictly larger than classes; successor-entry material, like all provider routing (D2).
- **Push routing into the module** — let a component name the catalog that should serve it. **Why not:** a module that can name k8up has stopped consuming a contract and started depending on an implementation, which forfeits the reason contracts exist.
- **Let providers ship transformers inside their module artifact** — a `module`+`package`+`version` claim resolving any CUE package that evaluates to `#Catalog`, buying single-artifact providers and atomic CRD/renderer lockstep. **Why not:** the member publish gates run only at `opm catalog publish`, so module-hosted transformers are the ungated back door until `opm module publish` learns to run them; deferred additively in D10's alternatives rather than foreclosed.
- **Registration as a `#Trait` on the provider's workload component.** **Why not:** `appliesTo` has no honest answer and the binding it would express is instance-level, not component-level — `providerRef` names the ModulePackage. Recorded in D9's alternatives; revisit only if per-component provider health-gating becomes real.
