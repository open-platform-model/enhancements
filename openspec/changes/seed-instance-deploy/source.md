## Disagreements between spec and code

The code wins in each.

- `mod-apply` says the command accepts directory inputs only. The code also accepts a published module path with a version selector. The requirement states the code.
- `mod-apply` "Failures surface validation errors before any cluster contact" says the instance is synthesized before any connection. The code builds the cluster client first, because the platform is read from the cluster during the render; only a published module is resolved before the cluster is contacted. Not seeded: the resolution order is held by `published-module-resolution`, and the exit code of a refused render by `cli-kernel-render`.
- `deploy` "Create-namespace creates the namespace only after every check passed" says a failed namespace read stops the apply "before any other call to the cluster". The code reads the cluster Platform during the render, before the apply workflow starts its namespace read (`internal/cmd/instance/apply.go`, `internal/workflow/apply/apply.go` `namespaceToCreate`). The requirement says only that the failed read makes no further call.
- `deploy` and `mod-apply` describe the record with history-bearing fields (`createdBy`, instance and module metadata, a change descriptor with path and local flag). The code writes the module path and version, the values, the inventory with a revision and digests, and the local-source mark. No module directory path is recorded.
- `deploy` "CLI mutating workflows refuse controller-managed instances" and "Legacy CLI-managed instances remain mutable" use the retired `createdBy` mark. The owner field replaced it; `instance-ownership` holds the behaviour.
- The legacy tables of `deploy` (the exit-code table 1 usage, 2 render, 3 Kubernetes; the command syntax blocks without the wait, version and delete-data options) are out of date. The exit codes in `spec.md` are the per-case codes the requirements of `deploy` and the code give.

## Left out

- The kind-class order of apply and delete (FR-D-003, FR-D-022, the weight order in "Apply stages CustomResourceDefinitions and Namespaces before the rest", the order scenario of "follows the shared deletion plan"): the converted 0012 `object-ordering` states it. The two stages are kept: 0012 leaves an engine's own staging open.
- That a CRD or Namespace is never deleted, that an object OPM does not own, that belongs to another instance or is adopted elsewhere is skipped, and that a frontend deletes only what the plan names and releases the hold only on a release verdict: the converted 0012 `deletion-protocol` states them. This seed states only what the user sees (listing, exit code, closing line) and the failure cases the entry does not state.
- Labels on every resource (FR-D-060 to FR-D-066): 0012 `inventory-identity` "Labels are stamped by the CUE render" and `instance-identity`.
- The stale set, prune, no-prune, the empty-render guard, kept stale claims, the let-go warnings, the ownership refusals, the unreadable record, apply and delete of an operator-owned instance: `instance-ownership`.
- The CRD presence, field floor, version ceiling and status access checks, their order and the dry run skipping them, and that a namespace is created only after the last check: `apply-preflight-gates`.
- Operator install, uninstall and their deletes: `operator-lifecycle` and the converted 0021.
- Platform choice for a render: `platform-resolution`. The version selector grammar and its report: `published-module-resolution`. Render failures and warnings: `cli-kernel-render`. The instance identity formula: `instance-identity`.
- The skip switch for unprovided demands and its record annotation: repo-only behaviour, ruled out of the seeds (DECISIONS.md 2026-10-11 12:30).
- Kubeconfig, context and namespace selection (flag, environment, configuration file), and the exit code 3 when the cluster client cannot be built (FR-D-051 to FR-D-053): no seed holds the configuration capability. Listed for the owner.
- Mechanism rows: FR-D-001 (pipeline call), FR-D-002 (server-side apply with force), FR-D-050 (client rate limiting), FR-D-009 (field-conflict warning), NFR-D-001 and SC-D-003 (idempotence, covered by the up-to-date scenario), SC-D-001.
- Consolidation T4.3c (DECISIONS.md 2026-10-11 14:45 and 15:00): `instance-ownership` holds what an operator-owned delete hands to the finalizer and the outcome the CLI reports ("Operator-owned delete hands cleanup to the finalizer", "Delete reports the outcome that occurred"). Its claim rules for the apply-side prune ("A stale claim is kept by default", "The prune deletes only the object it read") do not cover `instance delete`, so the delete-side requirements stay here: the operator-managed prompt, the precondition and Foreground propagation of each delete, and the kept claims of a delete.
