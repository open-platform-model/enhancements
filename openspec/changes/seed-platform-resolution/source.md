# Source note: seed-platform-resolution

Capability: `platform-resolution`. Full seed (23 requirements, 51 scenarios; 22 and 53 before the consolidation pass T4.3c). Written 2026-10-11 from `cli` at commit `09b0b81`. The text is rewritten at intent level: no Go symbol, flag, field path or file path in a requirement. The behaviour is stated as it ships after enhancement 0021 (owner ruling, DECISIONS.md 2026-10-11 11:20): the one place 0021 changed it is "Operator install renders against its own pins", cut to its source rule (see "Left out"). A later entry modifies a requirement here if it must.

## Disagreements between spec and code

The code wins.

- **The two registry warnings.** The spec says resolution warns in two cases (status behind the spec, Ready condition False) with no condition. The code raises both only when it generates from a recorded registry (`resolve.go:333-345`). With no recorded registry it generates from the spec and raises neither. The seed states the code's rule, with a closing sentence.
- **Where an unpublished pin fails.** The spec says a bad pin, a key-to-import mismatch or an unpublished build fails "at acquisition". For a platform generated from the cluster or from pins, an unpublished pin fails earlier, when the dependency closure is derived, naming the module path and version (`generate.go:76-81`, `moduledeps.go:88-93`). A key-to-import mismatch fails at the kernel's acquisition. The seed says "before any instance is rendered" for both.
- **"The local default".** The scenario "Same failure surface for every source" lists "the local default". No local default platform exists (the spec's own first requirement says so, and no code reads one). The seed lists the three sources that exist.
- **The hint for a provider-fulfilled demand.** The spec scenario says the hint names the platform option. The code gives the kernel-render hint first when a demand is one no provider supplies (`validation.go:120-122`); that hint also names the platform option. The deps hint applies to the other unresolved demands (`validation.go:130-132`). The seed says so in its last sentence and leaves the kernel-render hint to `cli-kernel-render`.
- **Platform check names its sources.** The spec says the refusal names "all three". The code's message names the directory argument, the option and the context flag of the cluster (`check.go:154`). The seed says "the argument, the option and the cluster".

## Where this capability touches the other seeds

- `platform-pull`: its "Pull follows the registry the operator recorded" holds the same rule as "The recorded registry wins over the spec" and "A stale or refused Platform warns, still renders" here, and its scenarios "A recorded entry with no enabled flag is disabled" and "A hand-edited status is refused" are the same as two scenarios here. Both go through one resolver (`check.go` and `pull.go` call the same `Resolve`). The ruling of DECISIONS.md 2026-10-11 11:20 gives the rule to this seed. The consolidation pass should keep it here and let the pull seed point to it.
- `platform-module-generation`: holds the generator (pure, sorted, core pinned at the kernel's verified release, the closure from published module files, the registry union, the stamped version). This seed states which inputs the CLI hands the generator and one deps rule the generator does not hold: core at the higher of the render's pin and the verified release. The words "the closure of those pins over the published module files" repeat one clause of "The dependency closure comes from published module files"; cut that clause here if the reviewer judges it one rule.
- `single-build-render`: holds the render's own dependency promotion, the opt-in for local replacements and the skew comparison. This seed holds only how a deps platform is generated and which skew policy it gets (none).
- `cli-kernel-render`: holds the hint for a demand no provider supplies and the re-pin hint for an old-core platform. This seed adds the deps-source hints.
- `platform-contract-gates`: holds the check's report (first line names the platform and how it was chosen) and "A directory that is not a platform module is refused as not found". The shape rule "A named platform must be a platform module" here is general (flag and argument, every command) and overlaps its second sentence. Keep the general one here.
- `platform-artifact`: holds the kernel's refusal of a package that is no platform and of an incomplete entry. This seed holds only that every source goes through one acquisition.
- `published-module-resolution`: a different object (a published module's version, development build = prerelease with the identifier `dev`). The catalog version rule here defines a development build by a numeric first prerelease identifier (`catalog.go:69-75`); the module rule uses the identifier `dev` (`internal/publish/compat.go:197-208`). Each is true to its own code, and the two rules stay apart; the scenarios here give a version of the numeric shape. Whether to keep both definitions or name them apart is the owner's question (review T4.R27).
- `operator-lifecycle` (a seed in parallel, not read): the cli spec of that name holds "Catalog resolution precedes every cluster write", "Platform flags are validated before any lookup" and "Platform seeding and the opt-in user role stay install steps". The three requirements here about the catalog version and the seeding ("A catalog version is resolved from the registry", "Resolution refuses rather than guesses a version", "Operator install seeds the Platform, no render does") may repeat it. The source spec of this capability states them, so they stay here; the consolidation pass T4.3c made this seed the holder of the catalog version resolution.
- `registration-acceptance`, `transformer-registration`, `platform-reconciliation`: the operator side of the Platform status the CLI reads. This seed states only what the CLI reads.

## Left out

- Behaviour a live entry states as a requirement (ruling DECISIONS.md 2026-10-11 13:30, rule by rule): the converted 0021 holds "Install leaves an existing Platform alone" and "Install does not depend on the cluster Platform" (`operator-install-module`). The never-overwrite clauses of "Only operator install seeds the cluster Platform" (the already-exists case treated as success, no server-side apply or update) are left out for the first. "Operator install renders against its own pins" keeps only the source rule (no cluster read, no platform directory, the reported source). Its Platform-independence sentence and scenario are left out for the second; see "For the owner at 0021's accept".
- The skew policy a cluster Platform or the config selects: `config-types` ("Skew policy configuration key") holds it. Only the deps source rule (no skew policy) is here.
- The exit code of each resolution failure (general, validation, connectivity, not found, permission): per-command mapping in `check.go`, `pull.go`, `env.go`. Only the refusals the spec states with an exit code are stated, with the code the spec names.
- An instance package under no CUE module is refused with a validation error when no platform option is given (`internal/workflow/render/render.go:61-65, 166-168`, `errNoModuleRoot`; code only). It is a rule about the instance, not about the platform. It belongs with the instance render seeds.
- Names of the reserved generated module paths (`opmodel.dev/platforms/cluster@v0`, `opmodel.dev/platforms/module-deps@v0`): a mechanism. The seed says "the reserved cluster platform path".
- The warning texts and the progress lines: wording, not a rule.
- The legacy files: `opm config vet` and `opm config init` still know the old platform file and directory (`internal/config/platform.go:34-47`); nothing reads them. This is the config seeds' business.
- Plan and history references in the spec (cli issue 229, 0006 D11/D17/D21/D22/D39, 0015 D6, 0019 D5/D6, 0021 D11:R10).

## For the owner at 0021's accept

Detail that this seed held and removed, because the converted 0021 states the rule coarsely (`operator-install-module`, "Install does not depend on the cluster Platform": the same objects whether or not the cluster holds a Platform, whatever it says). The detail is not in 0021's text. The owner decides whether 0021 takes it.

- A Platform that is missing, not Ready or unreadable does not refuse operator install's render (cli spec "Operator install renders against the operator module's own pins", fourth sentence).
- Scenario "A stalled Platform does not block repair": the cluster's Platform is Stalled and install runs; the render succeeds from the module's pins and install goes on to its checks.
- The reason in the cli spec: repairing the operator never depends on the Platform it serves (0021:D11:R10).
- Code: operator install sets the deps-only render, so neither a platform directory nor the cluster is consulted (`internal/cmd/operator/install.go:297-318`, `internal/workflow/render/module.go:132-137`).

## Consolidation (T4.3c, 2026-10-11)

One rule lives in one seed (DECISIONS.md 2026-10-11 10:00). What this seed gave up, and where each rule now lives:

- The new requirement "The seeded subscription uses the same resolution" holds the rule that operator install uses the catalog version resolution for the seeded Platform's subscription, over the CLI's default catalog in its current major, with nothing inferred from a neighbouring version, and the two install scenarios (moved in from `operator-lifecycle`'s requirement "The seeded subscription pins one catalog build"). It is a separate requirement because adding the sentence to "A catalog version is resolved from the registry" passed 500 characters. The seed has 23 requirements, 22 before.
- "Operator install seeds the Platform, no render does" is renamed "No render seeds a Platform" and keeps the render-side rule. Seeding the Platform at install (create when absent, report the catalog path and version, a denied create degrades to a warning) is `operator-lifecycle`'s "Platform seeding follows the rollout".
- "Deps become one catalog entry each, core floored": the dependency closure over the published module files is `platform-module-generation`'s ("The dependency closure comes from published module files"); the scenario "A catalog's own dependency is present" is gone. "A cluster Platform is generated like the operator's": the scenario "A subscribed catalog is generated" is gone; the generation of the module is `platform-module-generation`'s.
