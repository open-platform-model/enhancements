# Notes for the owner at accept

The first two points are clashes in the old requirement lines: the first between two lines of 0014, the second between a line of 0014 and the lines that moved in from 0013. The conversion is faithful, so it does not rewrite them. The third point is a sentence that the conversion added. The old entry did not hold any of the three as an open question, so none is in the proposal. The owner decides the wording of the requirements at accept.

- **A bare version in the live instance.** "The exported module version keeps its v prefix" (old 0014:D1:R5) says the exported version carries its `v` prefix. "Completed fields are named in the output" (old 0014:D1:R6) says a render-bearing field, the module coordinate among them, is copied unchanged and never altered. When the live instance carries a bare version, such as `2.1.0`, the two lines disagree: adding the prefix alters the field, and copying it leaves the prefix out. The comment in `evidence/contracts/contracts.cue` (lines 170 to 172) records this case from enhancement 0006: a bare version made a CLI-written instance unresolvable by the controller. The scenarios do not say which form the live object holds.
- **The values warning against the encrypted secret paths.** "Every export that writes values warns" (old 0014:D3:R2) says OPM cannot identify which values are secret. "Exported secret values are encrypted" (moved in from 0013) puts no plaintext secret value in the export, and "Secret-bearing export output can be SOPS-encrypted" (moved in from 0013) encrypts that output on request. For those paths the warning is untrue.
- **A sentence the conversion added.** The last sentence of "Exported values are copied byte for byte" ("Where a path is marked secret, the requirement that exported secret values are encrypted governs that value.") is in no old requirement line. The supervisor kept it at the conversion and flagged it for the owner. It bears on the previous point. The owner decides at accept whether it stays.
