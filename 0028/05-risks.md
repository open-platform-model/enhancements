# Risks, Drawbacks, Alternatives: The Operator Ships as an OPM Module

Risks describe what could go wrong. Drawbacks describe what definitely costs something. Alternatives describe the high-level paths not taken; per-decision detail lives in `03-decisions.md`.

## Risks and Mitigations

Ranked by blast radius.

- **A CRD change deletes or strands every instance.** An upgrade or a downgrade applies CRDs whose stored versions or schemas differ from what the cluster holds. A CRD delete would remove every ModuleInstance in the cluster. **Mitigation:** neither frontend deletes a CRD in an instance's inventory (0012:D1:R3), and D9 keeps that for upgrade and uninstall. Install refuses a module whose CRDs stop serving a version the cluster serves, even when a downgrade was asked for, and refuses an unasked downgrade (D10:R2, R3).
- **Install applies whatever the registry serves.** A version tag does not pin content: GHCR has no tag-immutability control (0011:D10), and experiment 01's local registry accepted a re-push of the same module version. Without an anchor, install would apply, with cluster-admin rights, whatever the registry or a mirror serves under the tag, where today it applies a manifest compiled into the CLI. The module is not the only input: its core, catalog and Kubernetes schema dependencies resolve from the same registry or mirror by version, CUE modules carry no checksum of their dependencies, and the catalog's transformers decide which RBAC the render grants. **Mitigation:** the module names the operator image by digest in its source (D1:R10), and the CLI pins its default module version with the content digests of the module and of every module its render resolves, and refuses when any of them differs (D1:R17). A version other than the default, and its dependencies, are trusted as served, its image still by digest, and install says so (D1:R18); verifying a signature instead is OQ7.
- **The first module install refuses, or recreates more than it must.** Every operator on a cluster today was installed from a manifest whose objects carry no OPM identity, so the apply guard of 0012:D8 treats them as foreign. A migration that recreates the CRDs would delete every instance. Experiment 02 measured both failure halves with the catalog-path module D2 now requires: the apply refused at the first foreign object, and once adoption was emulated the Deployment could not be taken over because its selector changed, leaving three old bindings unrecorded. **Mitigation:** install adopts exactly the objects it can prove came from an earlier operator release (D8:R8), deletes and recreates only the Deployment, deletes only the three superseded bindings (D8:R6, R7), and changes nothing another instance records (D8:R10); the CRDs, custom resources and Namespace are never deleted (D8:R2). D3:R12 makes a refused migration change nothing, and D8:R13 holds every delete to the same proof as an adoption. The install-driven migration is not yet measured end to end (04-graduation.md).
- **A migration stops after the Deployment is deleted.** The annotations and deletes come after every check, but the instance apply that follows can still fail, for example on an API error or a lost connection, and the controller then has no Deployment. **Mitigation:** D8:R11 keeps every write after the last refusing check, and D8:R12 makes re-running install complete the migration from wherever it stopped, which needs nothing from the operator (D4:R2).
- **A refused install leaves the CRDs half-migrated.** Experiment 02's CRD step relabelled the four CRDs to the new instance before the instance apply refused the rest. **Mitigation:** D3 runs every refusing check before the CRD step and D3:R12 requires a refused install to change nothing.
- **Deleting the operator's instance strands every operator-managed instance.** `opm instance delete` of the operator's instance went past an armed cleanup finalizer in experiment 02; the managed instance kept its finalizer, and its later delete wedged until install was re-run. **Mitigation:** D9:R5 puts the uninstall guard on every CLI delete path of the operator's instance; re-running install restores the operator, which then finishes the pending cleanups (measured).
- **A hand edit makes the operator own itself.** No frontend today stops `kubectl` from setting the operator's own instance to `owner: operator`. Experiment 02 measured all three outcomes: with the shipped RBAC the operator arms a finalizer on its own instance and fails; with broad rights it adopts itself seamlessly and the CLI can no longer take the instance back; deleting it with `spec.prune: true` then prunes the operator mid-cleanup and wedges the record until the finalizer is stripped by hand. **Mitigation:** D4 keeps the instance CLI-owned, D4:R1 makes the operator apply, prune and finalize nothing for it whatever its owner field says, and D4:R3 keeps every CLI command from handing it to the operator; any future ownership-transfer design must refuse it as well. Where the operator does not yet hold D4:R1, the only recovery is removing the finalizer by hand and re-running install.
- **Install reports success before the operator works.** After an upgrade in experiment 02, the CLI's wait reported the instance healthy about 30 s before the new operator's controllers started, and the first reconcile in that window failed with `PlatformNotReady`. **Mitigation:** D3:R10 waits for the cluster Platform to report Ready from the installed release.
- **CLI commands lose track of the operator.** The CLI's readiness check, which the per-instance delete guard uses, finds the operator through the manifest the CLI embeds today. Without that manifest the guard would never find a module-installed operator and would refuse. **Mitigation:** D3:R13 makes the operator's instance record the locator; D3:R18 fixes its name and namespace; D3:R15 finds an operator with no record, applied with kubectl or GitOps, by the fixed names every install path keeps.
- **An upgrade cannot render because the cluster Platform is unhealthy.** If install renders the operator module against the cluster Platform, a broken or mis-subscribed Platform blocks the one command meant to repair the cluster. **Mitigation:** install always renders the operator module against its own dependency pins, never the cluster Platform (D11). Where the render succeeds but the Platform never reports Ready, install keeps what it applied and names the Platform in its error (D3:R17). Experiment 02 measured the coupling D11 removes: once a Platform existed, the reinstall rendered through it, and the result matched only because both named the same catalog release.
- **A newer module needs a newer kernel than the CLI has.** A user selects a module version whose core or catalog pins the CLI's kernel cannot render, or whose operator the CLI then refuses to drive (0021:D9). **Mitigation:** each CLI release defaults to a module version it was tested with, and install refuses a module whose operator `MAJOR.MINOR` is above the CLI's, naming the CLI upgrade (D10:R1). A module whose pins the CLI's kernel cannot render fails at render, before anything changes (D3:R12).
- **Deleting the instance record with kubectl orphans the operator silently.** A CLI-owned instance carries no finalizer, so `kubectl delete` removes the record and leaves every object running with no record of them. **Mitigation:** the objects keep the instance's identity labels, so re-running install records them again without a refusal (D3:R3). Until then CLI commands still find the operator by its fixed names (D3:R15), and uninstall refuses and points at install instead of deleting nothing silently (D9:R6).
- **An operator release that no module release follows.** The image is published, but nothing the CLI can pin deploys it. **Mitigation:** D7 makes a module release follow every operator release; the CLI keeps installing the previous module version, which names an older image by digest, so nothing breaks while the follow-up is missing. A module release is never re-pointed (0021:D10), so a re-run of a partly failed module release must treat an already-published identical version as done (OQ11).
- **Names the module derives differ from the manifest's.** The CLI, its end-to-end tests, the demo repository and the documentation name the operator's Namespace, Deployment and CRDs. Every name derives from the instance's name and namespace, so an instance under another name renders another operator. **Mitigation:** D2:R10 keeps every name except the bindings', which nothing reads, and D3:R18 fixes the instance's name and namespace; experiment 01 reproduced 16 of 19 names on the catalog path, the other three being the bindings.
- **The operator loses its Pod Security posture.** The catalog's security context has no seccomp field, so a catalog-rendered controller fails the `restricted` profile the manifest's pods meet (experiment 01). **Mitigation:** D12:R1 adds the seccomp profile to the catalog before the module's first release, and D2:R8 requires the posture.
- **The catalog prerequisites slip.** The module cannot ship on the catalog path until a catalog release carries D12's two changes. **Mitigation:** both are small and additive; the role change keeps every role with subjects rendering as before (D12:R3).
- **A Deployment-selector change in a later catalog release.** The catalog derives the selector; a catalog release that changed what it derives would make the next module upgrade fail as immutable. **Mitigation:** D2:R11 requires every module version to render the same selector, so a module release that adopts such a catalog release is refused before it ships.
- **A future CRD the catalog cannot carry.** The catalog's CRD resource has no `conversion` or `preserveUnknownFields`. The module embeds each generated CRD spec whole, so such a field refuses the release's render instead of being dropped (experiment 01, negative check), but the release is then blocked until the catalog grows the field. **Mitigation:** D2:R1 and R3 make the failure loud; the catalog change has to land before the operator ships a multi-version CRD (06-operational.md).

## Drawbacks

- **Install needs a module registry.** The embedded manifest installed with no network. Every install, the CRDs-only form included, now resolves the module and its core and catalog dependencies from a registry or a mirror. A learner on a laptop with no network can no longer install OPM's CRDs.
- **Install is heavier.** The CLI resolves dependencies and renders a module with large CRDs instead of applying static bytes. Measured: 5.7 s and about 500 MB peak memory with a cold cache, 2 to 4 s warm (experiment 01). On a fresh cluster the whole install took the same time as today's within noise, because readiness dominates (experiment 02).
- **An air-gapped install needs every upstream mirrored.** The module mirror must serve the operator module, core and the catalog from GHCR and the Kubernetes schemas the module depends on from `registry.cue.works` (`cue.dev/x/k8s.io`, experiment 01's `cue.mod/module.cue`); the operator image comes through an image mirror the nodes are configured with or the image repository value of D5. Experiment 02 ran separate pull-through mirrors for GHCR and `registry.cue.works` and a node-level image mirror on a host whose cluster had no egress.
- **The migration recreates the operator's Deployment and renames its bindings.** The catalog path changes the Deployment's selector and the bindings' names, so the first module install deletes and recreates the controller's Deployment and deletes three bindings (D8). The controller does not reconcile until the new pod serves; nothing it manages changes. Users who apply the release manifest with kubectl meet the same break once, and need the same delete. The owner accepted this as a declared beta break.
- **Authoring the module surfaced opaque catalog errors.** A CPU limit written as a whole-number string, an unset optional service-account field, a missing restart policy or update strategy, and an empty-dir volume without an explicit read-only flag each failed the render with only "N errors in empty disjunction" (experiment 01). The operator module is written around them, but every module author meets them; they are catalog follow-ups (D12).
- **Another release unit.** The operator's repository releases two units, and every operator release is followed by a module release before the CLI can pin it (D7). Every core or catalog release the module adopts produces a module release and then a CLI pin bump, but no longer an operator release.
- **Nobody corrects drift on the operator.** The operator's own instance is CLI-owned (D4), so an edit to the operator's Deployment stays until the next install. This was true of the manifest as well; the entry does not improve it.

## Alternatives

- **The operator manages its own instance after a bootstrap, as Flux and Argo CD do.** **Why not:** a broken self-managed operator has no outer layer to repair it, and its own deletion wedges on a finalizer only it can clear (D4).
- **Write the controller's workload and RBAC as raw objects in the manifest's shape.** **Why not:** it kept every name and the selector, so the migration recreated nothing, but OPM's own controller would not exercise the catalog's workload abstractions; the owner chose the showcase (D2).
- **Release the module at the operator's version.** **Why not:** the image digest did not exist when the module was committed, every catalog adoption forced an operator release, and the module's bump rule fought the tooling train's shared `MAJOR.MINOR`; the owner chose a train of its own (D1).
- **Embed the module tree in the CLI for offline installs.** **Why not:** a vendored module renders through a local replacement, which marks it as local bytes, and it brings back the copy-and-sync plumbing the entry removes (D3).
- **Keep the install manifest as the CLI's artifact and publish the module only for GitOps users.** **Why not:** two install shapes that can drift, and the CLI would still not install OPM's controller with OPM (D3).
- **A separate CRD bundle artifact beside the module.** **Why not:** a second artifact per release that must agree with the first, for no gain on uninstall, since CRDs are never deleted anyway (D3).
