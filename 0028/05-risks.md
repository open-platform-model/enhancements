# Risks, Drawbacks, Alternatives: The Operator Ships as an OPM Module

Risks describe what could go wrong. Drawbacks describe what definitely costs something. Alternatives describe the high-level paths not taken; per-decision detail lives in `03-decisions.md`.

## Risks and Mitigations

Ranked by blast radius.

- **A CRD change deletes or strands every instance.** An upgrade or a downgrade applies CRDs whose stored versions or schemas differ from what the cluster holds. A CRD delete would remove every ModuleInstance in the cluster. **Mitigation:** neither frontend deletes a CRD in an instance's inventory (0012:D1:R3), and D9 keeps that for upgrade and uninstall. A served-version check before applying CRDs is OQ6.
- **Install applies whatever the registry serves.** A version tag does not pin content: GHCR has no tag-immutability control (0011:D10), experiment 01's local registry accepted a re-push, and 0029:OQ9 measured an overwritten module tag being re-rendered silently. Without an anchor, install would apply, with cluster-admin rights, whatever the registry or a mirror serves under the tag, where today it applies a manifest compiled into the CLI. **Mitigation:** the release's install manifest names the image by digest, and the CLI's default module version is checked against the module content and image the release published (D1:R6, R7). A version other than the default is trusted as served, and install says so (D1:R8); verifying a signature instead is OQ7.
- **The first module install refuses or recreates a running operator.** Every operator on a cluster today was installed from a manifest whose objects carry no OPM identity, so the apply guard of 0012:D8 treats them as foreign. A migration that recreates the CRDs would delete every instance. Experiment 02 measured both failure halves: the apply refused at the first foreign object, and once adoption was emulated a catalog-path module could not take over the Deployment because its selector changed, leaving three old bindings unrecorded. **Mitigation:** D8 requires adoption with no recreation; D2:R5 and R7 keep the names and the selector that make it possible, and D3:R12 makes a refused migration change nothing. Who sets the adopt annotation is OQ3. The migration with D2's module shape is not yet measured end to end (04-graduation.md).
- **A refused install leaves the CRDs half-migrated.** Experiment 02's CRD step relabelled the four CRDs to the new instance before the instance apply refused the rest. **Mitigation:** D3 runs every refusing check before the CRD step and D3:R12 requires a refused install to change nothing.
- **Deleting the operator's instance strands every operator-managed instance.** `opm instance delete` of the operator's instance went past an armed cleanup finalizer in experiment 02; the managed instance kept its finalizer, and its later delete wedged until install was re-run. **Mitigation:** D9:R5 puts the uninstall guard on every CLI delete path of the operator's instance; re-running install restores the operator, which then finishes the pending cleanups (measured).
- **A hand edit makes the operator own itself.** No frontend today stops `kubectl` from setting the operator's own instance to `owner: operator`. Experiment 02 measured all three outcomes: with the shipped RBAC the operator arms a finalizer on its own instance and fails; with broad rights it adopts itself seamlessly and the CLI can no longer take the instance back; deleting it with `spec.prune: true` then prunes the operator mid-cleanup and wedges the record until the finalizer is stripped by hand. **Mitigation:** D4 keeps the instance CLI-owned, D4:R1 makes the operator apply, prune and finalize nothing for it whatever its owner field says, and entry 0029 refuses the transfer at the CLI and in the operator. Until 0029's operator refusal ships, the only recovery is removing the finalizer by hand and re-running install.
- **Install reports success before the operator works.** After an upgrade in experiment 02, the CLI's wait reported the instance healthy about 30 s before the new operator's controllers started, and the first reconcile in that window failed with `PlatformNotReady`. **Mitigation:** D3:R10 waits for the cluster Platform to report Ready from the installed release.
- **CLI commands lose track of the operator.** The CLI's readiness check, which the per-instance delete guard uses, finds the operator through the manifest the CLI embeds today. Without that manifest the guard would never find a module-installed operator and would refuse, or a future transfer gate would. **Mitigation:** D3:R13 makes the operator's instance record the locator; D3:R11 fixes its name and namespace; D3:R15 finds an operator with no record, applied with kubectl or GitOps, by the fixed names every install path keeps.
- **An upgrade cannot render because the cluster Platform is unhealthy.** If install renders the operator module against the cluster Platform, a broken or mis-subscribed Platform blocks the one command meant to repair the cluster. **Mitigation:** OQ5 decides which platform install renders against; D4 makes install the recovery path, which argues for the module's own pins. Where the render succeeds but the Platform never reports Ready, install keeps what it applied and names the Platform in its error (D3:R17). Experiment 02 measured the coupling: once a Platform existed, the reinstall rendered through it, and the result matched only because both named the same catalog release.
- **A newer module needs a newer kernel than the CLI has.** A user selects a module version whose core or catalog pins the CLI's kernel cannot render, or whose operator the CLI then refuses to drive (0021:D9). **Mitigation:** each CLI release defaults to a module version it was tested with; OQ4 decides whether install refuses a newer one.
- **Deleting the instance record with kubectl orphans the operator silently.** A CLI-owned instance carries no finalizer, so `kubectl delete` removes the record and leaves every object running with no record of them. **Mitigation:** the objects keep the instance's identity labels, so re-running install records them again without a refusal (D3:R3). Until then CLI commands still find the operator by its fixed names (D3:R15), and uninstall refuses and points at install instead of deleting nothing silently (D9:R6).
- **A partial release publishes the image but not the module, or the module twice.** **Mitigation:** D1:R1 makes the release public only after the module is published; registry versions are never re-pointed (0021:D10), so a re-run must treat an already-published identical version as done (OQ11).
- **Names the module derives differ from the manifest's.** The CLI, its end-to-end tests, the demo repository and the documentation name the operator's Namespace, Deployment and CRDs. Every name derives from the instance's name and namespace, so an instance under another name renders another operator. **Mitigation:** D2:R5 keeps every name and D3:R11 fixes the instance's name and namespace; experiment 01 reproduced all 19 names with the manifest-shaped variant.
- **The operator loses its Pod Security posture.** The catalog's security context has no seccomp field, so a catalog-rendered controller fails the `restricted` profile the manifest's pods meet (experiment 01). **Mitigation:** D2:R8.
- **A future CRD the catalog cannot carry.** The catalog's CRD resource has no `conversion` or `preserveUnknownFields`. The module embeds each generated CRD spec whole, so such a field refuses the release's render instead of being dropped (experiment 01, negative check), but the release is then blocked until the catalog grows the field. **Mitigation:** D2:R1 and R3 make the failure loud; the catalog change has to land before the operator ships a multi-version CRD (OQ6).

## Drawbacks

- **Install needs a module registry.** The embedded manifest installed with no network. Every install, the CRDs-only form included, now resolves the module and its core and catalog dependencies from a registry or a mirror. A learner on a laptop with no network can no longer install OPM's CRDs.
- **Install is heavier.** The CLI resolves dependencies and renders a module with large CRDs instead of applying static bytes. Measured: 5.7 s and about 500 MB peak memory with a cold cache, 2 to 4 s warm (experiment 01). On a fresh cluster the whole install took the same time as today's within noise, because readiness dominates (experiment 02).
- **An air-gapped install needs every upstream mirrored.** The module mirror must serve the operator module, core and the catalog from GHCR and the Kubernetes schemas the module depends on from `registry.cue.works` (`cue.dev/x/k8s.io`, experiment 01's `cue.mod/module.cue`); the operator image comes through an image mirror the nodes are configured with or the image repository value of D5. Experiment 02 ran separate pull-through mirrors for GHCR and `registry.cue.works` and a node-level image mirror on a host whose cluster had no egress.
- **The operator's module does not exercise the catalog's workload abstractions.** D2 writes the controller's workload and RBAC in the manifest's shape, so OPM's own controller is a module of generated CRDs, a Namespace and hand-shaped objects. The dogfooding covers the registry, the version pin, typed values, render and inventory, not the workload blueprints. OQ12 asks when that can change.
- **Authoring the module surfaced opaque catalog errors.** A CPU limit written as a string, an unset optional service-account field, a missing restart policy or update strategy, and an empty-dir volume without an explicit read-only flag each failed the render with only "N errors in empty disjunction" (experiment 01). The manifest-shaped objects avoid most of these, but every module author meets them.
- **More releases.** Every core or catalog release the module adopts produces an operator release and then a CLI pin bump (D7).
- **Nobody corrects drift on the operator.** The operator's own instance is CLI-owned (D4), so an edit to the operator's Deployment stays until the next install. This was true of the manifest as well; the entry does not improve it.

## Alternatives

- **The operator manages its own instance after a bootstrap, as Flux and Argo CD do.** **Why not:** a broken self-managed operator has no outer layer to repair it, and its own deletion wedges on a finalizer only it can clear (D4).
- **Embed the module tree in the CLI for offline installs.** **Why not:** a vendored module renders through a local replacement, which marks it as local bytes, and it brings back the copy-and-sync plumbing the entry removes (D3).
- **Keep the install manifest as the CLI's artifact and publish the module only for GitOps users.** **Why not:** two install shapes that can drift, and the CLI would still not install OPM's controller with OPM (D3).
- **A separate CRD bundle artifact beside the module.** **Why not:** a second artifact per release that must agree with the first, for no gain on uninstall, since CRDs are never deleted anyway (D3).
