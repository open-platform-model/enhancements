# Open Questions: The Operator Ships as an OPM Module

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design. The validator requires this file for every entry; the `## Open Questions` block below (with or without entries) is required starting at `status: accepted`.

`OQ` numbers are permanent, never reused, never renumbered, like `DN` and `DN:Rn`, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/`/`contracts/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves.

Each **unresolved** entry also carries a `Blocking:` field saying whether the question gates acceptance:

| Value | Meaning |
| --- | --- |
| `acceptance` | `task promote` refuses while this question is open. Give the reason inline (`Blocking: acceptance: determines config.yaml.semver`). |
| `deferrable` | May stay open at `accepted`. |
| `implementation` | Handed to delivery; the change that settles it claims it via `resolves: [OQ9]` in `delivery.yaml`. |

Once resolved, the bullet collapses to its question and its status. The answer lives in the decision it points at (in `03-decisions.md`).

## Open Questions

### Evidence the experiments owe

- **OQ1: Can the module render the operator's whole install shape, names included?** Status: open. Blocking: acceptance: D2 rests on it. The module must render all 19 objects of the release manifest (four CRDs, the Namespace, the ServiceAccount, seven ClusterRoles, two ClusterRoleBindings, the leader-election Role and RoleBinding, the metrics Service and the Deployment) through the first-party catalog, with the names D2:R5 keeps. Known constraints: the catalog's role resource requires at least one subject, so the five unbound ClusterRoles need the `objects` resource; idiomatic workload resources derive names from the instance and component names, so keeping `opm-operator-controller-manager` needs either matching names or an explicit resource name. Also unknown: whether the CRD and RBAC import can be compared against the controller's generators mechanically (D2:R1, R2), and whether the render fits the CLI's and the kernel's memory on a typical workstation. [`experiments/01-operator-module-render/`](experiments/01-operator-module-render/) resolves it.
- **OQ2: Does the two-step install work on a cluster with no OPM objects?** Status: open. Blocking: acceptance: D3 and D8 rest on it. The experiment must show: the CRD subset of the render applies and is served; the CLI-owned instance then applies, rendered against a platform generated from the module's own pins because no Platform exists yet; the CRDs from step one are recorded in the inventory without the apply guard refusing them (D3:R3, R8); cluster-scoped objects (CRDs, ClusterRoles, ClusterRoleBindings) are recorded and handled by the CLI's inventory like namespaced ones; and a second run changes nothing (D3:R9). It should also run the migration of D8 over an operator installed from the current release manifest, recording object UIDs before and after. [`experiments/02-cli-bootstrap-install/`](experiments/02-cli-bootstrap-install/) resolves it.

### Contract questions

- **OQ3: Who sets the adopt annotation when install migrates a manifest-installed operator?** Status: open. Blocking: acceptance: decides D8's contract and how it reads against 0012:D8:R3. Every object of an earlier release manifest is foreign to the new instance under 0012:D8, and the only override is a per-object adopt annotation naming the adopting instance. Options: (a) the user annotates each object, with install printing the exact commands; (b) install annotates exactly the objects it can prove belong to an earlier operator release (by name and the operator's own labels), which 0012:D8:R3 may read as a second override and would then need an amendment of 0012:D8; (c) a one-off migration subcommand that does (b) only when the user runs it. Experiment 02 measures whether the guard sees these objects as foreign at all, since the adopt annotation is not implemented in either frontend when this question was written (read from the CLI and library on 2026-10-04: no adopt key exists).
- **OQ4: Does install refuse an operator version newer than the CLI?** Status: open. Blocking: acceptance: it is a refusal rule a user observes. The CLI refuses to drive an operator whose `MAJOR.MINOR` is above its own (0021:D9), but it learns the operator's version from the Platform only after the operator runs. A user who installs a newer module version than the CLI can then use none of the CLI's apply commands. Options: install refuses a module version whose `MAJOR.MINOR` is above the CLI's; install warns; install allows it, as selecting a newer manifest does today. A related case: a newer module may pin a core or catalog the CLI's kernel cannot render.
- **OQ5: Which platform does install render the operator module against?** Status: open. Blocking: acceptance: it decides whether an upgrade depends on the cluster Platform being healthy. The CLI renders against the cluster Platform when one exists and against a platform generated from the module's own pins otherwise. On a first install there is no Platform; on every later install there is, and its catalog subscription may lack what the module needs, or the Platform may be the reason the operator is being repaired. Rendering the operator module always against its own pins makes install independent of the Platform; rendering against the cluster Platform keeps one rule for every instance. D4 says install is the recovery path, which argues for the former.
- **OQ6: What does a downgrade do?** Status: open. Blocking: deferrable. Installing an older module version applies older CRDs over newer ones. A CRD that drops a stored version or narrows a schema can leave existing custom resources unreadable. Options: refuse a module version whose CRDs drop a version the cluster serves; warn; allow. The same check would guard an upgrade whose CRDs remove a served version (prior art: the CRD upgrade-safety preflight of OLM v1).
- **OQ7: Is the module's signing D1:R4's own rule or entry 0023's?** Status: open. Blocking: deferrable. D1:R4 asks the release to sign and attest the module like the image. Entry 0023 designs provenance and signatures for OPM artifacts as OCI referrers. If 0023 is accepted first, D1:R4 should depend on its decisions instead of stating a rule of its own; if not, the image's existing signing path is the interim answer.
- **OQ8: Does the module offer an opt-in applier identity?** Status: open. Blocking: deferrable. The operator applies instances as its own service account unless a default service account is set (D5), and its own role grants no workload rights, so a fresh install reconciles nothing until a platform team grants an applier. The module could offer an opt-in service account bound to a named role. That is a cluster-wide grant decision that belongs with entry 0029's applier-identity gate; until it is decided the module renders no applier.
- **OQ9: What is this entry's semver impact?** Status: open. Blocking: acceptance: determines `config.yaml.semver`. Install and the CRDs-only form now need a module registry, where the embedded manifest worked offline; selecting another version takes a module version instead of a release tag; uninstall deletes from the cluster's record instead of the CLI's list. On the CLI's beta line (0021:D7) a break is allowed as a declared change with a migration note; whether this entry is `major` or `minor` depends on how OQ3 and OQ4 settle.

### Implementation questions

- **OQ10: How does install take values from the user?** Status: open. Blocking: implementation. D5 makes the operator's tuning a set of instance values. Whether install takes a values file, typed options for the common fields, or both, is the CLI's to decide; the contract is D5:R1 to R3.
- **OQ11: How does the release produce the module's identity version?** Status: open. Blocking: implementation. The module version must equal the release version (D1:R1). The first-party catalog and the module fleet advance their identity file in the release pull request with the CLI's version command, and forbid a second writer to that file; the operator's release has no such step yet. The implementing change decides the step and proves that a re-run of a partly failed release does not republish a version.
