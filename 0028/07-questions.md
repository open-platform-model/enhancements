# Open Questions: The Operator Ships as an OPM Module

**This file is the single canonical location for Open Questions.** An `## Open Questions` block anywhere else in the entry fails `task vet`. This is the entry's working question register: track unresolved questions surfaced during design. The validator requires this file for every entry; the `## Open Questions` block below (with or without entries) is required starting at `status: accepted`.

`OQ` numbers are permanent, never reused, never renumbered, like `DN` and `DN:Rn`, because decisions (`**Resolves:** OQ4`), `// OQN:` markers in `schemas/`/`contracts/` CUE, and delivery-log entries in `delivery.yaml` (`resolves: [OQ9]`) cite them. A vacated number keeps a one-line tombstone.

Each entry carries a `Status:` line; close it with `resolved-by-D##`, `deferred-to-NNNN`, `deferred-to-implementation`, or `answered` when the question resolves.

Each **unresolved** entry also carries a `Blocking:` field saying whether the question gates acceptance:

| Value | Meaning |
| --- | --- |
| `acceptance` | `task promote` refuses while this question is open. Give the reason inline (`Blocking: acceptance: determines config.yaml.semver`). |
| `deferrable` | May stay open at `accepted`. |
| `implementation` | Handed to delivery; the change that settles it claims it via `resolves: [OQ9]` in `delivery.yaml`. |

Once resolved, the bullet collapses to its question and its status. The answer lives in the decision it points at (in `03-decisions.md`).

## Open Questions

### Questions the experiments answered

- **OQ1: Can the module render the operator's whole install shape, names included?** Status: resolved-by-D2 (yes, with no cluster and CRDs equal, but only by writing the workload and RBAC in the manifest's shape; experiment 01).
- **OQ2: Does the two-step install work on a cluster with no OPM objects?** Status: resolved-by-D3 (yes, reinstall and upgrade too; a refused install changed the CRDs first and `--wait` returned before the operator reconciled, hence D3:R10, R12 to R14; experiment 02).

### Contract questions

- **OQ3: Who sets the adopt annotation when install migrates a manifest-installed operator?** Status: open. Blocking: acceptance: decides D8's contract and how it reads against 0012:D8:R3. Every object of an earlier release manifest is foreign to the new instance under 0012:D8, and the only override is a per-object adopt annotation naming the adopting instance. Options: (a) the user annotates each object, with install printing the exact commands; (b) install annotates exactly the objects it can prove belong to an earlier operator release (by name and the operator's own labels), which 0012:D8:R3 may read as a second override and would then need an amendment of 0012:D8; (c) a one-off migration subcommand that does (b) only when the user runs it. The adopt annotation is not implemented in either frontend (read from the CLI and library on 2026-10-04: no adopt key exists). Experiment 02 (step 6) answered what the guard does today: it sees every object of the earlier manifest as foreign and refuses at the first one, and the only check is the managed-by label (`cli/internal/inventory/stale.go`), so relabelling the objects as OPM-managed was enough for the CLI to take 18 of them over in place. That is narrower than 0012:D8's per-object annotation, which names the adopting instance; whichever option is chosen, the CLI's guard has to grow from "any OPM manager" to "this instance". The experiment does not choose between (a), (b) and (c): it only shows that once adoption is allowed, D2's names and selector make the rest of the migration an in-place apply.
- **OQ4: Does install refuse an operator version newer than the CLI?** Status: open. Blocking: acceptance: it is a refusal rule a user observes. The CLI refuses to drive an operator whose `MAJOR.MINOR` is above its own (0021:D9), but it learns the operator's version from the Platform only after the operator runs. A user who installs a newer module version than the CLI can then use none of the CLI's apply commands. Options: install refuses a module version whose `MAJOR.MINOR` is above the CLI's; install warns; install allows it, as selecting a newer manifest does today. A related case: a newer module may pin a core or catalog the CLI's kernel cannot render.
- **OQ5: Which platform does install render the operator module against?** Status: open. Blocking: acceptance: it decides whether an upgrade depends on the cluster Platform being healthy. The CLI renders against the cluster Platform when one exists and against a platform generated from the module's own pins otherwise. On a first install there is no Platform; on every later install there is, and its catalog subscription may lack what the module needs, or the Platform may be the reason the operator is being repaired. Rendering the operator module always against its own pins makes install independent of the Platform; rendering against the cluster Platform keeps one rule for every instance. D4 says install is the recovery path, which argues for the former. Experiment 02 (step 4) measured the coupling: the first install rendered against the module's own pins, and the reinstall after the Platform was seeded rendered through the cluster Platform. The render digest stayed the same only because the Platform subscribed to the same catalog release (4.5.2) the module pins; a Platform on another catalog release would re-render the operator's own install on the next reinstall, with no change by the user. The evidence does not decide the question; it shows the choice is observable on every reinstall.
- **OQ6: What does a downgrade do?** Status: open. Blocking: deferrable. Installing an older module version applies older CRDs over newer ones. A CRD that drops a stored version or narrows a schema can leave existing custom resources unreadable. Options: refuse a module version whose CRDs drop a version the cluster serves; warn; allow. The same check would guard an upgrade whose CRDs remove a served version (prior art: the CRD upgrade-safety preflight of OLM v1). Related, from experiment 01: the catalog's CRD resource cannot carry `conversion`, so the first operator CRD with two served versions and a conversion webhook needs a catalog change before the module can render it; the render refuses rather than dropping the field.
- **OQ7: Is the module's signing D1:R4's own rule or entry 0023's?** Status: open. Blocking: deferrable. D1:R4 asks the release to sign and attest the module like the image. Entry 0023 designs provenance and signatures for OPM artifacts as OCI referrers. If 0023 is accepted first, D1:R4 should depend on its decisions instead of stating a rule of its own; if not, the image's existing signing path is the interim answer.
- **OQ8: Does the module offer an opt-in applier identity?** Status: open. Blocking: deferrable. The operator applies instances as its own service account unless a default service account is set (D5), and its own role grants no workload rights, so a fresh install reconciles nothing until a platform team grants an applier. The module could offer an opt-in service account bound to a named role. That is a cluster-wide grant decision that belongs with entry 0029's applier-identity gate; until it is decided the module renders no applier. Experiment 02 worked around the gap the way the CLI's development cluster does: it applied a workload grant to the operator's own account outside the module before its fixture could reconcile without a per-instance applier.
- **OQ9: What is this entry's semver impact?** Status: open. Blocking: acceptance: determines `config.yaml.semver`. Install and the CRDs-only form now need a module registry, where the embedded manifest worked offline; selecting another version takes a module version instead of a release tag; uninstall deletes from the cluster's record instead of the CLI's list. On the CLI's beta line (0021:D7) a break is allowed as a declared change with a migration note; whether this entry is `major` or `minor` depends on how OQ3 and OQ4 settle.
- **OQ12: When may the operator module render its controller through the catalog's workload and role resources?** Status: open. Blocking: deferrable, because D2 already says what the module must keep and the manifest-shaped objects keep it today. Experiment 01 found three gaps on the catalog path: workload selectors always gain the instance and component labels, role bindings are named after their roles, and the security context has no seccomp field. The last is a catalog change any module that runs under the `restricted` profile needs. The first two are fixed by Kubernetes once an operator runs: moving the Deployment onto a catalog-derived selector deletes and recreates it, which D2:R7 forbids, unless the catalog lets a module keep an existing selector. What would settle it: whether the catalog offers a selector and binding-name override, and whether OPM wants its own controller to exercise the workload abstractions badly enough to carry that override.

### Implementation questions

- **OQ10: How does install take values from the user?** Status: open. Blocking: implementation. D5 makes the operator's tuning a set of instance values. Whether install takes a values file, typed options for the common fields, or both, is the CLI's to decide; the contract is D5:R1 to R3.
- **OQ11: How does the release produce the module's identity version?** Status: open. Blocking: implementation. The module version must equal the release version (D1:R1). The first-party catalog and the module fleet advance their identity file in the release pull request with the CLI's version command, and forbid a second writer to that file; the operator's release has no such step yet. The implementing change decides the step and proves that a re-run of a partly failed release does not republish a version.
