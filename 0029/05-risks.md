# Risks, Drawbacks, Alternatives: Gated Ownership Transfer from CLI to Operator

The largest risk is a check that passes while the operator fails, because a failed adoption cannot be undone by a command. Per-decision alternatives live in `03-decisions.md`.

## Risks and Mitigations

- **The access review passes and the operator's apply is still refused.** Experiment 02 measured the main gap: a review of the apply verbs alone passes a role whose rules the account does not hold, and the operator's apply is then refused for escalation. **Mitigation:** D3 R7 and R8 model escalation and the impersonation groups; with both, every prediction in experiment 02 matched. Residual: a module version the transfer did not review can still need more rights (next item).
- **A later module version adds a kind or a rule the applier cannot apply.** The gate proves rights over what the instance renders now, not over future versions. **Mitigation:** the operator stalls with an impersonated-apply refusal on that version, its normal path, and the transfer's report says the proof covers what is deployed now. With a named account the stall is rechecked on a slow timer (experiment 02 measured a 30-minute recheck), so a granted right takes effect late unless the instance is touched.
- **The operator refuses an adoption after the owner changed.** D4 proves reachability and byte identity where the fetch runs, which is after the write. The instance is then operator-owned and unadopted, and no command hands it back. **Mitigation:** the refusal comes before the finalizer, so nothing is applied and setting the owner back by hand should work (inferred from experiment 02 case 1, which measured the reverse only with a finalizer present). OQ8 puts the trade to the owner.
- **The operator's own module cache is stale.** The CUE module cache is keyed by module and version, not by registry, on both sides. Experiment 01 flipped an instance whose tag had been republished while the operator's cache was warm, and the operator applied the old bytes. **Mitigation:** D4 now refuses that adoption, because the stale render does not reproduce the stated digest. The remedy is evicting the operator's cache; the refusal must say so.
- **A tag republished after the transfer changes what the operator runs.** Experiment 01 evicted the operator's cache and restarted it after a republish: every operator-owned instance of that version re-rendered the new bytes and stayed Ready with no event but an apply. The recorded source fingerprint hashes the path and version strings, so nothing on the record names the bytes. **Mitigation:** none yet. [entry 0011's decision that published artifacts are immutable](../archive/0011/03-decisions.md#d10-published-artifacts-are-immutable-enforced-by-the-registry-across-every-path-it-hosts) requires a registry that refuses tag overwrites and records that GHCR, the registry the fleet uses today, has no tag immutability, so the requirement takes no effect until a conforming registry is in place. `opm module publish` refuses to overwrite a tag client-side, which is a better error, not a guarantee; `cue mod publish` overwrites. OQ9 holds the content-pinning question.
- **The CLI's field ownership outlives the transfer.** After a flip the CLI co-owns every field, so a field a later module version drops stays on the object while the operator reports Ready (experiment 02 case 3c). **Mitigation:** D8 releases it after the verdict. A transfer that ended before its verdict leaves it in place (OQ11).
- **A finalizer the operator added stays after the owner goes back to `cli`.** The CLI's delete then removes every object and reports success while the record hangs in deletion (experiment 02 case 1). **Mitigation:** D4 and D5 refuse before the finalizer, so the transfer path no longer creates the state. OQ10 covers the case where an adoption passed and failed later.
- **Every pre-upgrade instance fails the digest gate once.** When the digest definition changes, as 0012:D6 changes it, a digest recorded before the change never matches a re-render after it. **Mitigation:** D2 R7 reports which input moved; the remedy is one CLI re-apply, which rewrites the digest, then the transfer.
- **The operator's first reconcile after a transfer rolls the workload.** Experiment 02 case 3 confirmed 0006:D40's claim: the only change on all six objects was the managed-by label, every object kept its identity, and the pod template did not change. A Platform change between the CLI's apply and the transfer could still change the render. **Mitigation:** gate 11 renders against the cluster Platform and D4 compares the operator's own render, so any change surfaces before adoption.
- **A prune right after the transfer removes an object still labelled as the CLI's.** The operator's prune guard accepts objects of the same instance whichever runtime labelled them, and experiment 02 variant 3d saw it prune one. **Mitigation:** none needed; this is the behaviour 0006:D40 asked the prune guard to have, and it is how a module change right after a transfer takes effect.

## Experiment Surprises

Facts the experiments found that the design did not predict. Each is cited where a decision rests on it.

- **The two actors fingerprint the same inventory differently.** The CLI and the operator serialise an empty group or namespace differently, so the inventory fingerprint changes across a transfer even when the entry set is identical (experiment 02 case 3). The verdict compares entry sets (D2). Fixing the serialisation is a CLI change this entry does not require.
- **The old verification leaked its cache.** A CUE module cache extracts read-only files, so a plain recursive delete fails; the removed command would have left about 3 MB behind per run (experiment 01). The isolated cache of D2 R11 must be made writable before removal.
- **A plain registry overwrites tags.** `cue mod publish` replaced a published tag without complaint, while `opm module publish` refuses (experiment 01). OQ9.
- **The publish report names the logical path.** `opm module publish` printed the module's logical coordinate even when the registry mapping sent it to a prefixed repository, so which registry received the push was not visible (experiment 01).
- **The CLI's apply cannot recover a failed adoption.** On an operator-owned record it only edits the spec and waits; no CLI command writes the owner or the applier account (experiment 02 case 1). D1 keeps this out of scope; OQ8 and OQ10 bear on it.
- **Environment, not design.** Containers on the experiment host had no route to GHCR, so experiment 01 side-loaded the operator image and seeded its module cache, and experiment 02 ran the operator binary outside the cluster under the controller account's token. Identity, RBAC and the render path were unchanged. Creating a kind cluster also switched the shared kubeconfig's current context. Neither affects a decision.

## Drawbacks

- **The transfer needs administrator rights.** Reviewing another identity's access, reading the cluster Platform and reading the operator's readiness are not namespace-tenant rights. 0006:D17 already accepted this for the transfer.
- **The user must state two things the CLI used to leave unset.** The applier account and the prune intent become required inputs, so the transfer is one more decision for the user than the removed command was.
- **The operator gains refusal paths and a render it may not apply.** An instance that was adoptable by a hand flip before now stalls if it carries the marker or its render differs. Each first adoption costs the operator one render before the finalizer. That is the point, and it is still a behaviour change a user can observe.
- **The verification is slower than a warm render.** A cold, isolated verification fetches core and the catalog every time: about 3 seconds for a one-object module on a good link in experiment 01, against about a third of a second warm.

## Alternatives

- **No transfer; export to GitOps is the only path off the CLI.** A user who wants the operator, not Git, would have to commit a tree to get there. **Why not:** the owner chose to revive the transfer.
- **Operator-side gates only, through an admission webhook.** It refuses even the hand edit. **Why not:** a webhook outage blocks every instance write, and the access review and verification are cheaper to report from the CLI before any write.
- **The operator reports its registry mapping and the CLI checks reachability from its side.** The first draft of D4. **Why not:** experiment 01 showed the mapping names in-cluster hosts the CLI cannot reach, and a mapping does not prove bytes.
