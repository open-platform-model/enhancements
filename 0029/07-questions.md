# Open Questions: Gated Ownership Transfer from CLI to Operator

This is the entry's working question register. `OQ` numbers are permanent. Each unresolved entry carries a `Status:` line and a `Blocking:` field (`acceptance` with the reason inline, `deferrable`, or `implementation`). Once resolved, the bullet collapses to its question and its status; the answer lives in the decision it points at.

## Open Questions

### Blocking acceptance

- **OQ8: The owner chose a CLI-side registry-reachability gate; the evidence says the CLI cannot prove the operator's reachability. Is a refusal by the operator after the owner field changed acceptable?** Status: open. Blocking: acceptance, because it conflicts with the owner's 2026-10-04 selection ("Shape of the redesigned handoff?": "CLI gates + operator backstop (Recommended)": "revive opm instance handoff: old gate chain plus applier-identity and registry-reachability gates"), and no agent may settle that. The conflict: experiment 01 showed the operator's registry mapping names hosts only the cluster network resolves, and that a coordinate two registries serve differently passes every CLI gate. A CLI-side gate therefore cannot predict the operator's fetch, so D4 makes the operator prove it at adoption. The consequence is that an unreachable module is no longer refused before any write, as D2 R1 promises for every other gate. The instance becomes operator-owned, unadopted, stalled with the reason, with no finalizer and its workloads untouched; setting the owner back to `cli` by hand then works, as experiment 02 measured. Options for the owner: (a) accept this as drafted, with the CLI's report saying the owner changed and how to set it back; (b) add a pre-flip probe, where the operator renders a still CLI-owned instance on request without adopting it and reports whether it reproduces the verified digest, which changes 0006:D3's hands-off rule and adds a request path, while D4's check still runs at adoption; (c) let the CLI set the owner back itself when the operator refused the adoption without adding a finalizer or applying anything, which narrows D1 R3 and the forward-only rule of 0006:D16 for that one case.

### Questions the experiments answered

- **OQ1: Does a CLI-side fetch through the operator's reported registry mapping predict whether the operator can fetch the module?** Status: resolved-by-D4 (no; experiment 01).
- **OQ2: Does an access review over the recorded inventory predict whether the operator's apply succeeds?** Status: resolved-by-D3 (yes once RBAC escalation is modelled and the review carries the impersonation groups; experiment 02).
- **OQ3: Which CLI render inputs put bytes into a render that the recorded coordinate and values cannot reproduce?** Status: resolved-by-D6 (a directory, a local replacement, and a module package inside the instance's own module; experiment 01).
- **OQ4: Does the flip leave server-side-apply field ownership that the success verdict should judge?** Status: resolved-by-D8 (yes, the CLI co-owns every field and strands later removals; experiment 02).
- **OQ5: Should the operator compare its own render digest to the CLI-recorded digest before adopting, once 0012:D6 makes the digest runtime-neutral?** Status: resolved-by-D4 (yes, and it need not wait for 0012:D6; experiment 01).

### Open, not blocking acceptance

- **OQ6: Should the transfer offer to create the named applier account and its RBAC?** Status: open. Blocking: deferrable, because D3 refuses with the missing rights named, which is complete without a helper. A helper derived from the verification render would make the common case one command, at the price of deciding a security posture for the user. Experiment 02's prototype review already computes the full table of missing rights, including the escalation rights a role entry needs, so a helper would have its input. 0014's second question asks the same thing for export, and the two answers should agree. What would settle it: whether the owner wants generated RBAC to be a starting point the user reviews, or a maintained artifact.
- **OQ7: How does the operator recognise the instance that deploys it?** Status: partial. Blocking: implementation. D5 R2 and R5 require the refusal whatever the owner field says and whether or not an inventory is recorded, and D2 gate 4 requires the same recognition in the CLI. 0028:D4 keeps the operator's own instance CLI-owned but defines no marker for it. Experiment 02's sketch (case 5) answers the shape: no single signal suffices, because forks and mirrors rename the module path and a user can remove a label. The operator knows its own namespace, Deployment and service account, so it can refuse an instance whose recorded inventory, or whose render, contains them; the module path and an install label are cheaper early signals. What remains for the implementer: which signals each repo checks, and how the CLI learns the operator's own object identities for gate 4.
- **OQ9: Should an instance pin its module's content, not only its version tag?** Status: open. Blocking: deferrable, because a transfer verifies what the tag serves at transfer time, and D4 refuses an operator whose cache disagrees. The gap is afterwards. Experiment 01 republished a tag with other bytes; after the operator's cache was evicted and its pod restarted, every operator-owned instance of that version silently re-rendered the new bytes and stayed Ready. The record pins only a path and a version, and the recorded source fingerprint hashes those two strings, not the content. First-party module tags on GHCR are immutable by workspace policy, but `cue mod publish` overwrote a tag on a plain registry without complaint. Options: rely on registry tag immutability and document it; record a content digest at transfer that the operator enforces on every render; or record one on every apply, which touches the instance contract beyond this entry and bears on 0028's own module too. What would settle it: whether OPM supports registries that do not enforce tag immutability.
- **OQ10: What should happen to an operator finalizer left on an instance whose owner went back to `cli`?** Status: open. Blocking: deferrable, because D4 and D5 refuse before the finalizer, so the transfer path no longer leaves one. It still arises when an adoption passed the checks and failed later, and the owner was set back by hand. Experiment 02 case 1 measured it: the finalizer stays, the CLI's delete removes every object and reports success, and the record hangs in deletion until the finalizer is stripped by hand. Options: the operator removes its finalizer when it sees the owner is `cli`; the CLI refuses or warns on delete when a finalizer it does not own is present; or both. Either is an observable change in a repo this entry affects.
- **OQ11: Who releases the CLI's field ownership when a transfer ended before its verdict?** Status: open. Blocking: deferrable, because D8 covers every transfer that waits for its verdict. A transfer that timed out, or whose user interrupted the wait, leaves the CLI co-owning every field after the operator later adopts; gate 3 then refuses a re-run, because the record is operator-owned. Options: a CLI command that performs only D8's release on an operator-owned instance whose verdict now holds; or an operator-side migration of the CLI's field-manager entries on its first apply after adoption, which would also cover hand flips. What would settle it: whether the owner wants the operator to rewrite another manager's field ownership.
