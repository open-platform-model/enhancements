# Open Questions: Gated Ownership Transfer from CLI to Operator

This is the entry's working question register. `OQ` numbers are permanent. Each unresolved entry carries a `Status:` line and a `Blocking:` field (`acceptance` with the reason inline, `deferrable`, or `implementation`). Once resolved, the bullet collapses to its question and its status; the answer lives in the decision it points at.

## Open Questions

### Questions the experiments answer

- **OQ1: Does a CLI-side fetch through the operator's reported registry mapping predict whether the operator can fetch the module?** Status: open. Blocking: acceptance, because it decides whether D4's report is enough or the operator must resolve the module itself (D2 R5, D4). The CLI and the operator sit in different network positions. A mapping naming a host only the cluster network resolves fails from the CLI and works in the operator: a false refusal. A host reachable only from the user's machine, over a VPN or a local port, works from the CLI and fails in the operator: a false pass, which is the dangerous direction. Candidates: (a) the CLI fetches with the operator's mapping and accepts both error directions as documented limits; (b) the CLI fetches with the operator's mapping and also refuses when a mapped host is not one the cluster can resolve, if that is detectable; (c) the operator exposes a resolve request the CLI asks, which proves reachability from the right place at the cost of a new request channel. `experiments/01-provenance-digest-reachability/` measures (a) against a kind cluster whose operator maps to an in-cluster registry.
- **OQ2: Does an access review over the recorded inventory predict whether the operator's apply succeeds?** Status: open. Blocking: acceptance, because D3 R3 promises a refusal before the write, and a review that passes while the apply is refused reproduces the stranding the command was removed for. Known gaps: escalation prevention refuses a Role or ClusterRole whose content grants rights the applier lacks, even when the authorizer allows creating it; binding a role needs the bind right on that role. A server-side apply is a patch that may create, so the rights reviewed must match what the operator's apply actually issues, including for cluster-scoped entries and entries the operator never deletes (Namespaces, CRDs). `experiments/02-applier-identity-and-field-transfer/` applies an inventory holding a workload, a ClusterRole and a binding under an account the review passed, and records which refusals the review missed.
- **OQ3: Which CLI render inputs put bytes into a render that the recorded coordinate and values cannot reproduce?** Status: open. Blocking: acceptance, because D6 marks by that property and the operator backstop (D5) trusts the marker's absence. Known: a module applied from a directory, and a local replacement in the instance's module. Suspected: content an instance package adds beyond its values, a dependency served by a CLI-only registry mapping, and a module cache holding bytes the registry no longer serves. The digest gate catches each of these at transfer time; the question is which of them the marker must also catch so the refusal is early and the backstop sees it. `experiments/01-provenance-digest-reachability/` applies each input and records the marker and the strict re-render's verdict.
- **OQ4: Does the flip leave server-side-apply field ownership that the success verdict should judge?** Status: open. Blocking: acceptance, because it decides whether 0006:D40's inventory-stable verdict is enough (D2 R10). After the operator's first reconcile, fields only the CLI's field manager set may stay owned by it. If the operator's render later drops such a field, the operator's apply does not remove it, and the field outlives the module's intent. Candidates: (a) the verdict stays inventory-stable and the residue is documented; (b) the transfer's write releases the CLI's field ownership on the inventory's objects; (c) the verdict also reports objects with CLI-owned fields the operator did not apply. `experiments/02-applier-identity-and-field-transfer/` records managed fields before the flip, after the first reconcile, and after a module version that drops a field.

### Questions the experiments do not answer

- **OQ5: Should the operator compare its own render digest to the CLI-recorded digest before adopting, once 0012:D6 makes the digest runtime-neutral?** Status: open. Blocking: deferrable, because D5's marker refusal is complete without it and the comparison is an extra guard. Today 0006:D40 bans cross-actor digest comparison because each runtime stamps its own name into the render. 0012:D6 removes the name from the digest, so the operator could render, compare to the CLI's recorded digest, and refuse a mismatch before applying. That would catch a hand flip with the marker stripped, which no current gate catches. It would amend 0006:D40's first corollary and give the operator a render it does not apply, which costs memory and time on every adoption. What would settle it: 0012:D6 landing, and a decision on whether the cost of a pre-adoption render is worth the case it covers.
- **OQ6: Should the transfer offer to create the named applier account and its RBAC?** Status: open. Blocking: deferrable, because D3 refuses with the missing right named, which is complete without a helper. A helper derived from the recorded inventory would make the common case one command, at the price of deciding a security posture for the user. 0014's second question asks the same thing for export, and the two answers should agree. What would settle it: whether the owner wants generated RBAC to be a starting point the user reviews, or a maintained artifact.
- **OQ7: How does the operator recognise the instance that deploys it?** Status: open. Blocking: implementation. D5 R2 requires the refusal whatever the owner field says, and D2 gate 4 requires the same recognition in the CLI. 0028:D4 keeps the operator's own instance CLI-owned but defines no marker for it. A marker on the record written by the install is the obvious signal, but a user can remove it. The operator also knows its own Deployment's namespace and name, and could refuse any instance whose recorded inventory includes it, which survives a removed marker. Context for the implementer: the inventory is in the record's status and is written by the CLI for a CLI-owned instance, so it is present before any flip.
