# Open Questions: CUE Testing and Conformance

This is the entry's working question register and the single canonical location for it. `OQ` numbers are permanent. Each unresolved entry carries `Status:` and `Blocking:` (`acceptance` with the reason inline, `deferrable`, or `implementation`).

## Open Questions

### Axes and location

- **OQ1: Does the kernel's render join the version matrix?** Status: open. Blocking: deferrable. D5 renders through the pure-CUE oracle. A kernel axis (`library`/`opm` CLI version) would catch kernel-side drift in the same corpus the parity harness already guards per commit, at the cost of a fifth axis and a Go dependency in the suite's runtime. What would settle it: whether any drift the parity harness cannot see (a release-to-release change in what the CLI emits around the rendered objects) is worth a cell.
- **OQ2: Is the upstream axis `cue.dev/x/k8s.io` snapshot versions, or Kubernetes releases mapped to them?** Status: open. Blocking: acceptance, because "each version of Kubernetes is represented" is either a mechanical statement about snapshots or a claim that needs a maintained mapping, and D4's coverage clause reads differently under each. Measured: the module records no Kubernetes release; v0.7.0 and v0.10.0 differ in one group version. Candidates: the snapshot is the axis and the entry says so; a mapping table maintained in the suite; or ask upstream to publish the mapping. What would settle it: whether any consumer needs to pin "Kubernetes 1.32" rather than a snapshot.
- **OQ3: Does the raw family's inverse coverage report (upstream kinds with no member) ever gate?** Status: open. Blocking: acceptance, because it decides whether the raw family is a mirror or a deliberate subset, which is a catalog policy this entry should not set by accident. `catalog_opm/CLAUDE.md` calls the raw family "the last resort for what the abstractions do not model", which reads as subset. What would settle it: a statement from the catalog owners that the raw family is intentionally partial, in which case the report stays a report.
- **OQ5: Where does the conformance suite live?** Status: open. Blocking: acceptance, because it decides `config.yaml.affects` and whether the `#Area` enum and the workspace routing table change. Candidates: a new workspace repo with its own task entrypoint and CI matrix; a directory in `opm/` (meta, currently "no Taskfile"); a directory in `library` (rejected in D1's alternatives). What would settle it: whether a repo that owns no product artifact fits the workspace's repo model, which the `#Area` comment anticipates ("add a value here when a new primary repo joins").
- **OQ9: Do product repos fail or only report on conformance drift?** Status: open. Blocking: acceptance, because D3 says drift "fails unless explained" and must name where. Candidates: the suite's own CI is the only place it fails, and product releases consult it; a product release check runs the predecessor-versus-candidate cells and fails; both. What would settle it: whether the release pipelines (release-please in `core` and `catalog_opm`) can run a check against a branch-published pre-release tag before the release PR merges.

### Mechanism handed to implementation

- **OQ4: How are diagnostic positions excluded from comparison, and which runner drives the cases?** Status: open. Blocking: implementation. Evidence: `cue vet` prints position lines indented under each message and offers no flag found to suppress them; CUE's own testscript goldens include them because their fixtures never move. Candidates: compare message lines only; a custom compare verb; a canonicalising filter. Runner candidates: testscript over txtar (CUE's convention, Go), a shell loop, a `cue cmd` workflow. What would settle it: the first corpus and one core release's worth of position churn.
- **OQ6: Do the abstraction family's 163 in-module `_test*` assertions stay where they are?** Status: open. Blocking: deferrable. D1 says the in-package layer is theirs already; the question is only whether any migrate to the suite or are duplicated there. Leaning: stay, with the suite exercising the same transformers from outside.
- **OQ7: Should a negative in-package assertion be allowed to pass on an incomplete value?** Status: open. Blocking: implementation. Measured: the `!= _|_` guard treats incomplete as bottom. Candidates: accept it (concrete evaluation catches the incomplete field anyway); require the paired positive; add a concreteness check to the idiom. What would settle it: a case where an incomplete value would wrongly satisfy a negative assertion under the repo's check task.
- **OQ8: Do in-package test files ship inside published CUE modules?** Status: open. Blocking: implementation. `cue mod publish` publishes the module root; a build-tagged test file in the same package is part of the module unless excluded. Candidates: accept shipping them (inert to importers); a sibling test package (cannot see hidden fields); publish-time exclusion if the tooling offers one. What would settle it: measuring what `cue mod publish` includes and what `opm catalog publish` does about it.
