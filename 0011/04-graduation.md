# Graduation Criteria — Module and Catalog Publishing

This document records the gates that must hold before the enhancement advances along the design lifecycle. Treat these as design acceptance criteria, not implementation milestones — implementation progress lives in `config.yaml.implementation` and the `history` list.

## accepted → implemented

The design is shipped when:

- `opm module publish` and `opm catalog publish` exist as one implementation with two entry points, with test coverage on every refusal path, not only the happy path.
- `opm module version set` and `opm catalog version set` both write `identity/identity.cue` idempotently, preserving formatting, comments, and any type assertion on the field — with real repos as fixtures rather than synthetic ones. Both exist (D12); a shipped surface with only the catalog form has not implemented this design.
- **The tag names the declared version (D18).** Publishing a catalog declaring `1.2.0` under tag `v1.3.0` is refused, with both values printed. This is the case that passed every other gate — the major matches and the identity is concrete — and the test is worth writing precisely because nothing else catches it.
- **`opm module vet` carries the `cue.mod` agreement check (D16) and the tag/version check (D18).** Publish still performs both; the vet copy moves discovery earlier and is not a substitute.
- `opm catalog registry check` verifies a published catalog against the registry, and the same verification runs when a catalog is added to a `#Platform` registry. Its `--compat` mode (D7) exists and its **help text** says it is an aid rather than a gate — the distinction 0010 D35 rests on belongs where a catalog author meets it, not only in a design document.
- **D9's compatibility gate ships, and it is the field-wise walk rather than `Subsume`.** [`experiments/03-d27-compat-gate`](experiments/03-d27-compat-gate/) measured a single `cue.Value.Subsume` call at 10/14 forward and 8/14 reverse, failing on disjoint sets, and a three-rule field-wise walk at 14/14; a shipped gate built on `Subsume` has reintroduced the measured defect regardless of what it scores on the happy path. Three checks distinguish it: a removed field is refused, a **changed default** is refused (the violation the consumer side provably cannot catch, which is the gate's entire reason to exist), and a bumped `apiVersion` finds no predecessor and passes trivially.
- **The gate is level-aware (0010 D34), and the alpha case is tested.** An `v1alpha1` contract that removes a field publishes successfully; the same removal at `v1beta1` is refused. The alpha test is the one worth writing, because a gate that checks everything passes every beta test while silently contradicting D34.
- **The comparator lives in `library`, not in `cli`.** Publish, `opm catalog registry check --compat`, and any CI action share one implementation — the argument 0010 D32 makes for putting the single-provider guard in the kernel. Predecessor selection **moves** rather than being rewritten: `materialize/enumerate.go`'s `enumerateVersions` plus `filter.go:112`'s `highestStable` already do it, and 0010 D14 deletes `filter.go` out from under them.
- The identity-completeness gate is exercised against a tree with an unfilled field and refuses, with a message naming the field and its file.
- The local-override gate is exercised in all four states: module clean, module blocked, module allowed by `--skip-override-check`, catalog blocked with the flag passed and ignored. A fifth assertion goes with them: the published artifact resolves against **published** dependencies in every one of those states, including the flag case — the flag waives the gate, never the ignoring (D6).
- **`opm mod init` repairs an existing tree and refuses to invent identity (D20).** Three checks: a tree missing `identity/identity.cue` is repaired after a second confirmation that names every file and every value change; a tree stating no module path anywhere is *asked* rather than having one derived from the directory name; and no version is ever chosen by the tool.
- **`#CatalogMemberFQNGate` ships in `core` and publish refuses a member that fails it (D22).** Two checks, one per failure enhancement 0010 traded `core`'s FQN derivation away for: a blueprint declared one segment deep (0010 D42's grouped path) is refused, and a primitive whose authored `fqn` names a build the catalog is not (0010 D21's measured `cue vet -c` exit 0) is refused. Both surface CUE's own error rather than a recomputed string comparison. Without this the gate exists only as CUE in 0010's `schemas/target.cue`, and 0010 D17, D21, D25 and D42 all delegate to something that never shipped.
- **`#IdentityPackage` ships in `core` and the CLI validates against it through the CUE API (D21).** Two properties: `identity/identity.cue` gains **no import** and stays at the bottom of its module's graph, and a renamed field, a wrong type and a wrong constraint each produce CUE's own distinct error rather than one field-presence message. Enhancement 0010 D43 deleted a duplicate assertion on the strength of this validation existing, so a shipped design without it has left that check with nothing behind it.
- Every catalog repo's copy-and-stamp publish task is **deleted**, not disabled, and its release workflow calls the new command.
- `modules/Taskfile.yml`'s checksum-driven `publish` and `modules/versions.yml` are deleted, every module carries `identity/identity.cue` with a `metadata` derivation (D12), and a fleet sweep has published at least one real module and correctly no-opped on the rest.
- **The publish sweep is idempotent, demonstrated rather than assumed (D15).** Run it twice against a non-production registry: the second run publishes nothing and exits successfully, because its registry filter selected nothing — **not** because publish tolerated an already-published version. Invoking `opm module publish` directly on an already-published version must **error**. Both halves need a test; a sweep that exits zero by swallowing publish's refusal has implemented the design D15 rejected.
- **D17's cleanup has run, minus the part that cannot yet.** Owned by the `registry-cleanup` slice in [`plan.yaml`](plan.yaml) — the one `phase: migration` slice this entry carries, added 2026-08-05 after an audit found this gate owned by neither plan. The hyphenated `opmodel.dev/modules/test/hello-web` is renamed to `test/hello_web`; `opmodel.dev/modules/test/*` and its `-e2e` prerelease tags are relocated to `testing.opmodel.dev` or deleted; `opmodel.dev/test/cleanmod` is deleted. **The legacy `opmodel.dev/<name>/v1alpha1` repositories are explicitly *not* deleted** — the v0 fleet still pins them (0010 D18), and removing them is the v0 → v1 migration's step, not this one's. Three items this gate previously listed are already done, measured 2026-08-04: `opm-platform` is gone, the `library/testdata` fixture now lives at `testing.opmodel.dev/modules/web_app@v1`, and the `opm-experimental` spelling collision is resolved. `opmodel.dev/releases/*` is out of scope entirely (D14) — Flux artifacts, not CUE modules.
- **No namespace migration is expected, and its absence is the check.** Every `opmodel.dev/modules/*` repository holds the same path after this lands as before it (D13). A migration step appearing in an implementation slice means D13 was not read.
- A publish has been rehearsed end to end against a non-production registry, including the failure cases, before the first real one.
- `config.yaml.implementation.status = complete` with `date`; `history` names the landing milestones; `README.md` carries the implementation-status quote block and a filled `## Deviations from Design`.
